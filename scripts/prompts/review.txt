You are acting as a senior software engineer performing a rigorous code review for a production codebase.

Review the commit stored in "commit.txt" exactly as if it were a pull request submitted by another experienced engineer.

Base your review explicitly on this txt file, it is the only information available regarding the commit.

Perform a thorough review covering the following areas:

1. Correctness

* Look for logic errors.
* Verify invariants.
* Check edge cases.
* Consider off-by-one errors, integer overflow, nullability, ordering assumptions, and failure paths.
* Identify any assumptions that are not enforced.

2. Design & Architecture

* Evaluate whether the design fits the existing architecture.
* Consider extensibility and maintainability.
* Identify unnecessary complexity.
* Suggest cleaner alternatives where appropriate.

3. Performance

* Analyze algorithmic complexity.
* Evaluate memory usage.
* Look for hidden performance costs.
* Consider worst-case behavior, not only average cases.
* Discuss scalability.

4. Concurrency & Thread Safety

* Look for race conditions.
* Locking issues.
* Visibility problems.
* Atomicity assumptions.
* Deadlocks.
* If concurrency is irrelevant, explain why.

5. Reliability & Failure Modes

* Corruption handling.
* Recovery behavior.
* Resource leaks.
* Invalid inputs.
* Backward/forward compatibility.
* Upgrade and migration concerns.

6. API & Maintainability

* Naming.
* Readability.
* Encapsulation.
* Separation of concerns.
* Duplication.
* Documentation quality.
* Logging and observability.

7. Testing
   Evaluate the tests critically.

* What scenarios are covered?
* What important scenarios are missing?
* Which edge cases deserve additional tests?
* Do the tests actually verify the intended behavior?

8. Risk Assessment
   List anything that could become problematic in production, even if the implementation is technically correct.

9. Suggestions
   Provide concrete improvements, refactorings, or simplifications where appropriate.

For every issue you identify:

* Explain why it matters.
* Estimate its severity (Critical / High / Medium / Low).
* Explain how confident you are that it is actually an issue.

If you believe something might be wrong but cannot prove it from the diff alone, explicitly label it as a question rather than a defect.

Do **not** invent problems merely to appear critical. If a section has no concerns, explain why.

At the end, provide:

* Overall assessment
* Merge recommendation (Approve / Approve with comments / Request changes)
* Top 5 risks (ordered by importance)
* Confidence score (0–100%) indicating how confident you are in your review.
