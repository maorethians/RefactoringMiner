#F1M63, #YE6G3, #82W0B, #57XKN, #4QEDK, #C55PY: The refactoring introduces a new method `migrateResource` to handle both system index and data stream migrations. However, the logic for handling failures in `migrateSingleIndex` and `migrateDataStream` should be consistent. In `migrateSingleIndex`, exceptions are logged and passed to `markAsFailed`. In `migrateDataStream`, exceptions are caught and handled differently, sometimes restarting the migration or marking it as failed. This inconsistency could lead to different behaviors for similar failures in system indices versus data streams.

#F1M63, #YE6G3: The method `migrateSingleIndex` includes a check for whether the index is closed before proceeding with the migration. However, there is no corresponding check in `migrateDataStream`. This could lead to issues if a data stream's backing indices are closed during the migration process.

#F1M63, #YE6G3: The method `migrateSingleIndex` includes detailed logging and error handling for various stages of the migration process. However, `migrateDataStream` lacks similar detailed logging and error handling for each stage (e.g., starting the migration, checking its status). This could make debugging issues with data stream migrations more difficult.

#F1M63, #YE6G3: The method `migrateSingleIndex` includes a retry mechanism for creating an index if it fails initially. However, there is no similar retry mechanism in `migrateDataStream`. This could lead to failures in data stream migrations not being retried automatically.

#F1M63, #YE6G3: The method `migrateSingleIndex` includes a check for whether the index would match any composable or legacy templates before proceeding with the migration. However, there is no similar check in `migrateDataStream`. This could lead to issues if a data stream's backing indices are created and matched by unintended templates.
