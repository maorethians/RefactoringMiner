#RWY37, #6EVX2, #EZGRY, #YNSDQ, #2B6YT: The introduction of a `strict` parameter in `HttpVersion.valueOf` and its usage in `HttpRequestDecoder` and `HttpResponseDecoder` is a good step towards stricter version checking. However, the changes introduce some redundancy and potential confusion:
- The `valueOf(String text)` method now delegates to `valueOf(String text, boolean strict)` with `false` as the default value. This is fine but could be made clearer by documenting that `strict` defaults to `false`.
- The `HttpVersion(String text, boolean keepAliveDefault)` constructor also introduces a `strict` parameter, which is not used in all places consistently. For example, `version0(String text)` does not use the strict pattern matching unless explicitly called with `strict=true`.

#8C819: The introduction of `VERSION_PATTERN_STRICT` is appropriate for stricter version checking, but it should be ensured that this pattern is only used when necessary (i.e., when `strict` is true). The current implementation correctly uses the strict pattern based on the `strict` flag.

#T61HK, #742YH: The addition of parameterized tests for invalid HTTP versions in both `HttpRequestDecoderTest` and `HttpResponseDecoderTest` is a good practice to ensure that the decoder handles invalid input gracefully. However, there is a minor issue in `#742YH`:
- The test uses `\n\r\n` instead of `\r\n\r\n` for the CRLF sequence, which might not be correctly interpreted by the decoder.
