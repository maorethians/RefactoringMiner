#9X7BY, #BEGFT, #S5DJ4: The variable name `maxTaskProcessingQuantumNs` is misleading because it suggests a quantum of time for task processing, but the value is actually used to limit the duration spent running tasks before switching to IO. A more descriptive name could be `maxTaskProcessingDurationNs`.

#9X7BY, #BEGFT: The default value calculation for `DEFAULT_MAX_TASK_PROCESSING_QUANTUM_NS` uses a minimum of 100 milliseconds and converts it to nanoseconds. However, the system property is named `io.netty.eventLoop.maxTaskProcessingQuantumMs`, which implies that the value should be in milliseconds. The conversion to nanoseconds should be done after retrieving the value from the system property to avoid confusion.

#BEGFT: In the constructor with parameters `maxPendingTasks` and `rejectedExecutionHandler`, the check for `maxTaskProcessingQuantumMs` being zero is unnecessary because `ObjectUtil.checkPositiveOrZero` already ensures that the value is non-negative. The ternary operator can be simplified to directly assign the converted value or the default if it's zero.

#DCQ00: The comment in `runAllTasks(maxTaskProcessingQuantumNs);` suggests that tasks are run for a maximum configured amount of time before trying to run IO again, but the method `runAllTasks` typically takes an integer parameter representing the maximum number of tasks to run. The method signature and usage should be consistent.
