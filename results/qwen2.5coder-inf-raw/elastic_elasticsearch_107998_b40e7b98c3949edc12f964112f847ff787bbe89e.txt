#7JHT4, #XMSQD, #835X8, #97JCT, #E64VP, #88BM4, #GF4WX: The introduction of `ParsingException` and its usage to wrap `StackOverflowError` is a good step towards handling large statements gracefully. However, there are some concerns:
1. **Consistency in Exception Handling**: The `ParsingException` is used in different contexts (`RuleExecutor`, `Node`) with the same message format. Ensure that this exception is consistently handled across the codebase to avoid confusion.
2. **Test Coverage**: While a test case (`testNoStackOverflow`) has been added, it focuses on catching `ParsingException`. It would be beneficial to have additional tests that verify the behavior when a `StackOverflowError` is indeed thrown and correctly wrapped by `ParsingException`.
3. **Performance Impact**: Wrapping every call in `try-catch` blocks for `StackOverflowError` can introduce performance overhead, especially in frequently called methods like `forEachDown`. Consider whether this approach is necessary or if there are more efficient ways to handle large statements.
4. **Source Text Availability**: The use of `plan.sourceText()` and `this.sourceText()` assumes that the source text is always available. Ensure that these methods do not return null or throw exceptions, which could lead to additional issues.
