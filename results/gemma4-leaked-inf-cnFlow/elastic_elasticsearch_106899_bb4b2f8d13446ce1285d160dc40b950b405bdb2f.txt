#DJPE3: The `Locate.process` method contains a logic error regarding Unicode handling. While it correctly calculates the starting offset using code points via `UnicodeUtil.codePointCount` and `utf8ToString.offsetByCodePoints`, it relies on `String.indexOf` to find the substring. `String.indexOf` returns a UTF-16 char offset, not a code point index. For strings containing characters outside the Basic Multilingual Plane (e.g., emojis), this will result in an incorrect 1-based position.

#DJPE3: The performance of `Locate.process` is suboptimal as it converts both the source string and the substring from `BytesRef` to Java `String` objects on every call. Since this method is executed per row within a page, this creates significant memory pressure and garbage collection overhead.

#P3DEE: There is an inconsistency in null handling between the block-based and vector-based evaluation paths. In the block path (`eval(int positionCount, BytesRefBlock strBlock, ...)`), if an input is null, `result.appendNull()` is called, resulting in a `NULL` output for that row. However, in the vector path (`eval(int positionCount, BytesRefVector strVector, ...)`), the code calls `Locate.process`, which returns `0` when inputs are null. This means the same query will produce different results (NULL vs 0) depending on whether the underlying data is stored as a vector or a block.
