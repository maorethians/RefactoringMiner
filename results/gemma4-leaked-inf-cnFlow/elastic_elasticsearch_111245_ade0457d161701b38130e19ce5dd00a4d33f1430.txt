#3TRGR: The current implementation serializes the `WatchRecord` to JSON to check its size before deciding whether to truncate it. If truncation is required, it performs a second serialization of the redacted record. While this involves multiple serialization passes for oversized records, this is an acceptable trade-off given that these are exceptional cases and the primary goal is to ensure the document can be indexed.

#QF8DR, #NF5P5, #CYM98: The implementation of `dropLargeFields` in `#QF8DR` and `#NF5P5` correctly handles nullability for `input` and `executionResult`, ensuring that truncation helpers in `#CYM98` are only called when data exists to be truncated. The use of a dedicated "truncated" type/value provides clear visibility in the history logs when data has been redacted.

#21BPQ, #2MPQS: The addition of both integration tests (`#21BPQ`) and unit tests (`#2MPQS`) comprehensively covers:
- Records below the limit (no truncation).
- Records above the limit (successful truncation).
- Edge cases where input or results are null.
- Different types of records (`MessageWatchRecord` and `ExceptionWatchRecord`).
