#4BZ40, #WDWMP, #MBSHW, #AGYGZ, #EJWNX, #2XFNV, #3EA2M: The introduction of `maxTaskProcessingQuantumNs` and its conversion from milliseconds to nanoseconds is clear. However, the default value of 1000 milliseconds (or 1 second) seems quite high for a processing quantum in an event loop context. This might lead to long periods where IO operations are blocked by task execution. Consider whether this default makes sense for typical use cases and if it should be lower.

#EJWNX, #2XFNV: In the constructors that now accept `maxTaskProcessingQuantumMs`, there is a check using `ObjectUtil.checkPositiveOrZero`. If the value is zero, it defaults to `DEFAULT_MAX_TASK_PROCESSING_QUANTUM_NS`. This behavior might be confusing because setting the quantum to zero would not disable task processing but instead use the default. Consider whether this is the intended behavior or if zero should mean no time limit.

#PC2PV: The change in `runAllTasks` from using a fixed number of tasks (`maxTasksPerRun`) to running for a maximum duration (`maxTaskProcessingQuantumNs`) is significant. Ensure that this change does not introduce regressions in performance or behavior, especially since the previous mechanism was based on task count rather than time. Consider adding test cases to verify that the new logic behaves as expected under various conditions.
