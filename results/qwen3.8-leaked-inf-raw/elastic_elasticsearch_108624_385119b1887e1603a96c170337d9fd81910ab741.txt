#7NC97, #W2JRP, #VFEWW, #4495P: The `createDummyRollupIndex()` helper is called from three different test methods within the same test class. Each call issues `PUT /dummy-rollup-index`, which will throw a `ResponseException` (400 `resource_already_exists_exception`) if the index already exists from a prior test in the same cluster. Depending on the test framework's per-test cleanup behavior, the second and third invocations may fail. Consider making the creation idempotent, e.g. by catching the "already exists" response or checking for index existence first:
```java
private static void createDummyRollupIndex() throws IOException {
    Request req = new Request("PUT", "dummy-rollup-index");
    req.setJsonEntity(...);
    try {
        client().performRequest(req);
    } catch (ResponseException e) {
        if (e.getResponse().getStatusLine().getStatusCode() != 400) {
            throw e;
        }
        // index already exists, safe to ignore
    }
}
```

#VG9V6: Two observations:
1. **Typo in the user-facing error message**: "therefor" should be "therefore". This string is returned to API callers, so it should be polished.
2. **No test exercises the rejection path.** Every test in this PR adds a dummy rollup index to *bypass* the new check, but there is no test that verifies the check actually fires—i.e., a `PUT _rollup/job/<id>` in a cluster with zero rollup jobs and zero rollup indices should return the `IllegalArgumentException`. A dedicated yaml REST test (or a unit/integration test) that asserts the 400 response and error message would close this gap.

#H2WK9: The token-walking logic is correct for the happy path, but there is a subtle fragility: the method assumes the filtered parser will always emit a `START_OBJECT` as the very first token. If the `XContentParserConfiguration` filtering with `includeRoot = false` ever changes the root-level token emission (e.g., in a future refactoring of the filtering layer), the first `if` would silently fail and the method would always return `false`, effectively disabling the guard. A more defensive approach would be to use `parser.nextToken()` in a loop or to assert the expected structure with a clear error message. Additionally, consider adding a brief comment explaining *why* the manual token walk is preferred over `sourceAsMap()` (the existing comment helps, but a note about the `includeRoot` parameter's effect on the token stream would aid future maintainers).
