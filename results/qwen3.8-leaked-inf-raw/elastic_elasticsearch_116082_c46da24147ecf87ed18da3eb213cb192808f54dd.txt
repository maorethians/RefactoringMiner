#5ECFD, #VJQJ9: The test `testBitAndCount` only exercises `andBitCountLong`. Since `andBitCountInt` is the path selected on aarch64 (per the `BIT_COUNT_MH` dispatch in #VKZZW), it would be valuable to add a parallel test:
```java
public void testBitAndCountInt() {
    testBasicBitAndImpl(ESVectorUtil::andBitCountInt);
}
```
The two implementations stride differently (4-byte vs 8-byte views) and use different `BitUtil` accessors, so a bug in one wouldn't necessarily manifest in the other.

#VRVZ1: In the `BitDotProduct` constructor accepting `List<Number>`, both `floatQueryVector` and `byteQueryVector` arrays are allocated unconditionally before `isFloat` is determined:
```java
float[] floatQueryVector = new float[queryVector.size()];
byte[] byteQueryVector = new byte[queryVector.size()];
```
Only one of the two is retained; the other is discarded. For large vectors this means a transient allocation of `size * 4` or `size * 1` extra bytes. A two-pass approach (first determine `isFloat`, then allocate only the needed array) would avoid this, though the impact is minor since these are short-lived.

#VP1N8, #EVM7B: The dispatch logic in `dotProduct(byte[])` uses a length equality check to decide between AND-bit-count and masked-sum:
```java
if (queryVector.length == vectorValue.length) {
    return andBitCount(vectorValue, queryVector);
}
return ipByteBit(queryVector, vectorValue);
```
This is correct given the upstream dimension validation in `BitDotProduct`, but the two call sites (`BitBinaryDenseVector` and `BitKnnDenseVector`) duplicate the same logic. If the dispatch rule ever changes (e.g., adding a new interpretation), both must be updated in lockstep. Consider extracting a shared helper or placing the dispatch in a common base/utility method to keep the two implementations in sync.
