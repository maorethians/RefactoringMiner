#0MMCM, #3C418: In `parseNonDynamicArray`, the ignored field name is constructed as `context.parent().name() + "." + arrayFieldName` (e.g., `"span.links"`), and in the `ObjectMapper.write` method the filter set is built from `IgnoredSourceFieldMapper.NameValue::name` (the full dotted path). However, the comparison is against `field.fieldName()`, which for a child field loader within the `span` object would return the simple name `"links"`, not `"span.links"`. This means the `arrays.contains(field.fieldName())` check will not match for non-root arrays, so the deduplication filter is ineffective in that case.
The bug is currently masked because `cloneSubContext` advances the original parser past the array, so the parent's field loader for the array field likely has no value and `field.hasValue()` is already `false`. But if any code path populates the field loader for the array field (e.g., a future change or a different parsing route), the filter would silently fail to prevent duplicate output. Consider comparing against `ignored.getFieldName()` (the simple name) instead of `ignored.name` (the full path), or building the set from `getFieldName()`:
```java
Set<String> arrays = ignoredValues.stream()
    .map(IgnoredSourceFieldMapper.NameValue::getFieldName)
    .collect(Collectors.toSet());
```

#6W34B: The refactored `encodeAndDecode` helper now delegates to `builder.copyCurrentStructure(parser)` instead of the previous `XContentDataHelper.encodeToken(p)` / `XContentDataHelper.decodeAndWrite(builder, ...)` round-trip. This means the scalar-type tests (`testBoolean`, `testInt`, `testLong`, `testFloat`, `testDouble`, `testString`, `testArrayInt`) no longer exercise the `encodeToken` → `decodeAndWrite` path. Only `testObject` still covers that path. Since `encodeToken` remains a production code path (used by `IgnoredSourceFieldMapper` for non-array ignored fields), consider keeping at least one scalar-type test that goes through `encodeToken`/`decodeAndWrite` to preserve coverage of that encoding/decoding round-trip.

#Y6Q6Q: `cloneSubContextWithParser` returns a `Tuple<DocumentParserContext, XContentParser>`, but the `DocumentParserContext` (created via `cloneDocumentParserContext`) already wraps its own `XContentParser` over the same byte array. The caller ends up with two independent parsers over identical data. If the intent is to give callers a choice between a context-wrapped parser and a raw parser, the Javadoc should make that distinction explicit and explain when each is appropriate. Otherwise, the method could be simplified to return just the `DocumentParserContext` (as `cloneSubContext` does), reducing the risk of a caller accidentally using the "wrong" parser.
