#Z9XB0, #Z6RJ6: The `doProcessCount` field is a plain `int` that is read and decremented in `doProcess` without synchronization. While the test flow is sequential in practice, `doProcess` is a method on a shared object and could theoretically be invoked from different threads (e.g., if the async job mechanism dispatches work on a different thread). Using `AtomicInteger` with `decrementAndGet()` / `get()` would make the intent and safety explicit, and the cost is negligible in a test.

#5ZN1G: The `bulkItemResponses` helper interleaves `id.get()` (in the second `.map`) with `id.getAndIncrement()` (in the `toMap` key function) inside a single stream pipeline. This works correctly for sequential streams because each element fully traverses the pipeline before the next begins, but it is fragile and hard to verify at a glance. A simple indexed loop or `IntStream.range` would make the ID assignment unambiguous and avoid relying on stream evaluation order for a side-effecting counter.

#5P3ME, #YBR2R: The two sites use different mechanisms to detect `IndexNotFoundException`:
- `#5P3ME` checks `IndexNotFoundException.class.isAssignableFrom(cause.getClass())` on the *direct* cause of the bulk item failure.
- `#YBR2R` checks `elasticsearchException instanceof IndexNotFoundException` on an already-unwrapped throwable.
Both are correct for the typical Elasticsearch bulk-failure shape (where the cause is the exception itself). However, if a future change wraps `IndexNotFoundException` inside another `ElasticsearchException` (e.g., a `ShardSearchFailure` or a custom wrapper), the `instanceof` check in `#YBR2R` would miss it while the `isAssignableFrom` check in `#5P3ME` would also miss it (since it only inspects the immediate cause class). Consider whether a small helper that walks the cause chain (similar to the existing `unwrappedThrowable` logic) should be shared between both call sites to keep the detection consistent.
