#F2WWP: The `ascending` method for doubles computes the median as `(values.getDouble(middle - 1) + values.getDouble(middle)) / 2`, while `doubleMedianOf` (used in the non-ascending `finish` path) computes it as `(values[middle - 1] / 2 + values[middle] / 2)` and additionally applies `NumericUtils.asFiniteNumber(median)`. These two formulas differ for extreme values: `(a + b)` can overflow to `Infinity` while `a/2 + b/2` cannot. For example, with values `[Double.MAX_VALUE/2, Double.MAX_VALUE]`, the ascending path computes median as `Infinity`, producing an incorrect MAD, while the non-ascending path would correctly compute `3*MAX/4`. The `ascending` method should use the same overflow-safe formula and apply `asFiniteNumber` for consistency with `doubleMedianOf`.

#JR3J0: The generated `evalAscendingNullable` and `evalAscendingNotNullable` methods for `MvMedian` allocate a `MvMedian.Doubles work = new MvMedian.Doubles()` object that is never passed to `MvMedian.ascending(v, first, valueCount)`. This is an unnecessary per-call allocation. Since this is generated code, the fix would be in the `MvEvaluatorImplementer` template to skip emitting the work variable when `withWorkParameter` is false.

#F2WWP: The `finish` method (used for the signed `long` type) uses `unsignedDifference` and `unsignedLongMedianOf` to compute absolute deviations and their median. While this may be functionally correct (since absolute differences are non-negative and thus compare identically under signed/unsigned ordering), the comment `// From here, this array contains unsigned longs` is misleading in a method that processes signed long inputs. A reader would reasonably expect `Math.abs(value - median)` or the explicit `value > median ? value - median : median - value` pattern used in `finishInts`. Consider either using the same explicit signed-difference pattern as `finishInts` (with `Math.subtractExact` for overflow safety) or adding a clearer comment explaining why unsigned arithmetic is safe here.
