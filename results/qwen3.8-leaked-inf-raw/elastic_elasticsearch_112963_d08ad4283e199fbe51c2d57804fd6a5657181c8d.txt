#M737X, #4609P, #MA4CR, #DVQCG, #CGVY6, #D12YV, #182NG, #XP7RZ, #694Y8, #0H63S: `IgnoredSourceFieldMapper.ensureLoaded` dereferences `indexSettings` unconditionally (`indexSettings.getSkipIgnoredSourceRead()`), but eight test call sites now pass `null` for the `indexSettings` parameter of `NestedObjectMapper.Builder`. If any of those mapper instances ever reach `syntheticFieldLoader()` → `ensureLoaded(...)`, this will throw a `NullPointerException`. While the current tests likely don't exercise that path, it is a latent NPE. Consider either making `ensureLoaded` null-tolerant (treat `null` as "not skipping") or asserting non-null in the `NestedObjectMapper` constructor so the contract is explicit.

#H9JY0: The test class covers `skip_ignored_source_read` and `skip_ignored_source_write` independently, but there is no test where **both** settings are enabled simultaneously. In that combined state the field is neither written nor read, and the synthetic source should be empty. Adding a test for this combination would guard against an interaction bug (e.g., a code path that assumes "if write is skipped, read must still work" or vice-versa).

#M737X: The `syntheticSourceSupport()` override returns a `SyntheticFieldLoader` whose `hasValue()` always returns `false`, `write()` is a no-op, and `docValuesLoader()` returns `null`. The only functional effect is declaring the field key in `storedFieldLoaders()` so `SourceLoader` knows to load it. This is a valid "declaration-only" pattern, but it is easy for a future reader to mistake the no-op methods for a bug or dead code. A brief comment on the `SyntheticSourceSupport.Native` constructor call (e.g., *"Declaration-only loader: actual decode/write is performed by SourceLoader"*) would make the intent immediately clear.
