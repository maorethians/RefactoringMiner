#Q2QYN, #8FYCF, #9812Q, #0CA5Y, #MAZ5Q, #NY8W5: The `logger.warn` added in the `add` method (#0CA5Y) is problematic in two ways:
1. **It is unconditional** — there is no guard checking whether the service is actually closed. This means the warning will fire on *every* watcher registration, including the normal startup path where the service is fully operational. This will produce misleading log noise in production.
2. **The message contradicts the code** — it says "cannot add resource watcher" but the very next line calls `watchers.add(watcher)`. If the intent is to warn that a watcher added after close will never be triggered (because the executor is terminated), the message should reflect that (e.g., "resource watcher service is closed; watcher will not be monitored"). If the intent is to *prevent* the add, the `watchers.add(...)` call should be removed and a no-op handle returned.
As written, this will either spam warnings on every legitimate add or silently mislead operators about what actually happened.

#8FYCF: The `RejectedExecutionHandler` lambda throws `IllegalStateException` when `exec.isShutdown() == false`. Because `ScheduledThreadPoolExecutor` uses an unbounded `DelayedWorkQueue`, rejection in practice only occurs during/after shutdown, so the "not shut down" branch is effectively unreachable. That is fine as a defensive assert, but be aware that if it *were* ever hit, the exception would propagate out of `threadPool.scheduleWithFixedDelay(...)` in the constructor, causing the entire `ResourceWatcherService` construction to fail. Consider whether a hard failure at construction time is the desired behavior versus logging and degrading gracefully (the service would simply not monitor).

#8FYCF: When `enabled` is `false`, the three `ResourceMonitor` fields are explicitly set to `null`. These are `final` fields, so any code path that dereferences `lowMonitor`/`mediumMonitor`/`highMonitor` without first checking `enabled` will throw a `NullPointerException`. The `close()` method is guarded by `if (enabled)`, but any future caller (or test) that accesses the monitors directly will hit an NPE. Consider documenting the invariant or adding a null-check helper to make the contract explicit.
