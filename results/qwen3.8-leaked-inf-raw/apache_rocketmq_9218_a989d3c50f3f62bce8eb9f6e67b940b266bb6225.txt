#S1K7R: In addition to the condition change, this hunk removes the final fallback:
```java
-            if (pullOffset < 0) {
-                pullOffset = brokerOffset;
-            }
```
Previously, in the pop path, `pullOffset` had a three-level fallback: `popBufferMergeService.getLatestOffset` → `offsetManager.queryOffset` → `brokerOffset`. Now only the first two remain. If both of those return a negative value (e.g., the group has no recorded offset yet), `pullOffset` stays negative and the subsequent `brokerOffset - pullOffset` calculation in `getAvailableMsgCount` will produce an inflated (or nonsensical) available-message count.
The `else` branch (`offsetManager.queryPullOffset`) also lacks such a guard, so the two paths are now symmetric—but that symmetry may be masking a real edge case. Please confirm that `offsetManager.queryOffset` is guaranteed to return a non-negative value in every scenario where the KV service is disabled, or restore the `brokerOffset` fallback to avoid a regression in the "no offset recorded yet" case.
