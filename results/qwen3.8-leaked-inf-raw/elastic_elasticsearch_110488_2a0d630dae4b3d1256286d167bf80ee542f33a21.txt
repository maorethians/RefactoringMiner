#7XJAN: The change from returning a list containing an unresolved attribute (a soft, user-facing failure) to throwing `IllegalStateException` is a significant behavioral shift. `IllegalStateException` signals a programming error and typically surfaces as a 500 to the user. If this code path can still be reached due to user input (e.g., an ambiguous reference that the new `mergeOutputExpressions` logic doesn't fully eliminate), the user will receive an opaque server error instead of the previous descriptive message ("Reference [x] is ambiguous; matches any of ..."). Consider whether a user-facing exception type (consistent with other ESQL analysis errors) would be more appropriate here, or add a comment clarifying that this path is guaranteed unreachable after the new validation and merge logic.

#4HXQD: The double-cast `(List<Alias>) (List) mergeOutputExpressions(...)` is a code smell that obscures intent. If `mergeOutputExpressions` returns a raw `List` or a `List<? extends NamedExpression>`, it would be cleaner to either:
- Have `mergeOutputExpressions` return `List<Alias>` directly (via a typed overload or generic parameter), or
- Use a single cast with a local variable and a brief comment explaining why the intermediate raw-type step is needed.
The `@SuppressWarnings("unchecked")` is fine, but the double-cast pattern makes it harder for future readers to verify type safety.
