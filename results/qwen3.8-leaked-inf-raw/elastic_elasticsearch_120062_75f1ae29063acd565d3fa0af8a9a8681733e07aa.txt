#DW5BH: The core fix replaces `searchContext.shardTarget().getShardId().id()` with `searchContext.request().shardRequestIndex()`. This is correct: when a search spans multiple indices via an alias, the shard ID (e.g., `0`) is not unique across indices, so using it as a key for shard results can cause collisions. `shardRequestIndex()` provides a globally unique position within the overall shard request, which is the right identifier here.

#B076X: The REST test sets up a realistic alias collision scenario (two indices with overlapping shard IDs, one empty). A couple of minor observations:
- The test only asserts that the correct document is returned (`hits.total.value: 1`, `hits.hits.0._id: "doc_1"`). Since there is only one document in the entire alias, the ranking is trivially correct. If the bug manifests as incorrect *scoring* or *explanation* attribution (rather than missing results), this test may not fully exercise the fix. Consider also asserting on the explanation or score to confirm the shard result was correctly attributed.
- The test does not verify behavior when the document lands in a shard whose ID collides with the other index's shard. Since `second-test-index` has 2 shards and the single document could land in either shard 0 or shard 1, the collision with `first-test-index`'s shard 0 is only guaranteed if the document ends up in shard 0. In practice, with a single document and default routing, it will go to shard 0, so this is fine, but it's worth being aware of the implicit assumption.
