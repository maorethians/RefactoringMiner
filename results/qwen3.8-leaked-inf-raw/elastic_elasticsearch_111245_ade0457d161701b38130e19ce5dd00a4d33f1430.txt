#H5BNE, #DCF3H, #5PZ5S: The `getTruncatedInput()` method's `toXContent` implementation writes a bare JSON value (`builder.value(TRUNCATED_RECORD_VALUE)`), but both the integration test (`HistoryIntegrationTests.testThatHistoryIsTruncated`) and the unit test (`HistoryStoreTests.testPutLargeHistory`) expect `input` to be a JSON **object** containing the key `TRUNCATED_RECORD_KEY`:
```java
Map<String, Object> input = source.getValue("input");
assertThat(input.containsKey(WatchRecord.TRUNCATED_RECORD_KEY), equalTo(true));
assertThat(input.get(WatchRecord.TRUNCATED_RECORD_KEY), equalTo(WatchRecord.TRUNCATED_RECORD_VALUE));
```
The commented-out code in the same method shows the correct implementation that matches the tests:
```java
// builder.startObject();
// builder.field(TRUNCATED_RECORD_KEY, TRUNCATED_RECORD_VALUE);
// builder.endObject();
```
As written, the serialized `input` field will be a plain string (e.g., `"input": "Watch history record exceeded..."`), which will cause a `ClassCastException` when the tests cast it to `Map<String, Object>`. The active `toXContent` body should use the object/field form (the commented-out lines) to be consistent with how the normal input is serialized and with the test assertions.

#EY0X0: After calling `dropLargeFields()` and re-serializing, there is no check that the resulting record actually fits within `maxHistoryRecordSize`. If the large contribution comes from other fields (e.g., `vars`, `watch`, or `triggerEvent`), the record will still exceed the limit and be indexed as-is. Consider either:
- Logging a warning when the truncated record still exceeds the limit, or
- Documenting that this setting only guarantees truncation of `input` and `result` fields, not a hard cap on total document size.
