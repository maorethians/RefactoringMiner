#93K0X: The expression `indexMetadata.getTierPreference().isEmpty() == false ? indexMetadata.getTierPreference().getFirst() : ""` calls `getTierPreference()` twice. While not a correctness bug, storing it in a local variable would be clearer and avoid the redundant call:
```java
var tierPreference = indexMetadata.getTierPreference();
String tier = tierPreference.isEmpty() == false ? tierPreference.getFirst() : "";
```

#MQ7W9, #DZZAJ, #KN5XK, #BF12P, #BXXNE: The `maybeRewriteBasedOnConstantFields` method is duplicated verbatim across five query builder classes (`MatchQueryBuilder`, `PrefixQueryBuilder`, `TermQueryBuilder`, `TermsQueryBuilder`, `WildcardQueryBuilder`). While this follows the pre-existing pattern of each class having its own `doIndexMetadataRewrite` logic, extracting this into a shared utility (e.g., a static method on `ConstantFieldType` itself, or a small helper class) would reduce the maintenance surface. If the rewrite logic ever needs to change (e.g., adding a new constant-field query result type), five call sites would need updating. This is a suggestion rather than a blocker, but worth considering for the codebase's long-term maintainability.

#MQ7W9, #DZZAJ, #KN5XK, #BF12P, #BXXNE: In `maybeRewriteBasedOnConstantFields`, the `else` branch contains only `assert false : ...`. In production (where assertions are disabled), if `internalTermQuery` ever returns a query that is neither `MatchAllDocsQuery` nor `MatchNoDocsQuery`, the method silently falls through to `return this` with no diagnostic. Consider adding a `logger.debug(...)` or `logger.warn(...)` before the `return this` so that unexpected behavior is at least observable in production logs without the cost of a full exception.
