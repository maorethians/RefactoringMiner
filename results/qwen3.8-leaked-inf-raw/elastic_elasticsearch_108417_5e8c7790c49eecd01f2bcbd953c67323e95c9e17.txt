#X8FT7: There is a bug in the `parentOffset` calculation. The code constructs the `NameValue` name using `context.parent().name()` (the simple name) but computes the offset using `context.parent().fullPath().length() + 1` (the full path length). These will differ for nested objects, causing a `StringIndexOutOfBoundsException` or incorrect field name extraction.
For example, with a 3-level nesting (`a` → `b` → `c` where `b` has `store_array_source`):
- `name` = `"b.c"` (length 3)
- `parentOffset` = `"a.b".length() + 1` = 4
- `getFieldName()` = `"b.c".substring(4)` → **StringIndexOutOfBoundsException**
The offset should be derived from the same string used to build the name:
```java
isRoot ? 0 : context.parent().name().length() + 1
```
The existing tests only exercise 2-level nesting (root → child) where `name()` equals `fullPath()`, which is why this isn't caught.

#JCNAH: The deduplication logic via `putIfAbsent` may not work as intended for non-root objects. The ignored value is keyed by `value.name()` (e.g., `"stored.path"`), while the `SyntheticFieldLoader` is keyed by `field.fieldName()` (e.g., `"path"`). Since these keys differ, `putIfAbsent` will not detect the collision, potentially writing the field twice (once from the stored source, once from doc-values reconstruction). This is related to the naming inconsistency in #X8FT7 — if the `NameValue` name were just the simple field name (matching `fieldName()`), the deduplication would work correctly.
