#7VH1X, #TA7QG, #3KE69, #YQCN7, #VR0EF, #C7PV8, #B24AY, #TTPN5, #YQ1XX, #0VZSK: The `isAlive` flag is set to `false` in the release lambda but is never reset to `true` when `capturing()` is called again on the same instance. This means a `MockLogAppender` that is captured, released, and then captured again will silently stop receiving events (the `RealMockAppender.append()` loop skips it). The new test `MockLogAppenderTests` exercises exactly this reuse pattern in a 1000-iteration loop, but since it never adds expectations, the bug is invisible. The old code (with `start()`/`stop()`) supported re-activation. Consider resetting `isAlive.set(true)` at the top of `appendToLoggers`, or documenting that instances are single-use.

#VR0EF, #B24AY: The dispatch in `RealMockAppender.append()` performs an exact string match: `mockAppenders.getOrDefault(event.getLoggerName(), List.of())`. In the previous implementation, attaching the appender to a Log4j logger meant that events from child loggers would propagate up and be captured (standard Log4j2 additivity). Now, registering for `"org.elasticsearch"` will not match events logged by `"org.elasticsearch.SomeClass"`. All current call-sites in this PR use leaf-level names so nothing breaks today, but this is a silent behavioral narrowing that could surprise future test authors who register a package-level logger expecting hierarchical capture. If hierarchical matching is not intended, a brief note in the Javadoc of `capturing(...)` would help; if it is intended, the lookup would need to walk the logger name hierarchy.
