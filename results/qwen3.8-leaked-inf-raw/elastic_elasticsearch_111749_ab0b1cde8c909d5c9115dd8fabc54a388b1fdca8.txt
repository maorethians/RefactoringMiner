#7QHJH: There is a significant index-offset bug in the sorted-ascending fast path of all three `process*` methods. When `valuesBlock.mvSortedAscending()` is true, the code reads values using absolute indices (`0`, `valueCount - 1`, `lowerIndex`, `upperIndex`) instead of offsetting by `firstValueIndex`. Compare with the non-sorted path which correctly uses `firstValueIndex + i`:
```java
// processDoubles - sorted path (BUGGY):
builder.appendDouble(valuesBlock.getDouble(0));                          // should be getDouble(firstValueIndex)
builder.appendDouble(valuesBlock.getDouble(valueCount - 1));            // should be getDouble(firstValueIndex + valueCount - 1)
valuesBlock.getDouble(lowerIndex)                                        // should be getDouble(firstValueIndex + lowerIndex)
valuesBlock.getDouble(upperIndex)                                        // should be getDouble(firstValueIndex + upperIndex)
// processDoubles - non-sorted path (CORRECT):
values[i] = valuesBlock.getDouble(firstValueIndex + i);
```
The same pattern of missing `firstValueIndex` offset exists in `processInts` and `processLongs` sorted paths. This will produce incorrect results for any row position > 0 in a page when the multivalue block is sorted ascending, because it will read values belonging to a different row.
