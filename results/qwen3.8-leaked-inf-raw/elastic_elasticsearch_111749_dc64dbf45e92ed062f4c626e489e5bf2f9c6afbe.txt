#6C0AH: **Critical: Missing `return` (or `else`) after the `mvSortedAscending()` branch causes double-append to the builder.**
In `processDoubles`, `processInts`, and `processLongs`, when `valuesBlock.mvSortedAscending()` is `true`, the code appends a result inside the `if` block but then **falls through** to the code below (copy → sort → append again). This means two values are appended for the same position, corrupting the output block.
For example in `processDoubles`:
```java
if (valuesBlock.mvSortedAscending()) {
    // ... appends a value ...
}
// No return / else — execution continues here:
var values = new double[valueCount];
// ... copies, sorts, and appends ANOTHER value ...
```
The fix is to either add a `return;` at the end of the `if (valuesBlock.mvSortedAscending())` block, or wrap the second section in an `else` clause. This affects all three methods (`processDoubles`, `processInts`, `processLongs`).

#6C0AH: **Critical: Wrong absolute indices used in the sorted-ascending fast path.**
Inside the `if (valuesBlock.mvSortedAscending())` branch, the code uses bare indices (`0`, `valueCount - 1`, `lowerIndex`, `upperIndex`) instead of offsetting by `firstValueIndex`. For any position other than the first in the block, this reads from the wrong location.
For example in `processDoubles`:
```java
if (percentile == 0) {
    builder.appendDouble(valuesBlock.getDouble(0));  // should be firstValueIndex
} else if (percentile == 100) {
    builder.appendDouble(valuesBlock.getDouble(valueCount - 1));  // should be firstValueIndex + valueCount - 1
} else {
    var result = calculateDoublePercentile(fraction,
        valuesBlock.getDouble(lowerIndex),   // should be firstValueIndex + lowerIndex
        valuesBlock.getDouble(upperIndex));  // should be firstValueIndex + upperIndex
}
```
The same issue exists in `processInts` and `processLongs`. The non-sorted path correctly uses `firstValueIndex + i`, confirming the intent.

#6C0AH: **Minor: `foldable()` only checks the `field` argument.**
```java
@Override
public boolean foldable() {
    return field.foldable();
}
```
If the `percentile` argument is a non-foldable expression (e.g., a column reference), this would incorrectly report the whole expression as foldable. Consider `return field.foldable() && percentile.foldable();` for correctness, or add a comment explaining why only `field` is checked (e.g., percentile is expected to always be a literal).
