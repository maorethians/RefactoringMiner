#KGFVX: The alias/pattern security check is placed **outside** the `if (esr.indexMode().equals(IndexMode.LOOKUP))` block, so it fires for every `EsRelation` on the right side regardless of index mode. This is a reasonable defense-in-depth choice (the security check should not depend on the mode check passing), but it means that if an index is both in the wrong mode *and* is an alias, the user receives two separate failure entries for the same root cause. Consider whether the alias check should be nested inside the `if` block (since a non-LOOKUP-mode index on the right of a LOOKUP JOIN is already an error), or add a brief comment explaining the intentional separation.

#KGFVX: The first error message reads:
```
"invalid [{}] resolution in lookup mode to an index in [{}] indices"
```
When `indexNameWithModes.size()` is, say, 3, this produces *"…to an index in 3 indices"*, which is grammatically confusing. The original message in `Analyzer` (now removed in #BHM43) was *"…to [3] indices"*, which reads more naturally. Consider adjusting the wording, e.g. *"invalid [{}] resolution in lookup mode: resolved to [{}] indices, expected exactly 1"*.

#0P23E: In `testLookupJoinDocLevelSecurity`, the first assertion expects `org` to be `null` when the DLS filter excludes the matching document:
```java
assertThat(respMap.get("values"), equalTo(List.of(Arrays.asList(40.0, null))));
```
This is correct for a LEFT JOIN with no match. However, the test does not verify the **column type** of `org` in this null case (it does check the schema, which is good). One edge case worth considering: if the DLS filter excludes *all* documents in the lookup index, the join still returns a row with `null`—this is implicitly covered by the first assertion, but a dedicated test case (or at least a comment) making that expectation explicit would improve clarity for future maintainers.
