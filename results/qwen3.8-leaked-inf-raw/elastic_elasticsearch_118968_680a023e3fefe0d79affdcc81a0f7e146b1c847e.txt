#AR9AB: In `IndexSortConfig.java`, the new validation in the LOGSDB default branch uses `"index.sort.fields:"` (plural) in error messages, while the existing validation code just below (unchanged) uses `"index.sort.field:"` (singular). For example:
- New: `"index.sort.fields:" + fields + " index.sort.order:" + order + ", size mismatch"`
- Existing: `"index.sort.field:" + fields + " index.sort.order:" + orders + ", size mismatch"`
This inconsistency in the setting name within error messages could confuse users when debugging.

#C1GB9: The `timeStampSpec` object is shared across three static arrays (`TIME_SERIES_SORT`, `TIMESTAMP_SORT`, `HOSTNAME_TIMESTAMP_SORT`). While currently safe because all code paths that reference these arrays `return` immediately without mutating the specs, this is a latent maintenance hazard. If any future code path modifies `sortSpecs[i].order` (as the existing code does for user-specified sort fields), it would silently corrupt the shared static objects. A defensive copy or a comment noting the immutability contract would be safer.

#N5VAA, #E1MC5: `getMappingData` is now called unconditionally (previously `newIndexHasSyntheticSourceUsage` was only called inside `if (supportFallbackToStoredSource())`). In stateless deployments where `supportFallbackToStoredSource` is `false`, this means a `MapperService` is now created on every index creation just to check whether `host.name` is a `FieldMapper`. The test counter changes (e.g., #4THB6: `equalTo(0)` → `equalTo(1)`) confirm this. While functionally necessary for the host.name type check, this is a measurable performance regression for stateless clusters where the synthetic-source fallback path is never taken. Consider whether the host.name field type check could be done via a lighter-weight mapping inspection (e.g., parsing the mapping JSON directly) to avoid full `MapperService` construction in the common stateless case.

#QC337: The condition `IndexSortConfig.INDEX_SORT_FIELD_SETTING.get(indexTemplateAndCreateRequestSettings).isEmpty() == false` is a double negation. The idiomatic form would be `!IndexSortConfig.INDEX_SORT_FIELD_SETTING.get(indexTemplateAndCreateRequestSettings).isEmpty()` or simply checking `.size() > 0`. Minor readability nit.

#E1MC5: The `sortOnHostName` expression:
```java
IndexSettings.LOGSDB_SORT_ON_HOST_NAME.get(indexTemplateAndCreateRequestSettings)
    || mapperService.mappingLookup().getMapper("host.name") instanceof FieldMapper
```
The first disjunct (`LOGSDB_SORT_ON_HOST_NAME.get(...)`) is always `false` at this point in the code, because the earlier branch in #QC337 already returns early when it is `true`. This makes the first operand dead code and may mislead readers into thinking there's a case where it could be `true` here.
