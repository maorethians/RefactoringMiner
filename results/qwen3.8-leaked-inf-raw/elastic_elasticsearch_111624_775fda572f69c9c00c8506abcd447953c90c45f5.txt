#STVWK, #HWSM3, #Z6RG9: **Potential test failure due to off-by-one in count comparison:**
In `testDropWarningsExceedingMaxSettings`, the test sets `maxWarningHeaderCount` to `1` and expects the second `addResponseHeader("Warning", "dropped, too many")` call to be dropped by the count check. However, the code in `putResponse` uses:
```java
if (warningHeaderCount > maxWarningHeaderCount) {
```
After the first warning is added, `warningHeaderCount` is `1`. The check `1 > 1` evaluates to `false`, so the second header is **not** dropped. The test assertion `assertThat(warnings, contains("warning"))` will fail because the list will contain both `"warning"` and `"dropped, too many"`.
To make the test pass with the current code, either:
- Set `maxWarningHeaderCount` to `0` (so that `1 > 0` triggers the drop), or
- Change the comparison in the production code to `>=` if the intended semantics is "at most N warning headers."
This is a pre-existing off-by-one in the production code, but since the test is new in this PR, it will fail on merge.

#VM664: **Minor inefficiency in header filtering:**
```java
Map<String, String> selectedHeaders = new HashMap<>(requestHeaders);
selectedHeaders.keySet().retainAll(List.of(Task.X_OPAQUE_ID_HTTP_HEADER, Task.X_ELASTIC_PRODUCT_ORIGIN_HTTP_HEADER));
```
This copies the entire `requestHeaders` map (which could be large) only to retain two keys. A more targeted approach avoids the full copy:
```java
Map<String, String> selectedHeaders = new HashMap<>(2);
for (String key : List.of(Task.X_OPAQUE_ID_HTTP_HEADER, Task.X_ELASTIC_PRODUCT_ORIGIN_HTTP_HEADER)) {
    String value = requestHeaders.get(key);
    if (value != null) {
        selectedHeaders.put(key, value);
    }
}
```
This is a low-priority concern since it only executes on the error path, but it avoids allocating a map proportional to the number of request headers.

#KMVMA: **Potential test flakiness from HashMap iteration order:**
The expected log message hard-codes the order of entries in the `selectedHeaders` map:
```
"Dropping a warning header for request [{X-Opaque-Id=abc, X-elastic-product-origin=product}], ..."
```
`HashMap.toString()` does not guarantee iteration order. While with two entries the order is deterministic for a given JVM, it is not contractually stable across JDK versions or hash-seed changes. Consider either:
- Using a `LinkedHashMap` (or `Map.of` with a fixed insertion order) in the production code, or
- Matching the log message with a regex / `containsString` that is order-insensitive in the test.
