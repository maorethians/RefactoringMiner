#M0YGS, #VPMEC, #66E9Z: The documentation still references the setting as `enrich.cache_size`, but the code defines it as `enrich.cache.size` (see `CACHE_SIZE_SETTING_NAME`). This is a documentation/code mismatch that will confuse users. The docs should be updated to `enrich.cache.size` to match the actual setting name.

#0T2QP: Two issues in `FlatNumberOrByteSizeValue`:
1. **Bitwise OR instead of logical OR**: `value.endsWith("b") | value.endsWith("B")` uses `|` (bitwise OR) instead of `||` (short-circuit logical OR). While functionally equivalent for booleans, it always evaluates both sides and is non-idiomatic. Should be `value.endsWith("b") || value.endsWith("B")`.
2. **Missing `equals()`/`hashCode()`**: The class does not implement `equals()` or `hashCode()`. This forces the test (`#A61RR`) to define a custom `assertEquals` helper and makes the class unusable in collections or with standard assertion utilities. Implementing `equals`/`hashCode` based on the two fields would be more maintainable.

#66E9Z, #0T2QP: The old setting enforced a minimum value of `0` (`Setting.longSetting("enrich.cache_size", 1000, 0, ...)`). The new `FlatNumberOrByteSizeValue.parse` does not validate that the parsed flat number is non-negative. A user could set `enrich.cache.size` to `-1`, which would be passed to `CacheBuilder.setMaximumWeight(-1)`, leading to undefined or erroneous cache behavior. Consider adding a check that rejects negative values (and possibly zero) with a clear error message.

#66E9Z: The setting name changed from `enrich.cache_size` to `enrich.cache.size`. This is a breaking change for any existing deployment that has the old name in its `elasticsearch.yml`. If backward compatibility is a concern, consider either keeping the old name or registering the old name as a deprecated alias that maps to the new one.
