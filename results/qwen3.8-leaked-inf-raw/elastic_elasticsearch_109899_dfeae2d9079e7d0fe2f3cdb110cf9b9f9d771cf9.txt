#A4ZQN: Thread safety of shared state: `inFlyRequests` and `isClosing` are plain fields accessed from the `sslCloseFuture` listener and from `channelRead`/`write`/`flush`. While in practice Netty's `SslHandler` completes the close future on the event-loop thread (making these operations serialized), the code does not enforce or document this assumption. If the listener were ever invoked off the event loop (e.g., in a test harness or a future Netty change), there is a race: the listener reads `inFlyRequests == 1`, the event loop decrements it to 0 and flushes (sees `isClosing == false`), then the listener sets `isClosing = true` — and no further flush ever triggers the close. Using `volatile` on both fields (or an `AtomicInteger` for the counter) would make the intent explicit and guard against this.

#A4ZQN: No timeout / stuck-request guard: If a request is dispatched but the handler never writes a `LastHttpContent` (e.g., the REST handler hangs or throws without writing a response), `inFlyRequests` never reaches 0 and the channel is never closed after close_notify. A timeout or a `channelInactive`/`exceptionCaught` fallback that forces the close would make the handler more robust. An `exceptionCaught` override that resets the counter (or at least logs) would also help with diagnosability.

#HCP90: The handler is added without a name:
```java
ch.pipeline().addLast(new Netty4CloseNotifyHandler(ch, sslHandler));
```
Every other handler in this pipeline is registered with a string name (`"chunked_writer"`, `"encoder_compress"`, `"pipelining"`, etc.). An unnamed handler is harder to identify in pipeline dumps, logs, and debugging. I'd recommend adding a name, e.g. `"close_notify"`.

#R7DGE: In `testSendCloseNotifyBeforeHttpResponse`, the test relies on `safePoll(server.dispatcher.reqQueue)` to retrieve each request in order. If the server-side pipeline reorders or drops a request (e.g., due to the close_notify already being processed), the test would time out with a generic "queue is empty" assertion. Adding a brief diagnostic (e.g., logging `inFlyRequests` or the channel state on timeout) would make failures easier to diagnose.

This is presumably because `TLSConfig` and `SSLService` live in the security plugin, but it's worth confirming the test will be picked up by the module's test task and not only by the x-pack build.
