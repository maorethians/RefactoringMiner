#SVF5C, #ANHXV: The error message in `expectValueToken` reads `"Failed to parse object: expecting value token but found [%s]"`, but this method is called from `extractArray` when parsing array elements (e.g., rejecting a nested object inside an array). The word "object" in the message is misleading in that context — a user debugging a multi-value dimension with a nested object would see "Failed to parse object" and might be confused about whether the issue is with the outer object or the array element. Consider a more neutral message like `"Expecting a value token but found [%s]"` (and update the corresponding assertion in `testRoutingPathObjectArraysInSource`).

#BZBVP: In `buildTsidHash`, the "concatenate all dimension value hashes" section only reads `values.get(0)`. This means two documents that differ only in the second (or later) value of a multi-value dimension will share the same limited-hash prefix and rely entirely on the full hash (computed later in `#Q9VY9`) for distinction. This is presumably intentional (the limited section is a bounded-size quick check), but it's worth a brief code comment noting that only the first value is used here by design, to prevent a future reader from "fixing" it to iterate all values and inadvertently changing the TSID format.
