#Y0NP3, #KY4A8: The `continueReading` change short-circuits to `true` when `isReceivedRdHup()` is set, bypassing the delegate's allocator-based limit check entirely. While this is intentional to drain remaining data on peer close, it means the read loop will ignore `maxBytesPerRead` / allocator constraints once RDHUP is observed. In practice this is safe (the loop terminates when `read()` returns 0), but it's worth confirming that no downstream handler relies on the allocator's byte-count ceiling being respected during the RDHUP drain. A brief inline comment explaining the intent (drain-on-close) would help future readers understand why the short-circuit exists.

#55RKG: `setEpollMode` previously called `ObjectUtil.checkNotNull(mode, "mode")` and `checkChannelNotRegistered()`. Both guards are now removed, so passing `null` or calling after registration silently succeeds instead of throwing. Since the method is a deprecated no-op this is an acceptable trade-off for backward compatibility, but it does mean any existing test or integration code that relied on the `IllegalStateException` from `checkChannelNotRegistered()` to detect a misconfiguration will now pass silently. Consider whether a `LOGGER.warn` (rather than `debug`) would be more appropriate to surface the no-op to operators who are still configuring ET mode.

#FAGS5: The simplified `maybeMoreDataToRead()` now unconditionally returns `lastBytesRead() == attemptedBytesRead()`. This is correct for level-triggered mode, but note that the Javadoc on the method (which was removed) previously documented the ET contract. If any external code or subclass still references the old two-branch semantics in its own logic, the behavioral contract has silently changed. The method is package-private so the blast radius is limited, but it's worth a release-note mention.
