#59RAM, #K541H: The TODO "Shouldn't we perform widening of small numerical types here?" appears in both `TypeResolutions.isType` and `Analyzer.resolveConvertFunction`. This is a real correctness gap: if a union field is mapped as `integer` in one index and `long` in another, and the predicate only accepts `long`, the `allMatch` check will fail even though `integer` is a valid widening source. Consider either implementing the widening check now or filing a follow-up issue so this isn't lost.

#ASZ5C: The `types()` method allocates a new `Set<DataType>` on every invocation via `stream().map(...).collect(...)`. Since this is called from `TypeResolutions.isType` (which runs during type resolution for every expression) and from `resolveConvertFunction`, it could be called repeatedly for the same field. Consider caching the result in a field (computed once in the constructor or lazily) to avoid repeated allocation, especially if `typesToIndices` is large.

#1DERJ: The guard condition changed from `p.resolved() || p.childrenResolved() == false` to just `p.childrenResolved() == false`. This means `doRule` will now also be applied to plans that are already marked as resolved. While this is likely intentional (to allow `InvalidMappedField` to pass through in already-resolved sub-plans), it's worth confirming that `doRule` is idempotent — i.e., running it a second time on a plan where `InvalidMappedField` has already been converted to `MultiTypeEsField` or `UnsupportedAttribute` won't cause a double-conversion or state corruption.

#TT4TC: In `checkUnresolved`, the types are joined into a comma-separated string (`"keyword,long"`) and passed to `UnsupportedEsField`. This string is used in user-facing error messages. If the set of types is large (e.g., a field mapped to 5+ different types across many indices), the message could become unwieldy. Consider whether a cap or a more structured representation would be more readable. Additionally, the order of types in the message depends on the iteration order of `getTypesToIndices().keySet()` — if this is a `TreeMap` (as suggested by the import in `InvalidMappedField`), the order is deterministic (alphabetical), which is fine, but worth noting for consistency with other error messages in the codebase.
