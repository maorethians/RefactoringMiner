#ZNRQT: The core logic change. I traced through the merge algorithm with the new sort step:
- The `IndexInfo` record's `compareTo` correctly orders by `timeSeriesStart` then `timeSeriesEnd`, giving a deterministic total order.
- The merge logic (adjacent → extend, gap → finalize + start new, overlap → warn) is unchanged from the old code, just operating on the sorted list.
- The `previous` variable is only dereferenced in the collision branch, which is unreachable on the first iteration (since `currentMergedRange == null` takes the first branch), so no NPE risk.
- The `IndexInfo` record is scoped locally, which is appropriate since it's a single-use helper.
One minor observation: the collision branch (the `else` at the end of the `if/else if` chain) logs a warning but neither adds the current range to `mergedRanges` nor updates `currentMergedRange`. This means a colliding index's range is silently dropped from the response. This behavior is inherited from the old code, so it's not a regression, but it's worth being aware of for future maintainers.

#Y0K3K: The new test provides indices in the order (middle, first, last) chronologically and asserts they merge into a single contiguous range. This directly validates the sort fix. Good coverage of the primary bug scenario.
