#PT136, #PX7S2, #KP7FB, #E6KYY, #DP1YP, #CWG2T, #M61PT, #T2NCX, #KGFVN, #NS1ZA, #YNPVA: These are straightforward changes (formatting, imports, option plumbing, Javadoc updates) and look correct. No issues identified.

#61SQM: In the `SHUTDOWN_COMPILATION` branch, `shutdownAndAwaitTermination(100)` is called unconditionally on every invocation of `isCompilationStopped()`. Since this method is called on every compilation attempt while the host is in SHUTDOWN mode, the queue shutdown (with its 100 ms `awaitTermination`) will be repeated indefinitely. After the first call the executor is already terminated, so subsequent calls are wasted work and add up to 100 ms of latency per compilation attempt. Consider guarding this with a one-time flag (similar to `logShutdownCompilations`) or moving it inside the `compareAndExchange` guard so it only executes once.
Additionally, in the `STOP_COMPILATION` branch the comment says *"the one we've just added after the StoppedCompilationRetryDelay ran out"*, but at this point the current target has **not** yet been submitted to the queue (the caller in `compile()` invokes `isCompilationStopped()` before any submission). The comment is misleading; the single target in the queue is from a *previous* attempt, not the current one.

#B5EFC: If `getCompilationActivityMode.invokeExact(...)` throws (e.g., the underlying native method fails, or the JVMCI runtime is in an unexpected state), the code wraps it in a `RuntimeException` that propagates up through `isCompilationStopped()` → `compile()` and will likely kill the compilation worker thread. Given that this is a best-effort query about host state, consider catching the `Throwable`, logging a warning, and defaulting to `RUN_COMPILATION` so that a transient failure in the introspection path doesn't permanently break compilation for the engine.

#VHAJ9: `CompilationActivityMode.fromInteger` throws a generic `RuntimeException` for an unknown value. An `IllegalArgumentException` (or `IllegalStateException`) would be more precise and easier to diagnose in stack traces. This is a minor point, but it aligns better with standard Java conventions for invalid-argument conditions.
