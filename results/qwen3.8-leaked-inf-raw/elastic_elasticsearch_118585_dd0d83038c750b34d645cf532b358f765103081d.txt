#SBSRP: `validateSortFields` does not guard against sort arrays longer than 2 fields. When `fields.length > 2`, the method validates only `fields[0]` and `fields[1]` and then returns `true` without inspecting the remaining fields. A sort like `[score, _shard_doc, other_field]` would pass validation, but the rescore reconstruction logic only updates `fields[0]`, potentially leaving the result incorrectly ordered for the third field. Consider adding an explicit `fields.length > 2 → return false` check (or asserting `fields.length <= 2`).
Additionally, in `rewriteFieldDocs`, the `Maps.newMapWithExpectedSize(rescoredTopDocs.length)` hint should be `originalTopDocs.length` since that is the number of entries actually inserted into the map.

#2NQBA: The constructor calls `extractMinWindowSize(rescorers)` (which returns `Integer.MAX_VALUE` for an empty list) before checking `rescorers.isEmpty()`. While functionally harmless since the exception is thrown immediately after, it's slightly misleading to compute a value that will be discarded.

#GQ97T: Removing the `_shard_doc`-requires-PIT validation from `SearchSourceBuilder.validate()` eliminates a user-facing guard for *all* search requests, not just those using the rescorer retriever. Previously, a user specifying `_shard_doc` sort without a PIT received a clear error; now the request is silently accepted, which can lead to inconsistent results in scroll or `search_after` contexts. If the goal is to permit `_shard_doc` as a tiebreaker only in the rescorer path, consider scoping the removal (e.g., skip the check only when a rescorer retriever is present) rather than deleting it unconditionally.
