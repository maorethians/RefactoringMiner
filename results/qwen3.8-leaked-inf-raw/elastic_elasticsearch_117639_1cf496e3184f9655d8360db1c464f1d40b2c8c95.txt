#GMBH8: The `computeOutput` method lives on the base `Join` class and is therefore shared by all join types, not just `LookupJoin`. The new logic filters the "other" side's output by `config.matchFields()` names:
```java
Set<String> matchFieldNames = config.matchFields().stream().map(NamedExpression::name).collect(Collectors.toSet());
```
For a **USING** join (which is what `LookupJoin` uses), both sides carry the same column names, so filtering `rightOutput` by the left-side match-field names correctly removes the duplicate. However, for a hypothetical **ON** join where the left and right match columns have *different* names (e.g., `left.id = right.emp_id`), `matchFieldNames` would contain `"id"` but the right-side attribute is named `"emp_id"`, so the filter would **not** remove it, potentially producing a duplicate column in the output.
If `Join` is only ever instantiated with USING-style configs in this codebase, this is safe. But because the method is on the shared base class, a future ON-clause join could silently hit this edge case. Consider either:
- Adding a brief comment noting the assumption that match-field names are identical on both sides, or
- Filtering by both `matchFields` and `rightFields` names to be robust for both USING and ON semantics.
