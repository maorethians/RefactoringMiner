#6SCCQ: The new early-exit block in `tumbleWindow` calls `doPayload(listener)` but is missing a `return` statement. After the listener is invoked, execution falls through to the subsequent `if (currentStage > matcher.firstPositiveStage && ...)` block and the rest of the method body. This can cause the listener to be invoked a second time (e.g., if `restartWindowFromTailQuery` is false, `doPayload` is called again; or the method continues to its normal completion path which also calls `doPayload`). A double-invocation of an `ActionListener` is undefined behavior and will likely cause a `RuntimeException` or silent data corruption.
Fix:
```java
if (allowPartialSequenceResults == false && shardFailures.isEmpty() == false) {
    doPayload(listener);
    return;
}
```

#KD3JJ: There is a stray no-op statement in `Results.fromPayload`:
```java
payload.shardFailures();
```
This line calls the method but discards the result. It appears to be a leftover from refactoring (the value is correctly passed to the constructor on the next line). It should be removed to avoid confusion.

#3FP2Y: The XContent parser for `shard_failures` is a stub that always returns `ShardSearchFailure.EMPTY_ARRAY`:
```java
parser.declareObjectArray(optionalConstructorArg(), (p, c) -> ShardSearchFailure.EMPTY_ARRAY, SHARD_FAILURES); // TODO fix this
```
This means any `EqlSearchResponse` deserialized from XContent (e.g., via `fromXContent`) will silently lose all shard failure information. If this path is exercised in production (e.g., REST-level deserialization, cross-version compatibility, or test assertions that round-trip through JSON), shard failures will be missing. The TODO should be tracked and resolved before this is considered complete, or at minimum the limitation should be documented.

#0N3S5, #QGJJJ: Both `SampleIterator.addShardFailures` and `TumblingWindow.addShardFailures` use `shardFailure.toString()` as the deduplication key in a `HashMap`. This is fragile: `toString()` output is not a stable contract, two logically distinct failures could collide, and the same logical failure reported with slightly different formatting would not be deduplicated. The TODO acknowledges this, but since the method is duplicated verbatim in two classes, consider extracting it into a shared utility (e.g., in `RuntimeUtils`) and using a more robust key such as `(shardFailure.index(), shardFailure.shardId(), shardFailure.reason())`.

#CVR0A, #KD3JJ: The new `shardFailures` field is declared without `final` in both `AbstractPayload` and `Results`, while all other fields in those classes are `final`. Since the value is set only in the constructor and never reassigned, declaring it `final` would be more consistent and would allow the compiler to verify immutability.
