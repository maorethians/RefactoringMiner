#VRVZ1: In the `BitDotProduct` constructor accepting `List<Number>`, the `isFloat` detection logic is:
```java
if (floatQueryVector[i] % 1.0f != 0.0f || floatQueryVector[i] < Byte.MIN_VALUE || floatQueryVector[i] > Byte.MAX_VALUE) {
    isFloat = true;
}
```
This works correctly for the intended cases, but there's a subtle edge: if a caller passes a `Double` value like `127.0000001`, `number.floatValue()` rounds to `127.0f`, the modulo check passes, and the value is treated as a byte. The original double precision is lost. This is acceptable given the API contract (the vector is either byte or float), but it means the boundary between "byte" and "float" interpretation depends on float precision rather than the original number's type. A stricter alternative would be to check `number instanceof Integer || number instanceof Short || number instanceof Byte` to decide the type, but the current approach is pragmatic and consistent with how other vector functions handle this.

#VP1N8, #EVM7B: The dispatch logic in `dotProduct(byte[])`:
```java
if (queryVector.length == vectorValue.length) {
    return andBitCount(vectorValue, queryVector);
}
return ipByteBit(queryVector, vectorValue);
```
This relies on the length comparison to distinguish bit-bit from byte-bit. The dimension validation in the `BitDotProduct` constructor ensures that a byte vector (8× longer) and a bit vector (same length) are both accepted, and the runtime check correctly disambiguates. This is sound, but the implicit contract (same length → bit vector, 8× length → byte vector) is only documented in the comment. If a future code path calls `dotProduct(byte[])` without going through `BitDotProduct`'s validation, a mismatched-length byte vector would silently fall into `ipByteBit` and throw there. Consider adding a brief Javadoc note on the `dotProduct(byte[])` override stating the expected length relationship.
