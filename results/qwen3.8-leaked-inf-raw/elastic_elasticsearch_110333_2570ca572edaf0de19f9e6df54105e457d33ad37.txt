#EPW1Q, #HGMZ0: Making `fold()` abstract in `UnaryScalarFunction` is a significant API change. All concrete subclasses (beyond those shown in this chapter) must now provide their own `fold()` implementation. If any subclass in other modules (e.g., `x-pack/plugin/esql`) previously relied on the default `fold()` → `makeProcessor().process(...)` path and hasn't been updated in this PR, it will fail to compile. Please confirm all subclasses across the codebase have been updated.

#6FXKX: The `doApply` method is `final` and unconditionally returns `null`. This is a footgun: if any code path (e.g., a default implementation in `PredicateBiFunction`, a reflection-based caller, or a future refactor) invokes `doApply` instead of `apply`, it will silently receive `null`, which in SQL three-valued logic means "unknown" rather than an error. Compare with `BinaryComparisonOperation` (diff #0BB68) where `doApply` is the actual computation hook and `apply` delegates to it. The two enums implement the same interface with opposite delegation patterns, which is confusing. Consider either:
- Making `BinaryLogicOperation` follow the same pattern as `BinaryComparisonOperation` (null-check in `apply`, real work in `doApply`), or
- Adding a clear `@Override` comment / `UnsupportedOperationException` in `doApply` to signal it should never be called.

#3N7HA: `RegexOperation` is a pure utility class (all static methods) but lacks a private constructor to prevent instantiation. Add `private RegexOperation() {}` to enforce its intended usage.
