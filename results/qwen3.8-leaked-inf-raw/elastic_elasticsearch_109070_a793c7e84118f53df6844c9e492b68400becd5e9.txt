#S3NG2, #ENNNP, #98G3R, #ZX7M3, #32BJ2: The `prefixLength` parameter description uses open-interval notation: "If in the range (0, 32), the IP is treated as an IPv4 address. If in the range (32, 128), the IP is treated as an IPv6 address." However, the implementation accepts 0, 32, and 128 as valid values (verified by the test cases `ip_prefix(ip4, 0)` → `0.0.0.0`, `ip_prefix(ip4, 32)` → full IP, `ip_prefix(ip6, 128)` → full IP). The open-interval notation technically excludes these boundary values, which is misleading to users. Consider using closed-interval notation like "[0, 32]" and "(32, 128]" or simply stating the valid range as "0 to 128 inclusive."

#5FDW0: The `ipPrefixWithWrongArguments` test case is skipped with the reason "null returns not supported yet in evaluators." This means the out-of-range prefix length cases (`ip_prefix(ip4, 129)` and `ip_prefix(ip4, -1)`) are not exercised in the CSV integration tests. While the unit test in `IpPrefixTests.java` covers null inputs via `anyNullIsNull(true, ...)`, the out-of-range integer cases (129, -1) are only covered in this skipped test. Consider adding these as explicit test cases in `IpPrefixTests.java` (e.g., a `TestCaseSupplier` with prefixLength=129 expecting null) so the boundary validation is covered even if the CSV test remains skipped.
