#2JCTF: The comment block states:
> If 'store' parameter was explicitly provided we'll reject the request.
However, no rejection logic exists in this diff or in the `Parameter` framework path shown. The `Supplier<Boolean>` default simply provides a fallback when the user omits `store`; an explicit `store: false` will silently override it. In a TSDB index without a compatible keyword sub-field, this would produce a mapping where the text field is neither stored nor backed by a usable keyword delegate, making synthetic `_source` reconstruction impossible at query time. Either the rejection should be implemented (e.g., a validation step that throws when `store` is explicitly set to `false` under these conditions), or the comment should be corrected to reflect the actual "explicit value wins" behavior.

#57NRX: The new `testStoreParameterDefaults` covers the default-resolution matrix well, but it never exercises the case where the user **explicitly** sets `store: false` on a TSDB index that has no compatible keyword sub-field. Given the comment in the builder (see above) and the fact that this is the one combination that produces an unusable synthetic-source mapping, a dedicated test asserting the expected outcome (rejection, or at minimum documenting the current "silently accepted" behavior) would close the gap.
