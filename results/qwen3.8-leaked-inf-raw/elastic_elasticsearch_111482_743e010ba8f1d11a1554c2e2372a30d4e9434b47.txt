#REPWB: The `allValuesNull` check uses `anyMatch(Block::areAllValuesNull)`, which will be `true` if *any* block in the input page has all-null values. If the input page ever contains more than one block (e.g., a multi-column aggregation input), this would zero out `seenGroupIds` even when only one of several blocks is entirely null. If the intent is "the entire input is null," `allMatch` would be the safer choice. If the method is only ever called with single-block pages, this is fine, but a brief comment clarifying the assumption would help future readers.

#Z8CDE: In `anyNullIsNull`, the "null in position" suppliers are registered with `original.types()` as their type list, while the "firstTimeSeenSignature" suppliers use `typesWithNull` (with `DataType.NULL` substituted). This means the two sets of generated cases carry different type metadata for the same logical scenario. Downstream, `errorsForCasesWithoutExamples` builds its `valid` set from `TestCaseSupplier::types`, so the `typesWithNull` variants (e.g. `[NULL, INTEGER]`) are treated as *valid* signatures and will not themselves generate error cases. This is likely intentional, but it means the `validPerPosition` sets will include `DataType.NULL` as an acceptable type at certain positions, which could suppress error-case generation for genuinely invalid `NULL`-typed arguments at those positions. Worth a quick sanity check that no test class inadvertently relies on `NULL` being rejected at a position where it was only "valid" because of this side-effect.
