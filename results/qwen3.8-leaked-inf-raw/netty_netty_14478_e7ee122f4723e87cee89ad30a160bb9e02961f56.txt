#ZT8RS: The modulo constant is off by one. TCP sequence numbers are 32-bit unsigned integers with a valid range of `[0, 2^32 - 1]`, meaning they wrap at `2^32`. The correct modulo should be `0x100000000L` (i.e., `2^32`), not `0xFFFFFFFFL` (i.e., `2^32 - 1`).
With the current code, consider `sequenceNumber = 0xFFFFFFFE` and `value = 2`:
- Expected: `(0xFFFFFFFE + 2) % 0x100000000 = 0`
- Actual: `(0xFFFFFFFE + 2) % 0xFFFFFFFF = 1`
This produces an incorrect sequence number at the wrap boundary.

#YYZNY: Copy-paste bug: the second line assigns to `sendSegmentNumber` instead of `receiveSegmentNumber`:
```java
sendSegmentNumber = incrementUintSegmentNumber(sendSegmentNumber, 1);
sendSegmentNumber = incrementUintSegmentNumber(receiveSegmentNumber, 1); // should be receiveSegmentNumber = ...
```
This overwrites `sendSegmentNumber` with a value derived from `receiveSegmentNumber`, and `receiveSegmentNumber` is never incremented. The subsequent `writePacket` call will use the wrong values for both fields.

#HCNCS: The test reuses the same `ByteBuf` instance across all loop iterations:
```java
final ByteBuf payload = Unpooled.wrappedBuffer(payloadString.getBytes());
for (int i = 0; i < ((fourGB / chunkSize) + 2); i++) {
    embeddedChannel.writeInbound(payload);
}
```
Once `PcapWriteHandler` reads from the `ByteBuf` during the first `writeInbound` call, its reader index advances to the end. All subsequent iterations will see `readableBytes() == 0`, so the test does not actually exercise the >4 GB sequence-number wrap path. A fresh `ByteBuf` should be created (or the existing one duplicated) on each iteration, e.g.:
```java
for (int i = 0; i < ((fourGB / chunkSize) + 2); i++) {
    embeddedChannel.writeInbound(payload.copy());
}
```
The same issue applies to the `writeOutbound` loop.
