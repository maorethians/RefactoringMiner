#3A1FE: In `parseDocForMissingValues`, after a leaf field is found and `encodeToken(parser)` is called, the code falls through to `currentToken = parser.nextToken()` at the bottom of the outer while loop. If the encoded value was a container (START_OBJECT/START_ARRAY), `encodeToken` consumes through the END token, so `parser.nextToken()` correctly advances past it. However, if the encoded value was a scalar, the parser is still at the scalar token, and `parser.nextToken()` advances to the next sibling. Both cases work, but this correctness depends entirely on `encodeToken` leaving the parser at the last token of the value (END_OBJECT/END_ARRAY for containers, the scalar itself for primitives). There's no assertion or comment documenting this contract. A brief comment at the `encodeToken` call site noting the expected post-condition would help future maintainers.

#8QPH9: The `canAddIgnoredField()` method previously included `indexSettings().getSkipIgnoredSourceWrite() == false` as a guard. This check is now removed. Similarly, `markFieldAsCopyTo` in #MYQGZ drops the same check. If `skipIgnoredSourceWrite` was a user-facing setting that suppressed writing the `_ignored` field for performance, removing the guard means synthetic source values will now always be recorded regardless of that setting. Please confirm this is intentional and that the setting is either deprecated or its semantics have been subsumed by the new two-pass approach.

#F9YWY, #8QPH9: `context.addIgnoredFieldMissingValue(null)` is used to signal "store the enclosing array." The method signature accepts `IgnoredSourceFieldMapper.NameValue`, and the null case is disambiguated internally by checking `arrayFieldMissingValue != null`. This works, but passing `null` as a meaningful sentinel is fragile — a future caller could accidentally pass null when they meant to pass a real NameValue, and the assert in the else-branch would only catch it in test/development builds. Consider a dedicated no-arg overload (e.g., `markArrayForSourceRecording()`) to make the intent explicit and eliminate the null-sentinel pattern.

#3A1FE: In `parseDocForMissingValues`, the `fields` map is keyed by `field.name()` (the full dotted path). If two distinct `NameValue` entries happen to share the same `name()` (e.g., the same logical field recorded from two different code paths), the second `put` silently overwrites the first. Given that `addIgnoredFieldMissingValue` can be called from multiple sites (#RS15A, #8EES4, #5K6K0, #F9YWY), a defensive check or at least a comment noting the assumption of unique names would be prudent.

#RT420: The added `match: { errors: false }` assertion appears after the bulk index call. This is a good addition to catch unexpected indexing errors that were previously silently ignored, and it aligns with the bug fix (the test was likely failing because of the very issue being resolved). No concern here.

#PXC7H, #A0YDX, #T79M7: The test expectation changes confirm the behavioral fix: arrays that contain stored-source elements now preserve their array structure in the synthetic source rather than being flattened into a single object. The new `testObjectArrayAndValue` test covers the mixed case (array element vs. object element within the same array), which is a good boundary condition.
