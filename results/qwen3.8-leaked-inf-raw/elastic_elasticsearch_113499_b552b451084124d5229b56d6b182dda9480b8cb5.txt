#NE7CX: In `addField()`, the `ignoreAbove` check now happens after `createKeyedValue(key, value)` and `new BytesRef(keyedValue)` are computed. When the value exceeds `ignoreAbove` and the source is *not* synthetic, the keyed value and `BytesRef` are allocated for nothing. While this is a minor allocation cost on a path that was previously a fast-return, it's worth noting that the old code returned before any allocation. If this is a hot path with many over-length values in non-synthetic-source indices, consider moving the `ignoreAbove` check before the `createKeyedValue` call and only computing the keyed value when it's actually needed (i.e., when it will be indexed or stored).

#PFA43: In `DocValuesSortedKeyedValues.next()`, `docValues.getValues()` is called on every invocation:
```java
var sortedSetDocValues = docValues.getValues();
return sortedSetDocValues.lookupOrd(sortedSetDocValues.nextOrd());
```
Since `getValues()` returns a stable reference (either the stored `dv` field or `null`), this could be resolved once in the constructor to avoid the repeated virtual/interface call in a tight loop:
```java
private final SortedSetDocValues dv;
DocValuesSortedKeyedValues(DocValuesFieldValues docValues) {
    this.dv = docValues.getValues();
}
```
This is a minor performance/clarity improvement, not a correctness issue.

#0H6ZZ: The `write()` method in `FlattenedFieldSyntheticWriterHelper` calls `sortedKeyedValues.next()` without a null check on the first invocation:
```java
KeyValue curr = new KeyValue(sortedKeyedValues.next());
```
The caller (`FlattenedSortedSetDocValuesSyntheticFieldLoader.write()`) guarantees at least one value exists before calling `write()`, so this is safe in practice. However, since `SortedKeyedValues` is now a public-facing interface (package-private but used across multiple classes), a defensive `Objects.requireNonNull` or an explicit `if (curr == null) return;` guard would make the contract explicit and prevent a confusing NPE inside `KeyValue` if the invariant is ever violated.

#68F80: The custom comparator in `assertStoredFieldsEquals`:
```java
Comparator<IndexableField> comp = Comparator.comparing(IndexableField::name).thenComparing(IndexableField::binaryValue);
```
`IndexableField.binaryValue()` returns `null` for fields that don't carry a binary value. If any stored field in the document lacks a binary value, `thenComparing` will throw a `NullPointerException`. In the current use case all stored fields are `BytesRef`-backed, so this is safe, but using `Comparator.comparing(IndexableField::name).thenComparing(IndexableField::binaryValue, Comparator.nullsLast(Comparator.naturalOrder()))` would make the comparator robust against unexpected field types.
