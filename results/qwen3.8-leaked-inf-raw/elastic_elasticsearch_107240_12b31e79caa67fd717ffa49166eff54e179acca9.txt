#XM6R4: The `PIPELINE_STAT_COMPARATOR` refactoring inadvertently reverses the sort order. The original comparator uses `Long.compare(p2, p1)` (descending), while the new `Comparator.comparingLong(...)` produces ascending order. This changes the order in which pipeline stats are returned to API consumers, which is a behavioral regression not described in the PR summary.
```java
// Old: descending (p2 compared to p1)
Long.compare(p2Stats.ingestTimeInMillis, p1Stats.ingestTimeInMillis)
// New: ascending (natural order)
Comparator.comparingLong((PipelineStat p) -> p.stats.ingestTimeInMillis)
```
To preserve the original descending order, the new comparator should use `.reversed()` or explicitly negate the comparison:
```java
Comparator.comparingLong((PipelineStat p) -> p.stats.ingestTimeInMillis).reversed()
    .thenComparing(Comparator.comparingLong((PipelineStat p) -> p.stats.ingestCount).reversed())
    .thenComparing(Comparator.comparingLong((PipelineStat p) -> p.byteStats.bytesProduced).reversed());
```

#NN5KF, #0EZVN: `peekFirst()` is called unconditionally before the `hasNext()` guard. When both `defaultPipeline` and `finalPipeline` are null (no pipelines configured), `getPipeline(null)` is invoked. Depending on the `getPipeline` implementation (likely a map lookup), this could throw a `NullPointerException`. It would be safer to either:
- Move the `peekFirst()` call after the `hasNext()` check, or
- Add a null guard inside `peekFirst()`:
```java
public Pipeline peekFirst() {
    String first = defaultPipeline != null ? defaultPipeline : finalPipeline;
    return first != null ? getPipeline(first) : null;
}
```

#4KAVQ: The `ByteStats.toXContent` method only serializes fields when *both* values are greater than zero:
```java
if (bytesIngested > 0 && bytesProduced > 0) {
```
This means a pipeline that ingests documents but drops all of them (e.g., a `drop` processor) will have `bytesIngested > 0` and `bytesProduced == 0`, resulting in *neither* field appearing in the API response. While this may be intentional (avoiding partial stats), it's worth confirming: a user debugging a pipeline that drops all documents would see no byte information at all, which could be confusing. If the intent is to always show `ingested_in_bytes` when it's non-zero, the condition should be split:
```java
if (bytesIngested > 0) {
    builder.field("ingested_in_bytes", bytesIngested);
}
if (bytesProduced > 0) {
    builder.field("produced_in_bytes", bytesProduced);
}
```
