#FHDP8: `pendingNodes` is a `Collections.synchronizedSet`, whose methods synchronize on an internal mutex. The `queryNodesFeatures` method additionally wraps the check-and-add loop in `synchronized (pendingNodes)`, which locks on the *set object itself* — a different monitor. Meanwhile, the `onResponse`/`onFailure` callbacks call `pendingNodes.removeAll(outstandingNodes)` without holding that outer lock. In practice the worst case is a harmless duplicate request (since `add()` is individually atomic), but the two different locks make the intent unclear. Consider either using a plain `HashSet` guarded entirely by the `synchronized (pendingNodes)` block (including in the callbacks), or dropping the outer `synchronized` and relying solely on the `synchronizedSet` semantics with a comment explaining why duplicate requests are safe.

#FHDP8: `scheduleRetry` retries every 30 s indefinitely with a fixed interval. If a node is permanently removed from the cluster (e.g., decommissioned) but its entry lingers in cluster state briefly, the listener will keep issuing transport calls to a non-existent node forever. Consider adding a maximum retry count (or at least an exponential backoff cap) and logging at `WARN` after a threshold number of failures, so operators can notice a stuck fixup.

#WD7TW: The existing tests cover the happy path, version filtering, and full-failure retry, but two important paths are untested:
- **Partial failure**: some nodes succeed, some fail. The code in `handleResponse` is supposed to submit a task for the successful nodes *and* schedule a retry for the failed ones. A test asserting both behaviors would guard against a regression where one path accidentally suppresses the other.
- **Non-master / no-master-change case**: a test asserting that `clusterChanged` is a no-op when `event.localNodeMaster()` is false or `masterNodeChanged()` is false would document the guard condition.

#5W8KF: Both `readNodesFrom` and `writeNodesTo` delegate to `TransportAction.localOnly()`, which throws. This is correct for the current use (the response is only ever materialized on the coordinating/master node), but it means the response type can never be used in a remote context. A brief comment on the class or methods stating *why* serialization is intentionally unsupported (e.g., "response is only consumed locally by the master; never sent over the wire") would prevent a future developer from accidentally trying to use it in a remote flow and hitting the `UnsupportedOperationException` at runtime.
