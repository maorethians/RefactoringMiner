#NDAEZ, #9DFSF, #VG8DB: The core fix is correct: replacing the unsynchronized check-then-act on `perThreadProvider` with `ConcurrentHashMap.computeIfAbsent` eliminates the race condition where two threads could both observe a stale/null provider and overwrite each other's assignment. Using `Thread.getId()` as the key is safe since Java guarantees thread IDs are unique and never reused.

#JDK6Q: One minor observation on the test: the `expectedMeterColumn` is built with a manual loop (`val += 10000.0`), but since the indexed value is `10000 * i` (int arithmetic, well within range for `i < 256`), this is equivalent to `LongStream.range(0L, numDocs).mapToDouble(i -> i * 10000.0).boxed().toList()`. Not a bug, just a slightly more concise alternative that mirrors the style already used for `k1Column` two lines above.

#1JD7R: The unbounded `Map<Long, SourceProvider>` will retain entries for threads that have already finished. In practice the number of threads per query is bounded by `task_concurrency`, so this is not a real concern, but it is worth being aware of if this class were ever reused across many sequential queries with high thread churn.
