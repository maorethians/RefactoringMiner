#59RAM, #ASZ5C: The `types()` method in `InvalidMappedField` allocates a new `Set<DataType>` on every invocation via `stream().map(...).collect(Collectors.toSet())`. This method is called in the `isType` hot path (per-expression type resolution) and in `resolveConvertFunction`. If the `typesToIndices` map is small (typically 2-4 entries), the allocation overhead is negligible, but if this is called in a tight loop over many expressions, it could add up. Consider caching the set as a field (computed once in the constructor) since `typesToIndices` is immutable after construction.

#RTS4M: In `castStringLiteral`, the return type changes from `UnsupportedAttribute` to `UnresolvedAttribute` when a cast of a string literal fails. An `UnsupportedAttribute` is a terminal error state, while `UnresolvedAttribute` implies the expression may still be resolved by a later rule. For a failed literal cast (e.g., casting a non-numeric string to `long`), there is no later rule that would resolve it — it is inherently unsupported. This could result in a less precise error message reaching the user (e.g., "unresolved" instead of "unsupported type"). If this is intentional to unify error handling through a later rule, a brief comment explaining why `UnresolvedAttribute` is preferred here would help future readers.

#1DERJ: Removing `p.resolved() ||` from the `transformUp` predicate in `ResolveUnionTypes.apply` means the rule will now also visit plans that are already marked as resolved. This is necessary for the fix (plans containing `InvalidMappedField` may be "resolved" in the structural sense but still need union-type processing), but it broadens the set of plans visited. If the plan tree is deep and most plans are already resolved, this adds unnecessary traversal cost. Consider whether a more targeted check (e.g., checking for the presence of `InvalidMappedField` in the plan's expressions) could short-circuit the traversal for plans that genuinely don't need processing.

#59RAM, #K541H: The TODO about widening small numerical types appears in two places. This is a real correctness gap: if a field is mapped as `[integer, long]` and a convert function supports `long` but not `integer`, the `allMatch(predicate)` check will fail even though `integer` is safely widenable to `long`. This means queries that should work will still produce errors. Since this is a known limitation, consider filing a follow-up issue and referencing it in the TODO so it doesn't get lost.

#TT4TC: The `checkUnresolved` method now constructs the types string via `imf.getTypesToIndices().keySet().stream().collect(Collectors.joining(","))`. This produces an unordered string (since `keySet()` iteration order depends on the underlying map implementation). If the `typesToIndices` map is a `TreeMap` (as suggested by the import in `InvalidMappedField`), the order is deterministic (lexicographic by type name). However, if it's ever changed to a `HashMap`, the error message order would become non-deterministic, which could break tests that match on the exact error string. Consider explicitly sorting or documenting the expected order.
