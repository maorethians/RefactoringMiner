#T4DYB, #5VW1W, #V3H4M, #QRQGW, #MS3NM, #X9MM7, #4RKV4: The overall change is a well-motivated resource-leak fix: ensuring `HttpEntity` streams are consumed (and thus closed) on both success and failure paths. The framework-level methods (`entityAsMap`, `entityAsList`, `assertAcknowledged`, `assertOKAndConsume`) now guarantee consumption via `finally` blocks, which is the correct pattern.
One minor observation on the call-site changes in `TransformRestTestCase`:
In **#X9MM7** (`doBulk`) and **#4RKV4** (`matchAllSearch`), the manual `try/finally { EntityUtils.consumeQuietly(...) }` wrapper is redundant in the success path because `entityAsMap` (added in #5VW1W) already consumes the entity in its own `finally`. The outer `finally` is only meaningful if `assertOK` throws before `entityAsMap` is reached. This is a valid defensive pattern and `consumeQuietly` is idempotent, so there is no bug — but a brief inline comment (e.g., `// safety net if assertOK throws before entityAsMap consumes`) would make the intent clearer to future readers and prevent someone from "cleaning up" the seemingly-duplicate call.

#M60GM, #6HRFE, #7ZGDG: Changing `putTransform` from returning `Response` to `void` is a breaking signature change for any external callers of this test-base class. The one caller shown here (#7ZGDG) is updated consistently. If other test classes in the repo (or downstream forks) still call `putTransform(...)` and use the returned `Response`, they will fail to compile. Worth confirming no other call sites exist outside this diff.

#TAZC3: `createReviewsIndex` switches from `assertOK` to `assertAcknowledged`, which additionally asserts the body contains `"acknowledged":true`. This is a stronger check and is appropriate for index-creation responses. Just flagging that this is a behavioral change (a test that previously passed on a 200 with an unexpected body would now fail), in case it surfaces as a flaky-test regression.
