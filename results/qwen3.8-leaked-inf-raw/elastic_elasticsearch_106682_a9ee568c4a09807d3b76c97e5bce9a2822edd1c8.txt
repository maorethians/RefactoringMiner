#70J1V: Two concerns with the new fallback logic:
1. **Unhandled `IllegalArgumentException` from Base64 decoding.** `Base64.getUrlDecoder().decode(context.sourceToParse().id())` will throw an `IllegalArgumentException` if the `_id` is not valid base64url. The previous code had a safe fallback (`encode(0)`) when `routingHash` was null. Now, any document with a null routing hash and a non-base64url id will fail with an uncaught exception. Consider wrapping the decode in a try/catch or validating the id format before decoding, and falling back to a safe default (or a more descriptive error message) on failure.
2. **`Arrays.copyOf` with a length of 4 silently pads with zeros** if the decoded id is fewer than 4 bytes. This is likely intentional (taking the first 4 bytes as the routing hash), but it means a 1-byte id and a 4-byte id that happens to start with the same byte will produce the same routing hash. If this is the intended behavior, a brief comment would help future readers understand why exactly 4 bytes are taken.

#PKP9K: The removed test `testParseWithDynamicMappingNullId` covered the null-id / null-routing-hash scenario. The new code path in `#70J1V` (deriving the routing hash from the first 4 bytes of the decoded `_id` when `routingHash` is null) does not appear to have a corresponding test in this chapter. Consider adding a test that:
- Provides a valid base64url-encoded `_id` with a null routing hash, and asserts the resulting `_ts_routing_hash` field equals the expected value derived from the first 4 bytes of the decoded id.
- Optionally, verifies the behavior when the id is not valid base64url (to document the expected failure mode).
