#SSCWF: The `extractInnerHitBuilders` override in `RankDocsQueryBuilder` (#SSCWF) iterates over nested `queryBuilders` and delegates to each `AbstractQueryBuilder`, but does not call `super.extractInnerHitBuilders(innerHits)`. If the default implementation in `AbstractQueryBuilder` performs any bookkeeping (e.g., registering the builder itself in the map), that step is silently skipped. In practice `RankDocsQueryBuilder` likely has no inner-hits of its own, so this is probably fine, but it's worth confirming that the parent's default is a true no-op to avoid a subtle divergence if the base class contract changes later.

#855J4: The `skipInnerHits` flag is set in four places (`CompoundRetrieverBuilder`, `KnnRetrieverBuilder`, `RankDocsRetrieverBuilder`, `StandardRetrieverBuilder`). In `CompoundRetrieverBuilder.createSearchSourceBuilder` (#855J4) it is set unconditionally, while in the three leaf retrievers it is gated on `compoundUsed`. This is logically correct (a compound retriever's sub-searches should always skip inner hits; a leaf retriever only skips them when embedded in a compound), but the asymmetry could be confusing to future readers. A brief comment at the `CompoundRetrieverBuilder` site explaining *why* it's unconditional (the compound retriever itself will compute inner hits on the merged results) would help.

#GX19F, #3833R: The `skipInnerHits` field in `SearchSourceBuilder` (#GX19F, #3833R) is a mutable public field with a setter, consistent with the existing style of that class. However, it is intentionally excluded from `toXContent` and stream serialization of `SearchSourceBuilder` (it is only extracted into `ShardSearchRequest`). This is the right call since it's an internal optimization flag, not a user-facing parameter, but it means the flag is invisible if anyone inspects a serialized `SearchSourceBuilder` (e.g., in debug logs or REST responses). No action needed, just noting for awareness.

#8SCMR, #JV7KW: The transport-version guard in `ShardSearchRequest` (#8SCMR, #JV7KW) correctly defaults `skipInnerHits` to `false` when reading from an older node, preserving backward compatibility.

#B208T: The YAML test (#B208T) covers the primary scenario well: an RRF compound retriever with two sub-retrievers that define `inner_hits` on nested fields, verifying that inner hits appear in the top-level results with correct per-document values. One gap: there is no assertion that a sub-retriever's inner hits are *not* independently present (i.e., confirming the skip actually took effect rather than just that the compound retriever's inner hits happen to be correct). Adding a negative check or a standalone-retriever comparison would strengthen the test.
