#DY9N3, #S92QS, #KG61E, #FVWQF, #3A1FE, #WXCV7, #7ZNDQ, #W2GYJ, #1ZR6Y, #64HWB: The `DocumentParser` changes. A few observations:
1. In `parseDocForMissingValues`, the token-advancement sequence for a matched leaf field is:
   ```java
   parser.nextToken();   // to value
   result.add(leaf.cloneWithValue(XContentDataHelper.encodeToken(parser)));
   parser.nextToken();   // "Skip the token ending the value."
   // ... falls through to:
   currentToken = parser.nextToken();
   ```
   That is three `nextToken()` calls after the `FIELD_NAME`. If `encodeToken` does not itself advance the parser past the value (i.e., it reads the current token in place), then for a scalar value the sequence would be: `VALUE_X` → `nextToken` → `FIELD_NAME_next` → `nextToken` → `VALUE_next`, effectively skipping the next `FIELD_NAME`. For object/array values where `encodeToken` consumes through `END_OBJECT`/`END_ARRAY`, the extra `nextToken` after `encodeToken` plus the loop's `nextToken` would also skip one token. Please verify the exact post-condition of `encodeToken` (does it leave the parser *at* the closing token or *past* it?) and adjust the number of `nextToken` calls accordingly. A unit test with two sibling leaf fields at the same level (e.g., `{"a": 1, "b": 2}` where both are in the target set) would catch an off-by-one.
2. `internalParseDocument` was changed from `static` to an instance method solely to access `parserConfiguration` in `addIgnoredSourceMissingValues`. This is fine, but it means every call site must now go through an instance. Since the method is `private`, this is contained, but worth noting for future refactors.

#JJWNN, #4CYN3, #2G4GJ, #ENHDW, #SYNWM, #S8BK8, #T1GZW, #T9MTM, #WJ8GX, #3PP1V, #VGEPA: `DocumentParserContext` changes. The rename `clonedSource` → `recordedSource` is clearer. The new `parentArrayField` + `ignoredFieldsMissingValues` fields and the `addIgnoredFieldFromContext` / `maybeCloneForArray` methods implement the deferred-encoding logic.
One concern in `addIgnoredFieldFromContext`:
```java
if (parentArrayField != null
    && parent != null
    && parentArrayField.equals(parent.fullPath())
    && parent instanceof NestedObjectMapper == false) {
```
The condition `parentArrayField.equals(parent.fullPath())` checks that the *immediate* parent is the top-level array. If a field needing source is nested deeper (e.g., `arr[0].inner.leaf` where `arr` is the top array), the `parent` at the point of the call would be the `inner` object mapper, not `arr`. In that case the condition would be false and the code would take the "immediate encode" path. Is that the intended behavior for deeply nested fields within a tracked array, or should the check walk up the parent chain to see if *any* ancestor is the tracked array?
