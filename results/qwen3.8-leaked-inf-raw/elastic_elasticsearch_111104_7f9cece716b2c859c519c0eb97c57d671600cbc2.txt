#9YXHR, #W7QJT: The new `getResponseMediaType(RestRequest)` overload does not call `checkNonNullMediaType`, unlike the existing `getResponseMediaType(RestRequest, EsqlQueryRequest)` which does. This means the new `EsqlResponseListener(RestChannel, RestRequest)` constructor can leave `this.mediaType` as `null`. Downstream in `buildResponse`, a null `mediaType` will not match any of the format-specific branches (`CSV`, `ArrowFormat`, etc.), which could lead to an unhandled path or a `NullPointerException` when the code attempts to use the media type. Consider calling `checkNonNullMediaType` in the new overload (or in the new constructor) to preserve the invariant that `mediaType` is always non-null after construction.

#EM297: In the branch where `id != null` and `isRunning == false` (query completed immediately with `keep_on_completion=true`), the text-format path relies on `initialValues` having been populated earlier from the entity body. However, if the entity body is empty (e.g., a zero-row result in txt mode), `initialValues` will be `""`. The later comparison guard:
```java
if (initialValues != null && ((String) initialValues).isEmpty() == false) {
    assertEquals(initialValues, result);
}
```
will skip the assertion, meaning the async-get result is never compared against the initial result for empty text responses. This is likely intentional (an empty string is trivially equal), but it means a regression where the async-get returns non-empty content for a zero-row query would go undetected in txt mode. Consider asserting `initialValues` equals the async-get result unconditionally when `isRunning == false` and `isTextFormat`, rather than skipping on empty.
