#TRJ5Y, #1D5HC, #K6Q58: The `@FunctionInfo` description reads: *"Returns an integer that indicates the position of a **keyword** substring within another string."* The word "keyword" here is a data-type name leaking into user-facing prose and is confusing (it implies the substring must be of type `keyword`, but `text` is also accepted). It should read something like: *"Returns an integer that indicates the position of a substring within another string."* Because the asciidoc files and meta.csv-spec entries are generated from this annotation, fixing the annotation in `Locate.java` will propagate the correction.

#TRJ5Y, #QJ49F, #Y9C93: The `indexStart` helper explicitly supports **negative** `start` values (interpreted as an offset from the end of the string), but no test—neither in the unit tests (`LocateTests`) nor in the CSV spec (`string.csv-spec`)—exercises this path. For example, `locate("hello", "ll", -2)` should search starting at code-point index 3 and return `3`, while `locate("hello", "ll", -10)` should return `0`. Adding at least one positive and one out-of-range negative-start case would cover this branch and guard against regressions.

#TRJ5Y: In `process`, the early-exit guard `str.length < substr.length` compares **byte** lengths. While this is a valid necessary condition (a shorter byte sequence cannot contain a longer one), it is easy to misread as a code-point comparison. A brief inline comment clarifying that this is a byte-length short-circuit (and therefore safe regardless of multi-byte characters) would improve maintainability for future readers.
