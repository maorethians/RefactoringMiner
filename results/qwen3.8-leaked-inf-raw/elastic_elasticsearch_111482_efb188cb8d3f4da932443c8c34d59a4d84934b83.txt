One minor note: the human-readable message `"any type except unsigned_long and spatial types"` is helpful, but consider whether `UNSIGNED_LONG` should also be excluded from `Max`/`Min` (which it already is via `e != DataType.UNSIGNED_LONG`). The three aggregate functions now have consistent exclusion of `UNSIGNED_LONG`, which is good.

#EN13J: The variable name `allValuesNull` is misleading. It is assigned via `anyMatch(Block::areAllValuesNull)`, which returns `true` if *any* block is entirely null — not that *all* values across all blocks are null. A name like `anyBlockAllNull` or `hasAllNullBlock` would more accurately reflect the `anyMatch` semantics. As written, a reader could assume a stronger invariant than what is actually checked.

#FNG87: The `evaluate` method is refactored from using the runtime evaluator (`evaluator(...).eval(...)`) to calling `evaluableExpression.fold()`. This is consistent with its new role in `testFold`, but note that this is a **private** method — if any other test method in `AbstractAggregationTestCase` (e.g., `aggregateSingleMode`, `aggregateWithIntermediates`) also calls `evaluate`, those paths now exercise the fold code path instead of the evaluator code path. Please confirm no other callers rely on the evaluator-based evaluation, or that the fold path is a valid substitute in those contexts.

#Z8CDE: In `anyNullIsNull`, the main-loop branch uses `od.withData(od.isMultiRow() ? Collections.singletonList(null) : null)` which preserves the original `DataType` (e.g., `INTEGER`) while setting the value to null. The first-time-seen-signature branch uses `TypedData.NULL` / `TypedData.MULTI_ROW_NULL` which carry `DataType.NULL`. This distinction is intentional and correct, but it means the two generated test cases exercise different type-resolution paths (null-of-type-X vs. type-NULL). Worth a brief inline comment for future readers, since the distinction is subtle and easy to conflate.

#DJE2A, #W2V7A, #S3XYW: Fixing the `types()` list from a single-element list (e.g., `List.of(DataType.INTEGER)`) to a two-element list matching both parameters (`List.of(DataType.INTEGER, DataType.INTEGER)`) is a necessary correction. The old single-element list would have caused `errorsForCasesWithoutExamples` and `anyNullIsNull` to generate incorrect permutations and null-injection cases for a two-argument function. The field-name corrections (`"field"` → `"number"`/`"weight"`) also align the test data with the actual parameter names.

#R5MTH: The fix from `new Literal(Source.synthetic(name), values, type)` to `new Literal(Source.synthetic(name), values.get(0), type)` is correct — the guard above ensures `values.size() == 1`, so `get(0)` is safe and produces a proper scalar literal rather than a list literal.
