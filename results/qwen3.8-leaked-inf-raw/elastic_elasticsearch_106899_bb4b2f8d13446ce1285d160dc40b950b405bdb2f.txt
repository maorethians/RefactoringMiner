#QJ49F, #JWNYE: The `start` parameter is never exercised with a non-zero value in any test. The `indexStart` helper in `Locate.java` has three distinct branches (`start > 0`, `start < 0`, `start == 0`), but every unit test and csv-spec test passes `start = 0`. This means:
- Positive `start` (e.g., `locate("hello world", "world", 7)` → expected `7`)
- Negative `start` (e.g., `locate("hello world", "world", -5)` → expected `7`)
- `start` beyond the string length (clamped to `codePointCount`)
- `start` so negative that `codePointCount + start < 0` (clamped to `0`)
…are all untested. The `indexStart` sanitization logic (`Math.min(Math.max(0, indexStart), codePointCount)`) is the kind of boundary code that is most likely to harbor off-by-one errors, and it currently has zero coverage. I'd recommend adding at least a few targeted unit tests for these paths in `LocateTests` and a csv-spec case that uses a non-zero `start`.

#RHK61: The `process` method does not guard against an empty `substr`. If `substr` is the empty string, `String.indexOf("", fromIndex)` returns `fromIndex`, so the method would return `1 + fromIndex` (e.g., `locate("hello", "", 3)` → `3`). Most SQL dialects define `LOCATE('', s)` as `1` (or `0` for "not found"). This is an undefined edge case that should either be explicitly handled (return `0` or `1`) or documented, and covered by a test.

#RHK61: Minor: the early-exit condition `str.length < substr.length` compares **byte** lengths. While this is a valid necessary condition (a string with fewer bytes cannot contain a string with more bytes), it is not sufficient for multi-byte characters and may be misleading to a reader who expects a code-point comparison. A brief inline comment clarifying that this is a byte-length fast-path (the real check is done by `indexOf`) would prevent future confusion.
