#D9WHT, #4QRM4, #FPGEB, #47K4P, #JG551, #8TKKH, #HNH11, #WA7ZP: The depth counter is not decremented when the `ParsingException` is thrown because the `throw` occurs outside the `try` block. In both `ExpressionBuilder.expression()` and `LogicalPlanBuilder.visitCompositeQuery()`, the pattern is:
```java
expressionDepth++;
if (expressionDepth > MAX_EXPRESSION_DEPTH) {
    throw new ParsingException(...);  // finally block is never reached
}
try {
    return typedParsing(this, ctx, Expression.class);
} finally {
    expressionDepth--;
}
```
If the limit is exceeded, `expressionDepth` is left incremented (e.g., at 501) and never restored. While this is unlikely to cause a practical issue (the builder instance is typically discarded after a parse failure), it leaves the object in an inconsistent state and would mask the problem if the instance were ever reused. The increment should be moved inside the `try` block so the `finally` always executes:
```java
expressionDepth++;
try {
    if (expressionDepth > MAX_EXPRESSION_DEPTH) {
        throw new ParsingException(
            "ESQL statement exceeded the maximum expression depth allowed ({}): [{}]",
            MAX_EXPRESSION_DEPTH,
            ctx.getParent().getText()
        );
    }
    return typedParsing(this, ctx, Expression.class);
} finally {
    expressionDepth--;
}
```
The same fix applies to `queryDepth` in `LogicalPlanBuilder.visitCompositeQuery()`.

#JG551: The error message embeds `ctx.getText()`, which for a composite query at the 500-command limit will be the full text of the entire query (potentially thousands of characters). This makes the error message unwieldy and could bloat logs. Consider truncating the text or using a shorter identifier (e.g., the command name at the overflow point) instead of the full query text.
