#3YQWQ, #SNPXP: The `geoPointCases` and `cartesianPointCases` methods pass names that already contain angle brackets (e.g., `"<no alt geo_point>"`, `"<with alt cartesian_point>"`) to `addSuppliers`, which then wraps them in its own angle brackets. This produces malformed test-case names like `"<<no alt geo_point>s>"` and `"<single <with alt cartesian_point>>"`. The names should be passed without the surrounding brackets (e.g., `"no alt geo_point"`) to be consistent with every other call site in this file.

#H9GWE: The new `addSuppliers` helper never produces a zero-element list: the "single" branch always generates exactly 1 element, and the multi-row branch uses `Math.max(2, minRows)` as the lower bound. The previous code called `randomList(minRows, maxRows, ...)` directly, so when a caller passed `minRows = 0`, an empty list was a possible outcome. If any caller relies on `minRows = 0` to exercise the empty-input path of an aggregation, that coverage is silently lost. Consider whether an explicit empty-list case should still be emitted, or document that callers must guarantee `minRows >= 1`.

#EMVBD: When `fieldData.size() == 0`, neither the `if` nor the `else if` branch executes, leaving `expected` as `null`. Although the refactored `addSuppliers` currently prevents zero-element lists, the method has no guard against it. A defensive `else` branch (e.g., `throw new IllegalStateException("Expected at least one row")`) would make the contract explicit and prevent a confusing `null` expected-value from propagating into the test framework if a future caller passes an empty supplier.
