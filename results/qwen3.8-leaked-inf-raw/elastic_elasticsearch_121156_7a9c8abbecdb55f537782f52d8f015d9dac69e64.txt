#W996H: The `findRedundantSort` traversal stops when it encounters a node that is neither `OrderBy` nor `SortAware` (or is `SortAware` with `dependsOnInputOrder() == true`). `TopN` does not implement `SortAware`, so if the plan contains a `TopN` between the triggering node and a redundant `OrderBy`, the traversal halts and the inner sort is not pruned. For example:
```
SORT z
  TopN (sort y, limit 5)
    MvExpand
      SORT x   ← not pruned, but is redundant
        Source
```
While `PushDownAndCombineLimits` may eliminate this shape in most cases, adding `SortAware` to `TopN` (with the default `dependsOnInputOrder() == false`) would make the pruning more robust and cover edge cases where a `TopN` survives in the middle of the plan.

#W996H, #04GEN: The old `PruneOrderByBeforeStats` was declared `final`, but the new `PruneRedundantOrderBy` is not. Since this is a concrete optimizer rule with no extension points, marking it `final` would be consistent with the project's existing pattern for optimizer rules and prevent accidental subclassing.

#5X7J7, #T2JCT, #822NS, #Z5K4Z, #VTXT5, #X48DK, #WNJHG, #TRE8F, #XPYD2, #Y7THW, #DG6NQ, #HRHTC, #5YFH2: There is an inconsistent pattern in how `SortAware` is adopted. `Aggregate`, `Eval`, `Filter`, and `InlineStats` explicitly override `dependsOnInputOrder()` to call `SortAware.super.dependsOnInputOrder()` (which returns `false`) with a TODO comment about window functions. The remaining classes (`Drop`, `Enrich`, `Keep`, `Lookup`, `MvExpand`, `Project`, `RegexExtract`, `Rename`, `Join`) simply rely on the interface default without any override or comment. Since the default already returns `false`, the explicit overrides are functionally redundant. Either all classes should carry the TODO (to flag the window-function risk uniformly), or none should — the current split makes it harder for a future contributor to know which classes were explicitly considered.
