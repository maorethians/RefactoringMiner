#370GF, #MXYWG: The old code in `IgnoredSourceFieldMapper.postParse` iterated over `context.getCopyToFields()`, which (based on the name and the deduplication semantics of the old loop) collected **unique** copy_to target fields. The new code adds a void value inside `createCopyToContext`, which is called **once per source field** that has a `copy_to` directive. If two (or more) source fields target the same copy_to destination — e.g., both `k` and `k2` in the test mapping copy to `my_values.copy` — the new code will append **two** `NameValue` entries for the same target into `ignoredFieldValues`, and `postParse` will write two duplicate stored fields.
The old code would have produced a single entry because `getCopyToFields()` deduplicated. This is a behavioral change. If the synthetic-source reader tolerates duplicate void markers (e.g., it only checks "does a void entry exist for this path?"), the impact is benign. If it iterates entries and acts on each, duplicates could cause subtle issues. Consider either:
- Adding a guard to skip if an entry for the same `copyToField` already exists in `ignoredFieldValues`, or
- Confirming that the reader is idempotent with respect to duplicate void values and adding a brief comment noting this.

#W00DA: The test exercises two **separate documents** each triggering one copy_to source field. It does not cover the case where a **single document** has two fields that both `copy_to` the same target (e.g., a doc with both `my_values.k` and `my_values.second_level.k2` set). That is precisely the scenario where the duplicate-void-value concern above would surface. Adding a third document (or extending an existing one) with both source fields populated would strengthen the test and validate the deduplication behavior.
