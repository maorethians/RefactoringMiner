#B8DTP, #Y1Y8E, #X6X2G: **Testability regression:** The `SleepFunction` abstraction was removed and replaced with a direct `Thread.sleep(interval.millis())` call inside `innerDetect`. Previously, tests could inject a no-op sleep function (as seen in the old test: `(interval) -> null`) to avoid real sleeping. Now that the sleep is hardcoded, any test that exercises `innerDetect` with a non-zero interval will incur a real `Thread.sleep`, slowing the test suite and making it harder to test the logic in isolation. Consider keeping an injectable sleep mechanism (e.g., a `LongConsumer` or a small functional interface) alongside the new `onNextThread` parameter, or at minimum ensuring the test interval is set to zero.

#TFG8C, #1SE5R: **Callback invoked while holding the monitor lock:** `onNextThread.run()` is called inside the `synchronized (mutex)` block in `detect`. In `logLocalCurrentThreads`, the callback performs `logger.log(...)`, which may involve I/O (appender writes, network transport, etc.). This means the `HotThreads` mutex is held for the duration of each log write. If other threads are contending on this lock (e.g., a concurrent hot-threads detection), they will be blocked during logging I/O. Consider invoking the callback outside the synchronized region, or at least documenting this constraint.

#1SE5R: **Broad exception catch swallows `InterruptedException`:** The `catch (Exception e)` in `logLocalCurrentThreads` will catch `InterruptedException` (propagated from `Thread.sleep` inside `innerDetect`) and log it as a generic error without restoring the interrupt flag. The standard practice is to re-interrupt the thread (`Thread.currentThread().interrupt()`) when catching `InterruptedException`, so that the calling context is aware of the interruption.
