#5V1ZM: **Thread-safety of `stoppedCompilationTime` and `logShutdownCompilations`:** Both fields in `OptimizedTruffleRuntime` are plain (non-volatile) instance fields that are read and written from `submitForCompilation`, which can be invoked concurrently by multiple compiler threads. Without `volatile` (or equivalent synchronization), there is no happens-before guarantee between threads, and on 32-bit JVMs a `long` read/write is not even atomic. The check-then-act on `logShutdownCompilations` (`if (logShutdownCompilations) { logShutdownCompilations = false; ... }`) is a classic race that can cause the warning to be logged multiple times or, conversely, the flag to be lost. Consider making both fields `volatile`, or guarding access with the existing queue-level synchronization.

#K8K5K: **Repeated `shutdownAndAwaitTermination` in the SHUTDOWN_COMPILATION branch:** Every subsequent call to `submitForCompilation` while the host is in SHUTDOWN_COMPILATION mode will invoke `queue.shutdownAndAwaitTermination(100)` again on an already-shut-down queue. This is wasteful (it blocks up to 100 ms each time) and may throw or behave unexpectedly depending on the queue implementation. A guard flag (e.g., `boolean queueShutDown`) or a check on the queue's state before calling shutdown would avoid the repeated work.

#6QH8K: **Name collision between the static field and the instance method:** The static field `getCompilationActivityMode` (a `MethodHandle`) and the instance method `getCompilationActivityMode()` share the same name. Inside the method body, the unqualified reference `getCompilationActivityMode` resolves to the field, but this is极易 to misread and to accidentally shadow in future edits. Renaming the field (e.g., `compilationActivityModeHandle`) would eliminate the ambiguity.

#K8K5K: **Retry condition does not re-check the host mode after the delay elapses:** When `stoppedCompilationTime != 0` and the retry delay has passed, the code submits the compilation unconditionally (first branch of the `if`). However, the host may still be in STOP_COMPILATION mode (e.g., the code cache is still full). The intent appears to be "retry and let the host decide," which is fine, but the code path bypasses the `else if (STOP_COMPILATION)` branch entirely, so `stoppedCompilationTime` is reset to 0 even though the host has not actually resumed. If the next call again sees STOP_COMPILATION, the timer restarts from zero, effectively resetting the retry window on every attempt. Consider only resetting `stoppedCompilationTime` when the mode is confirmed to be RUN_COMPILATION.
