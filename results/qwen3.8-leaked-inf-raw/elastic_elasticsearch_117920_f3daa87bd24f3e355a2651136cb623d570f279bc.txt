#E3THM, #0S0Z0, #P473A: In `stopProcessAfterCompletingPendingWork()` (#P473A), the old code explicitly called `handleAlreadyShuttingDownWorker()` (which invoked `priorityProcessWorker.notifyQueueRunnables()`) when the worker was already shut down, before proceeding. The new code unconditionally calls `signalAndWaitForWorkerTermination()`. If `signalAndWaitForWorkerTermination()` does not internally handle the already-shut-down case (i.e., it does not call `notifyQueueRunnables()`), then any requests still waiting in the work queue when the worker has already crashed/stopped will never be notified and could hang indefinitely. Please confirm that `signalAndWaitForWorkerTermination()` covers this path, or restore the `notifyQueueRunnables()` call for the already-shut-down case.

#BJY0X: The switch from `shutdown()` to `shutdownNow()` + `awaitTermination(30s)` is a solid improvement for the forceful-stop path, and the interrupt-flag restoration is correct. Two minor observations:
1. `shutdownNow()` returns a `List<Runnable>` of tasks that were not given a chance to execute. The return value is discarded here. If any of those tasks hold resources or need cleanup, they will be silently dropped. If that is intentional for a forceful kill, a brief comment would help future readers.
2. The 30-second timeout is a magic number. Consider extracting it to a named constant (e.g., `WORKER_SHUTDOWN_TIMEOUT_SECONDS`) so it is easy to find and adjust, and so it can be shared if the same timeout is needed elsewhere.
