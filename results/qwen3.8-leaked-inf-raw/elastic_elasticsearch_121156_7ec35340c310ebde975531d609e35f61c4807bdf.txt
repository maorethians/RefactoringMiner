#D9R5R: Two observations on the `findRedundantSort` traversal logic:
1. The explicit exclusion of `Eval` and `Aggregate` (with the commented-out lines) means any query where an `Eval` sits between the TopN and the redundant `OrderBy` will fail with "unbounded sort" even when the sort is provably redundant. This is a safe, conservative choice, but it's worth confirming that the `testRedundantSortOnMvExpand` and `testRedundantSortOnJoin` tests pass because the optimizer restructures the plan (pushing Eval below the OrderBy) *before* `RemoveRedundantSort` runs, rather than because the rule traverses through Eval. If a future rule change alters the plan shape, these tests could regress silently.
2. The `Join` branch only walks `lj.left()`. For lookup joins this is correct (the right side is a small static table), but if this rule is ever applied to non-lookup joins, a redundant sort on the right side would be missed and the query would fail. The TODO comment acknowledges this; consider adding a brief note in the class Javadoc that this rule is intended for lookup-join / mv-expand scenarios specifically.
