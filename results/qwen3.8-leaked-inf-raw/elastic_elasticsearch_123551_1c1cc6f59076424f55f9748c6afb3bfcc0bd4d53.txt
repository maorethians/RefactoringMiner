#2RWRH: The `NO_UPGRADE_REQUIRED_VERSION` is set to `Version.V_8_0_0` with a comment saying "These versions should be set to current major and current major's index version." The computed `UPGRADED_TO_VERSION` becomes `9`, producing the suffix `-reindexed-for-9`. If the intent is that indices created in 9.x don't need migration (i.e., we're upgrading *to* 9), then `NO_UPGRADE_REQUIRED_VERSION` should logically be `V_9_0_0`, making `UPGRADED_TO_VERSION = 10`. As written, the semantics are: "indices created before 8.0 need migration to 9" — which means 8.x indices *do* need migration. Please confirm this is the intended semantics and not a placeholder that needs updating before release.

#JGFND: The migration detection in `buildManagedSystemIndexUpdateRequest` relies on two string checks:
```java
boolean indexMigrationInProgress = cause.equals(SystemIndices.MIGRATE_SYSTEM_INDEX_CAUSE)
    && request.index().endsWith(SystemIndices.UPGRADED_INDEX_SUFFIX);
```
When this condition is true, the method skips the validation that the index name matches the descriptor's primary index or alias. This means any request carrying the internal cause string `"migrate-system-index"` and ending with `-reindexed-for-9` will bypass the `IllegalArgumentException` guard. While the cause is an internal constant, consider whether a more robust mechanism (e.g., a dedicated request flag or a check that the caller is the system user) would be safer, especially now that the migrator goes through the full transport layer where action filters and security checks apply.

#FCQ2E, #32N61: The `SystemIndexMigrator` now routes `createIndex` and `updateSettings` through `baseClient` (the transport layer) instead of calling `MetadataCreateIndexService` / `MetadataUpdateSettingsService` directly. This is a significant architectural shift: the requests will now pass through all action filters, security checks, and the full REST/transport pipeline. Two concerns:
1. The `ackTimeout(TimeValue.ZERO)` combined with `waitForActiveShards(ActiveShardCount.ALL)` — please confirm that `TimeValue.ZERO` here means "wait indefinitely for ack" rather than "return immediately without waiting." In some Elasticsearch APIs, `ZERO` timeout means "don't wait," which would contradict the `ALL` shard count requirement.
2. Any action filter registered by other plugins (or the security plugin's own filters) will now intercept these internal migration calls. The `BlockingActionFilter` in the test plugin hints at this interaction. Ensure that the system user's privileges (added in `SystemPrivilege`) are sufficient and that no filter can inadvertently block or modify the migration requests.

#YHXGR: Adding `TransportCreateIndexAction.TYPE.name() + "*"` and `TransportUpdateSettingsAction.TYPE.name() + "*"` to `SystemPrivilege` grants the system user the ability to create *any* index and update settings on *any* index, not just system indices. While this is scoped to the internal system user and is necessary for the migrator to work through the client layer, it is broader than the previous direct-service-call approach. Consider whether a more targeted permission (e.g., restricted to system index patterns) is feasible within Elasticsearch's permission model, or at minimum add a comment explaining why the wildcard is necessary.

#349K6, #M0BQE: `MigratePlugin` stores `SystemIndices` in a `SetOnce` field, set in `createComponents` and read in `getPersistentTasksExecutor`. If the plugin lifecycle ever changes such that `getPersistentTasksExecutor` is called before `createComponents`, `systemIndices.get()` will throw. While the current lifecycle guarantees the ordering, a `SetOnce` that is read in a separate lifecycle callback is a latent fragility. Consider whether the `SystemIndices` reference could be obtained directly from the `PluginServices` parameter of `getPersistentTasksExecutor` (if available) to eliminate the ordering dependency.

#S6R08: The new test `testCreatingSystemIndexForMigration` verifies that settings pass through correctly in the migration path, but it does not assert on the `mappings` field of the captured `CreateIndexClusterStateUpdateRequest` (which will be `null` since the test doesn't set mappings on the request). It also doesn't verify that the `indexName` in the update request equals `request.index()` (the migrated name with suffix). Adding these assertions would make the test more robust against regressions in the `buildManagedSystemIndexUpdateRequest` logic.
