#TF2WR, #D1G34, #EX616: The removal of `RocksDBLmqConsumerOffsetManager` and the simplification in `BrokerController` to always use `RocksDBConsumerOffsetManager` is a significant behavioral change. The deleted class provided LMQ-specific offset storage in a separate flat `ConcurrentHashMap<String, Long>` (keyed by `topic@group`). Now LMQ offsets are expected to flow through the base `RocksDBConsumerOffsetManager`'s offset table (which the tests show uses a nested `Map<String, Map<Integer, Long>>` structure). Please verify that:
1. `RocksDBConsumerOffsetManager` correctly handles LMQ-prefixed groups in both `queryOffset` and `commitOffset` without any special-casing that was previously in the deleted subclass.
2. Any previously persisted LMQ offset data (in the old flat `lmqOffsetTable` format) will not be silently lost or misread after this change. If there is a migration concern, a data migration step or compatibility read path should be considered.

#VVGBV, #9TXZY: `testQueryOffsetForLmqGroupWithoutExistingOffset` now asserts `assertNull(actualOffsets)` when querying an LMQ group with a non-existing topic. However, `testQueryOffsetForNonLmq` (the single-queue variant) expects `-1` for a missing offset. This inconsistency — one overload returns `null`, the other returns `-1` — is a potential NPE source for any caller that invokes the two-argument `queryOffset(group, topic)` and iterates the result without a null check. The old LMQ-specific implementation always returned a non-null (possibly empty) map. Consider either:
- Making `RocksDBConsumerOffsetManager.queryOffset(group, topic)` return an empty map instead of `null` for consistency with the single-queue variant, or
- Documenting the null contract clearly and auditing all call sites for null-safety.
