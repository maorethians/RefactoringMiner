#34ZCG, #RPHPJ, #AB819: The `SingleValueMatchQuery` class is moved from `org.elasticsearch.xpack.esql.querydsl.query` to `org.elasticsearch.compute.querydsl.query` and made public. This is a reasonable architectural move since it's now used by the compute module's `QueryList`. However, making the class and its constructor `public` broadens the API surface of the compute module. Consider whether a package-private or protected access level would suffice, or at minimum document the intended usage contract for external callers.

#R24M5: Two issues in `wrapSingleValueQuery`:
1. **Silent exception swallowing**: The `catch (IOException e)` block simply ignores the exception with a `TODO` comment. If `rewrite()` fails, the code falls through and adds the un-rewritten `SingleValueMatchQuery` as a `FILTER` clause in the `BooleanQuery`. This could produce incorrect query semantics or a runtime failure later during search. At minimum, log the exception; ideally, decide on a deterministic fallback (e.g., return the original `query` unmodified, or propagate the error).
2. **Missing `@Nullable` annotation**: The old abstract `getQuery` was annotated `@Nullable`. The new concrete `getQuery` can still return `null` (when `onlySingleValues` is false and `doGetQuery` returns null for a zero-value position), but the annotation was dropped. Callers relying on nullability contracts (e.g., static analysis tools) will lose that signal.

#C32BQ: The `makeTermsBlock` helper hardcodes the block builder capacity to `6`:
```java
try (BytesRefBlock.Builder termBuilder = blockFactory.newBytesRefBlockBuilder(6)) {
```
This is called from `testRandomMatchQueries` where `numPositions` can be up to 1000. The capacity hint should be `terms.size()` to correctly size the builder for the actual number of positions. While the builder may auto-resize, passing an incorrect initial capacity is misleading and could cause unnecessary reallocations.

#R24M5: In `getQuery`, when `onlySingleValues` is true and `valueCount == 1`, the code calls `doGetQuery` and then `wrapSingleValueQuery`. If a future subclass's `doGetQuery` returns `null` for a single-value position (e.g., a field type that can't produce a query), `wrapSingleValueQuery(null)` would be called, leading to a `NullPointerException` inside `BooleanQuery.Builder.add(null, ...)`. Consider adding a null guard before wrapping, or documenting the contract that `doGetQuery` must return non-null when `valueCount == 1`.
