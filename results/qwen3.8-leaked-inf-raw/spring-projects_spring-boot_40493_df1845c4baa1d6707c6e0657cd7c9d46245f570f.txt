#E5H09, #ZD4YK: The `escapeJson` method is applied to the value but not to the key. In the format string `"\"%s\":\"%s\"".formatted(entry.getKey(), escapeJson(entry.getValue()))`, if a user-supplied key contains a double-quote or backslash (e.g., `my"key`), the resulting JSON will be malformed. Consider applying `escapeJson` to the key as well:
```java
.map((entry) -> "\"%s\":\"%s\"".formatted(escapeJson(entry.getKey()), escapeJson(entry.getValue())))
```

#ZD4YK: The `escapeJson` method handles the six most common control characters but does not escape the remaining JSON-required control characters (U+0000–U+001F, excluding the six already handled). Per the JSON spec (RFC 8259 §2), all characters in that range must be escaped. A value containing, say, `\u0001` would produce invalid JSON. You could add a final pass that escapes any remaining control character via a `\uXXXX` sequence, or at minimum document the limitation.

#ZWNQY, #X5N3A: The updated tests cover newlines, tabs, and embedded quotes well, but there is no test case for a value containing a literal backslash (e.g., `"C:\\path\\to\\file"`). Since backslash escaping is the most critical case (it is the escape character itself and must be handled first to avoid double-escaping), a dedicated assertion for that scenario would strengthen the test coverage.
