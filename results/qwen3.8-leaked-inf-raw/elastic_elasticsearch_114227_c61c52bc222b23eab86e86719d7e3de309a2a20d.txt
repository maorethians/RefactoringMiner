#AX6AG: The assertion loop uses `oneOf("long", "float")` uniformly for every field. However, `field0` is only ever written as an integer (`0`) and `field16` is only ever written as a float (`0.1`), so their types are deterministic. Asserting the exact expected type for those two boundary fields (`"long"` for `field0`, `"float"` for `field16`) and keeping `oneOf` only for the genuinely conflicting `field1`–`field15` would make the test catch a regression where, say, the non-conflicting field's type is accidentally altered.

#YPH0Q, #8QC2Y: When `isConflictingDynamicMapping` returns `true`, neither branch of the `if / else if` executes, so the field is simply absent from `mergedMappers`. The Javadoc comment explains the intent (the document will be re-indexed against the existing mapping), which is good. One thing worth confirming: if the *existing* mapping in `mergeIntoMapper` was itself produced by a prior dynamic update in the same batch, the "winning" type is whichever document's mapping update was applied first. That is acceptable for a race, but it means the final type is non-deterministic across runs. The test already accounts for this with `oneOf`, so no code change is needed—just flagging it for anyone reading the fix later.
