#W1QVA: The alias resolution is only one level deep. Consider the test case in **#XAX1F**:
```
EVAL k = languages, k1 = k
STATS c = 3*COUNT() BY languages, k, k1, languages
```
The alias map becomes `{k → languages, k1 → k}`. Resolving `k1` yields `k` (an Attribute), not `languages`. The result is groupings `[languages, k]` rather than `[languages]`. This is correct *today* because all projections are preserved in the aggregates (so `k` remains a valid attribute), but it's a latent fragility: if a future refactor drops intermediate aliases from the aggregates, `k1` would point to a dangling attribute. A transitive resolution loop (or a `while` that keeps resolving until a fixed point) would make this robust:
```java
Attribute resolved = (Attribute) aliases.resolve(attr, attr);
while (aliases.containsKey(resolved)) {
    resolved = (Attribute) aliases.get(resolved);
}
replaced.add(resolved);
```
This is a minor concern given the current invariants, but worth a comment or assertion to document the assumption that intermediate aliases are always preserved in the aggregates.
