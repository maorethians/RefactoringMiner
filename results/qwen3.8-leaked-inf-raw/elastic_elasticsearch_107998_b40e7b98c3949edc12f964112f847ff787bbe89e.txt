#835X8: The test passes silently if `physicalPlan(query)` succeeds without throwing. With the randomized `randomInt(20)` inner loop, some runs may produce a query small enough to plan successfully, meaning the `catch` block (and its assertion) is never reached. Consider either:
- Asserting that the exception *is* thrown (e.g., `assertThatThrownBy(() -> physicalPlan(query)).isInstanceOf(ParsingException.class)`), or
- Increasing the fixed prefix (1900) so the query reliably exceeds the stack limit on all supported JVM configurations, making the catch path deterministic.
As written, the test only guards against a *regression* to an uncaught `StackOverflowError` when the SOE does occur, but a green build does not prove the new catch logic was actually validated.

#GF4WX: `forEachDown(Class<E>, Consumer)` and `forEachUp(Consumer)` are wrapped, but the single-argument `forEachDown(Consumer)` (the actual recursive workhorse) is not. If a caller invokes the single-argument overload directly (bypassing the two-argument variant), a `StackOverflowError` will propagate past `Node` and only be caught at the `RuleExecutor.execute()` level. The end result is still a `ParsingException`, so correctness is preserved, but the error message will reference the top-level plan rather than the specific subtree, and any code path that calls `forEachDown(Consumer)` outside of `RuleExecutor` will be unprotected. Consider wrapping the single-argument `forEachDown(Consumer)` as well for consistency.

#E64VP, #GF4WX: `plan.sourceText()` / `this.sourceText()` is interpolated into the exception message. In the very scenario this code guards against (a query large enough to overflow the stack), that string can be tens or hundreds of kilobytes. Embedding it verbatim in an exception message that may be logged, serialized into a REST response, or displayed in a UI could be expensive or unwieldy. Consider truncating (e.g., first 200 chars + `…`) or omitting the full text and relying on the request ID / query ID for correlation.
