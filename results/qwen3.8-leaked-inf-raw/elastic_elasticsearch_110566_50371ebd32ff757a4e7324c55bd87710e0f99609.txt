#MP3M3: The `runPhase` method lacks exception-safe resource cleanup for drivers. In the previous code (visible in the removed lines of #3PVXB), a `try/finally` block guaranteed `Releasables.close(drivers)` even if an exception was thrown during `executionPlanner.plan()` or `createDrivers()`. In the new code, `ActionListener.releaseAfter(listener, () -> Releasables.close(drivers))` is only set up just before `runToCompletion`. If an exception is thrown during plan creation or driver instantiation (e.g., in `executionPlanner.plan(...)` or `createDrivers(...)`), any drivers already added to the list will leak. Consider wrapping the driver-creation and execution block in a `try/finally` that closes `drivers`, or at minimum ensure the `releaseAfter` registration happens before any driver is created.

#3PVXB: The `EsqlSession` constructor is called with three consecutive `null` arguments:
```java
EsqlSession session = new EsqlSession(
    getTestName(),
    configuration,
    null,
    null,
    null,
    functionRegistry,
    ...
);
```
This is fragile and unreadable — it's impossible to tell which parameters are `null` without consulting the constructor signature. If the constructor signature changes (parameter reordering, new parameters inserted), this call will silently bind the wrong values or fail to compile in a confusing way. Consider using a builder pattern, named parameters (if the project supports them), or at minimum a comment identifying what each `null` represents. Additionally, if any code path within `executeAnalyzedPlan` → `logicalPlanToPhysicalPlan` → `optimizedPlan`/`physicalPlan`/`optimizedPhysicalPlan` ever touches one of those `null` fields, it will produce a hard-to-diagnose NPE.

#BPN90: The `optimizedPlan` method asserts `logicalPlan.analyzed()`, which is a good invariant check. However, `physicalPlan` and `optimizedPhysicalPlan` are also public and can be called independently with an un-analyzed plan. Since `physicalPlan` internally calls `optimizedPlan`, the assert will fire there — but the error message will point at `optimizedPlan` rather than the caller. Consider adding a brief Javadoc on the public methods stating the precondition (plan must be analyzed), so callers get a clear contract without relying on an assert that only fires in debug builds.
