#V560T: Two concerns in `ConsumingTestServer`:
1. **Busy-wait when no consumer is registered.** In `consumerThread()`, when `consumer` is `null` the `while (consumerRunning)` loop iterates with no blocking or sleep, spinning at full CPU until a consumer is set via `addMessageConsumer`. In the test flow the consumer is registered before the request is fired, but the window between `before()` (which starts the thread) and `addMessageConsumer` is non-trivial (cluster startup). A simple `Thread.sleep(50)` or, better, a `BlockingQueue`/`CountDownLatch` to wait for the consumer would avoid the spin.
2. **Consumer thread is never joined in `after()`.** `after()` sets `consumerRunning = false` and stops the server, but does not call `messageConsumerThread.join(...)`. The thread may still be inside `received.poll(1, SECONDS)` for up to a second after the test class finishes. This can cause a brief resource leak and, in CI with tight teardown, a `RuntimeException` from the interrupted poll leaking into the next test's output. A bounded `join` (e.g. `messageConsumerThread.join(2000)`) after flipping the flag would make teardown deterministic.

#X700T: The test logic is sound overall. One minor robustness note:
`finished.await(30, TimeUnit.SECONDS)` returns a `boolean` that is ignored. If the latch does not count down within 30 s the test proceeds to `assertThat(assertions, equalTo(Collections.emptySet()))` and fails with a somewhat opaque "expected empty set but was {…}" message. Capturing the return value and asserting it (or using `assertThat(finished.await(...), equalTo(true))` with a descriptive message) would make timeout failures easier to diagnose, since the remaining predicates' `toString()` output (e.g. `"trace_id is \"0af76519…\""`) would be the primary clue.
