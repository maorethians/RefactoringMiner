#GZWR9: In the new `MvExpand` branch of `PushDownAndCombineLimits`:
```java
var limitVal = (int) limitSource.fold();
```
`fold()` returns a `Number`. If the limit literal were ever a `Long` exceeding `Integer.MAX_VALUE`, this cast would silently overflow. While unlikely in practice for a `LIMIT` clause, using `Math.toIntExact(limitSource.fold())` would fail fast with a clear `ArithmeticException` rather than producing a wrong (negative) limit value that would then be stored on the `MvExpand` node.

#GZWR9: The guard condition:
```java
if (mvxLimit == null || mvxLimit < 0 || mvxLimit > limitVal) {
```
A negative `limit` value has no semantic meaning in this context. The rest of the codebase uses `null` to represent "no limit" (see the constructor in `LogicalPlanBuilder`, the deserialization path, and the `Mapper` check `mvExpand.limit() != null`). If a negative value could ever be set, it would be silently treated as "no limit" here but would pass the `!= null` check in the `Mapper` (#9JBSW) and produce a `LimitExec` with a negative limit. Consider either:
- Removing the `< 0` check and relying solely on `null` for "no limit", or
- Adding an `assert mvxLimit == null || mvxLimit >= 0` to make the invariant explicit.

#KV2FE: The `writeTo` method:
```java
assert limit == null;
```
This is a reasonable invariant (the limit is coordinator-only and handled via `LimitExec` in the physical plan). However, if a future code path accidentally sets a non-null limit and then serializes the plan, this would only be caught in debug builds. A `Preconditions.checkState(limit == null, ...)` or an `IllegalArgumentException` would provide a clearer failure in production. That said, if the project convention is to use bare `assert` for internal invariants, this is acceptable.

#DDRB6: The `whereMvExpand` test case in the CSV spec uses `where b > 3` (which filters out the row, producing an empty result), while the corresponding Java unit test in **#BX0QS** (`testWhereMvExpand`) uses `where b < 3` (which keeps the row and validates plan structure). Both are valid and test different aspects, but the mismatch in the filter direction between the two tests for the same issue (#102084) could be confusing to a future reader. Consider aligning them or adding a brief comment explaining why each uses a different condition.
