#PBPB9, #3MRYD: Changelog entries. Straightforward, no issues.

#WMMZG: Removes the now-unused `Strings` import. Correct, since `Strings.split` is no longer called.

#44FAG, #P67E1: CSV header parsing now escapes `::` before splitting on `:`, then unescapes afterward. This correctly handles column names like `client_ip::ip` in the header `client_ip::ip:ip`. The error message improvement (`Arrays.toString` instead of raw array) is a nice touch.
One minor observation: the `TYPECAST_SPACER` constant `__TYPECAST__` is a fixed sentinel string. If a column name ever legitimately contained `__TYPECAST__`, the unescape step would silently corrupt it. This is extremely unlikely in a test fixture, but a more robust approach (e.g., splitting on the *last* `:` rather than escaping) would avoid the sentinel entirely. Not a blocker, just a fragility note.

#R09F3, #90KBJ, #JPDJ0, #KTBVA, #NVZPZ, #WH2W0, #GKM49, #9N8CF: Test spec changes. The new test cases (`singleIndexIpStringStatsInline`, `multiIndexIpStringStatsInline2`, `multiIndexIpStringStatsInline3`, `multiIndexMultiColumnTypesRenameAndKeep`, `multiIndexMultiColumnTypesRenameAndDrop`) provide good coverage for inline type-casting in STATS BY, nested STATS, and multi-column type scenarios with KEEP/DROP.
In `multiIndexIpStringStatsInline2` (#GKM49), the SORT clause references `` `client_ip::ip` `` with backtick quoting, and the output header is `client_ip::ip:ip`. This exercises the escape/unescape path in the CSV parser, which is good.

#BP67S: Re-resolves aggregate expressions after MultiTypeEsField resolution. The logic builds a map of already-resolved attributes from the groupings, then uses `transformExpressionsOnly` to replace any remaining `UnresolvedAttribute` instances. The guard `agg.expressionsResolved() == false` ensures this only runs when needed.
One thing to verify: `Expressions.attribute(e)` returns null for non-attribute expressions (e.g., function calls wrapping an unresolved attribute). If a grouping were something like `UPPER(client_ip)` where `client_ip` is still unresolved, this re-resolution pass would not fix it. In practice, the groupings that need re-resolution here are direct attribute references produced by the MultiTypeEsField resolution, so this is likely fine, but it's worth being aware of the limitation.

#Q0728: The `resolveAttribute` helper is clean. Returning the original `UnresolvedAttribute` on zero matches (deferring the error) and producing a descriptive unresolved message on ambiguous matches follows the existing ES|QL error-deferral pattern.

#HNA1P, #5FSV9, #7711X: The `CombineProjections` fix correctly prevents multi-type field attributes from being used as replacement aliases, since they represent different types across indices and cannot substitute for each other. The `isMultiTypeFieldAttribute` check is precise: it requires both a `FieldAttribute` and a `MultiTypeEsField`, avoiding false positives on other attribute types.
