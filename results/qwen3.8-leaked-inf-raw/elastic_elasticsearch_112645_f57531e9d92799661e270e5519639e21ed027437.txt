#DXB5S, #65HSY, #BZ702: The `extractItem` method only handles `VALUE_STRING` (and `VALUE_NULL`) as value tokens, but `extractArray` calls `expectValueToken` which permits *all* value tokens (including `VALUE_NUMBER` and `VALUE_BOOLEAN`) to pass through. This means that if a routing path field contains an array of numbers or booleans (e.g., `{"b": [21, 42]}`), the parser will reach the `default` branch in `extractItem` and throw a `ParsingException`.
However, the test `testRoutingPathArraysInSource` (in `#BZ702`) explicitly includes `List.of(21, 42)` and `List.of(true)` and expects them to be hashed as `"21"`, `"42"`, `"true"`. The `createId` (flat-map) path handles this correctly via `value.toString()`, but the XContent-parsing path does not.
The `extractItem` switch should handle all value token types, for example:
```java
case VALUE_STRING:
case VALUE_NUMBER:
case VALUE_BOOLEAN:
    hashes.add(new NameAndHash(new BytesRef(path), hash(new BytesRef(source.text()))));
    source.nextToken();
    break;
```
Without this, the XContent-parsing path and the flat-map path will disagree for non-string array elements, and the test will fail (or the feature will be broken for numeric/boolean routing values in arrays).
