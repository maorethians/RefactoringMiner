#GP9DW: The `resolvedPipelineCache` is keyed solely by `indexRequest.index()`. The `computeIfAbsent` lambda captures the current iteration's `actionRequest` and `indexRequest`, but the cached `Pipelines` result is reused for any subsequent bulk item targeting the same index. This is correct today because `resolveStoredPipelines` is a pure function of the index name and cluster metadata. However, the method signature still accepts `originalRequest` and `indexRequest` (which could in principle carry request-specific state), creating an implicit coupling: if `resolvePipelinesFromMetadata` ever begins to produce different results for different requests targeting the same index, the cache would silently return a stale result. Consider either (a) documenting this assumption on the cache, or (b) keying the cache on a tuple that includes any request-specific inputs that actually affect the result.

#WH2ZQ: In `resolveStoredPipelines`, when `isRolloverOnWrite` is true the `originalRequest` and `epochMillis` parameters are unused. This is a reasonable API trade-off for a unified entry point, but it does mean callers (like the cache lambda in #GP9DW) always compute `System.currentTimeMillis()` even when it will be discarded. Minor, but worth being aware of if this method is called in a hot path with many rollover-on-write data streams.
