#1XZHE, #8BDEF: The test in `160_nested_fields.yml` verifies index creation and a search that returns 0 hits, but it does not exercise the primary motivation for the `postParse` change: that deleting a parent document also removes its nested documents. Without a test that indexes a document with nested fields, deletes it by ID, and confirms the nested documents are gone, a regression in the `StringField` back-fill (e.g., wrong field name, wrong encoding) would go undetected. Consider adding a step that deletes the indexed document and then verifies a search on the nested field returns no hits.

#1XZHE: The existing search uses a plain `bool.must` with `term` queries on nested paths, which (as the 0-hit result shows) does not correlate fields within a single nested object. A `nested` query that *should* match (e.g., `courses.name: "Linear Algebra"` AND `courses.credits: 3` → 1 hit) would confirm that nested field indexing actually works in TSDB mode, not just that the index can be created.

#FM122: ```java
} else if (indexSettings().getMode() == IndexMode.TIME_SERIES) {
    // ...comment...
} else {
    throw new IllegalStateException(...);
}
```
The empty block is valid but slightly unusual. An alternative that some teams prefer is to invert the guard:
```java
if (idField == null && indexSettings().getMode() != IndexMode.TIME_SERIES) {
    throw new IllegalStateException("The root document of a nested document should have an _id field");
}
if (idField != null) {
    doc.add(new StringField(IdFieldMapper.NAME, idField.binaryValue(), Field.Store.NO));
}
```
This avoids the empty branch and keeps the "happy path" (adding the field) as the primary flow. This is a style suggestion, not a bug.

#8BDEF: ```java
assert context.id() != null;
for (LuceneDocument doc : context.nonRootDocuments()) {
    doc.add(new StringField(IdFieldMapper.NAME, Uid.encodeId(context.id()), Field.Store.NO));
}
```
Java `assert` is disabled by default in production. If `context.id()` were ever null at this point, `Uid.encodeId(null)` would throw a `NullPointerException` with a less actionable message. A defensive `Objects.requireNonNull(context.id(), "…")` would give a clearer failure in all environments. This is low-risk since `postParse` is only reached after ID generation, but the cost of the guard is negligible.
