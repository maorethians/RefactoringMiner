#WEE4R, #HEJ1K, #088Y1, #7SDG8, #V5TZD, #ZP0MS, #00D4K, #QTTWR, #574CJ: The overall design is sound: plain `long` counters guarded by the arena's `lock()`/`unlock()`, `default` methods in the interface for backward compatibility, and `max(val, 0)` in `numActiveChunks()` consistent with the existing `numActiveHugeAllocations()` pattern.
However, there is a potential correctness concern with where `pooledChunkAllocations` is incremented. In #HEJ1K the counter is only bumped inside `allocateNormal`. In Netty's `PoolArena`, small-size allocations (`allocateSmall`) can also trigger the creation of a new `PoolChunk` when the existing chunks are exhausted. If that path does not route through `allocateNormal` (or a shared helper that contains this increment), then chunks allocated to serve small allocations will never be counted, making `numChunkAllocations()` and `numActiveChunks()` under-report. Please verify that every code path that creates a new `PoolChunk` increments this counter, or move the increment into the shared chunk-creation helper.

#6P6CR: The test only exercises the normal-allocation path (one chunk allocated, none deallocated). Consider adding a case that:
1. Allocates and then frees enough memory to trigger `destroyChunk = true`, asserting `numChunkDeallocations() == 1` and `numActiveChunks() == 0`.
2. If the concern above applies, a small-allocation scenario that forces a new chunk to be created, asserting the counter is still incremented.
