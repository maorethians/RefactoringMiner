#WFNS6, #64F0X, #BDA3Z: The removal of the `retainedSlice()`, `retainedSlice(int, int)`, and `retainedDuplicate()` overrides from `AdaptiveByteBuf` means these operations will now fall through to the default implementations in `AbstractReferenceCountedByteBuf`, which allocate non-recyclable `UnpooledSlicedByteBuf`/`UnpooledDuplicatedByteBuf` instances. Previously, when `handle != null`, the pooled (recyclable) variants were used. Since `handle` is now always non-null (always created via `Magazine.newBuffer()`), this is a clear performance regression for any workload that calls `retainedSlice()` or `retainedDuplicate()` on adaptive-pooled buffers — those wrapper objects will now be allocated and GC'd on every call instead of being recycled. If this is intentional (to simplify the code), consider documenting the trade-off; otherwise, the pooled overrides should be restored unconditionally (without the `handle == null` branch).

#8S9DH: In the new `tryAllocate(int size, int sizeBucket, int maxCapacity)` method, if the inner `allocate(size, sizeBucket, maxCapacity, buf)` call throws an exception, the buffer obtained from `newBuffer()` is neither returned to `bufferQueue` nor released. The previous code had a `try/finally` block in the outer `allocate` method that called `buf.release()` on failure to prevent a leak. Consider wrapping the allocation in a try/catch (or try/finally) that returns the buffer to the queue (or releases it) if the inner `allocate` throws, to avoid leaking a recycled buffer back into the GC.

#SFVAT: The `MAGAZINE_BUFFER_QUEUE_CAPACITY` default of `4 * 1024` (4096) is annotated with `// TODO: Choose a good default.`. Each magazine holds up to 4096 `AdaptiveByteBuf` wrapper objects. With multiple magazines (one per thread for non-shared, plus shared ones), this can accumulate to a large number of retained objects. While each object is small, the total retained memory and the queue's internal array allocation (`FixedMpscQueue` pre-allocates its backing array) should be validated. Consider whether a smaller default (e.g., 256 or 1024) would be more appropriate, or at least remove the TODO before merging so the value is a deliberate choice.

#281A4, #NGFZ6: The refactored `allocate` method now returns `null` on failure instead of using a boolean + in/out buffer parameter. This is cleaner, but note that in the `for` loop over magazines (diff #NGFZ6), each failed `tryAllocate` call that acquires and releases the write lock still incurs the lock overhead. More importantly, if `tryAllocate` returns `null` because the write lock could not be acquired, the buffer was never created — that's fine. But if it returns `null` for any other reason (currently there is none), the caller would not know whether a buffer was partially initialized. The current implementation is safe, but the contract of "null means no buffer was created" should be documented on the method to prevent future misuse.
