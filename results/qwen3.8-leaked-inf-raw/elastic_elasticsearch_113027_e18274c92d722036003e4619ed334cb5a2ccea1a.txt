#VA5KB: The import of `joptsimple.internal.Strings` is a concern. The `joptsimple.internal` package is explicitly an internal implementation detail of the joptsimple library and is not part of its stable public API. It can be renamed, removed, or changed in behavior without notice. The only usage is `Strings.join(path, ".")` in `getCurrentPath`, which is directly available in the standard library as `String.join(".", path)`. Prefer the JDK built-in to avoid a fragile dependency on a third-party internal package.

#AG7AS: The `parseDocForMissingValues` method implements a manual token-walking loop to locate target fields in a second pass. Two observations:
1. When a target field is found and its value is a complex structure (object or array), `XContentDataHelper.encodeToken(parser)` presumably consumes the entire subtree, leaving the parser positioned at the corresponding `END_OBJECT`/`END_ARRAY`. The subsequent `currentToken = parser.nextToken()` then correctly advances past it. This is correct but non-obvious; a brief comment noting that `encodeToken` leaves the parser at the closing token would help future maintainers avoid "fixing" what looks like a double-advance.
2. The method silently drops any target field that is not found in the source (it simply remains in the `fields` map and is never added to `result`). This is the intended behavior for genuinely absent fields, but it means the caller cannot distinguish "field was absent from source" from "field was found but had a null value." If that distinction ever matters (e.g., for error reporting), it would need to be surfaced here.

#8QPH9: In `addIgnoredFieldMissingValue`, the `else` branch relies on `assert` to guard against a null `ignoredFieldWithNoSource`. In production (where assertions are disabled), a null would be silently added to `ignoredFieldsMissingValues` and would later cause a `NullPointerException` in `parseDocForMissingValues` when `field.name()` is called. A defensive `Objects.requireNonNull` or an explicit `if (ignoredFieldWithNoSource == null) throw ...` would make the failure mode clearer in production.

#WRJYB: The old `cloneSubContext` / `cloneSubContextWithParser` methods performed `builder.copyCurrentStructure(parser)`, which both serialized the subtree *and* advanced the original parser past it. The new `cloneSubContextWithRecordedSource` simply wraps the same parser in a new context without advancing it. This is correct for the new design (the parser continues from its current position), but it means the sub-context and the parent context now share the same underlying parser. Any code that assumes the sub-context's parser is independent (e.g., that it can be positioned differently) would break. The `recordedSource` flag mitigates double-recording, but it's worth confirming no downstream code relies on the old isolation guarantee.

#K5JK1, #8Z1NG, #6V1VA: These three call sites follow the same new pattern: record a missing-value entry, then parse via `cloneSubContextWithRecordedSource`. The logic is consistent. One minor note: in `#K5JK1`, the `NameValue` is constructed with `context.parent().fullPath().lastIndexOf(context.parent().leafName())` for the parent offset. This `lastIndexOf` approach works for simple names but could produce an incorrect offset if the leaf name appears earlier in the path (e.g., a field named `path` inside an object also named `path`). This is pre-existing logic (not introduced by this diff), but it's worth verifying it's correct for all mapper configurations.
