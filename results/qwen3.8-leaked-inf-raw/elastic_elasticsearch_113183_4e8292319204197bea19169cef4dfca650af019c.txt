#0KXAQ: Two bugs in `BytesRefBucketedSort`:
1. In `checkInvariant`, the heap-mode loop checks `values.get(rootIndex)` instead of `values.get(l)`:
```java
for (long l = rootIndex; l < common.endIndex(rootIndex); l++) {
    if (values.get(rootIndex) == null) {  // should be values.get(l)
        throw new AssertionError("values missing in heap mode");
    }
}
```
This only verifies the root element is non-null (repeatedly) rather than checking every slot in the bucket.
2. In `merge`, the invariant check uses the wrong bucket:
```java
other.checkInvariant(bucket);  // should be other.checkInvariant(otherBucket)
```
This checks the invariant for the *target* bucket on the *source* object, rather than the *source* bucket that is actually being read from.

#0KXAQ: In `toBlock`, the general (size > 1) path stores `BytesRef` views obtained from `BreakingBytesRefBuilder.bytesRefView()` into `bucketValues[i]`, but then immediately closes the builder via try-with-resources:
```java
for (int i = 0; i < size; i++) {
    try (BreakingBytesRefBuilder bytes = values.get(start + i)) {
        bucketValues[i] = bytes.bytesRefView();
    }
    values.set(start + i, null);
}
```
If `close()` releases the underlying byte buffer (which is the typical contract for a `Releasable` backed by a circuit breaker), the `BytesRef` references in `bucketValues` become dangling. The subsequent `Arrays.sort` and `builder.appendBytesRef(bucketValues[i])` would then read freed memory. Compare with the `size == 1` path, which correctly calls `builder.appendBytesRef(...)` *inside* the try block (copying the data before close). The fix would be to copy the bytes into a new `BytesRef` before the builder is closed, e.g. `bucketValues[i] = new BytesRef(bytes.bytesRefView().bytes, 0, bytes.bytesRefView().length)`.

#P7QGY: The javadoc for `rootIndex` contains a broken `@link` reference:

```java
/**

```
