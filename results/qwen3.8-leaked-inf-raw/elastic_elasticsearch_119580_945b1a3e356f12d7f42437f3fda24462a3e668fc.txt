#7W49T, #NHPJK: The removal of the validation block in `planLookupJoin` is a behavioral change worth calling out. The old code extracted the *concrete* index name from `indexNameWithModes` (the key of the single entry) and validated that exactly one concrete index existed and was in LOOKUP mode. The new code simply uses `localSourceExec.indexName()`, which is the *logical* index name (potentially a pattern like `lookup-*`). If a LOOKUP index pattern resolves to a single concrete index, these would differ. The `LookupFromIndexOperator` now receives the logical name rather than the resolved concrete name. If that operator expects a concrete index to open, this could fail at runtime. Please confirm that either (a) LOOKUP indices are always concrete names (never patterns), or (b) the downstream operator handles index patterns correctly.

#H8D80, #B7KCY: When serializing `EsQueryExec` and `EsSourceExec` to a node on the older transport version, the code constructs `new EsIndex(indexName, Map.of(), Map.of())` — passing empty maps for both `mapping` and `indexNameWithModes`. In contrast, `EsRelation`'s backward-compatible path passes the actual `indexNameWithModes` (`new EsIndex(indexName, Map.of(), indexNameWithModes)`). If any code path on the older receiving node calls `index().indexNameWithModes()` on a physical plan node (e.g., to derive concrete indices for permission checks or index resolution), it will now see an empty set during a rolling upgrade. Consider whether the physical plan nodes should also carry `indexNameWithModes` for the backward-compatible write path, or document that this is safe because the older node never reads that field from physical plan nodes.
