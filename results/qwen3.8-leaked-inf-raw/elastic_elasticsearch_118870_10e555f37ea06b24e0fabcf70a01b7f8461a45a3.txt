#XBEKX: The `ReplaceCaseWithInsensitiveMatch` rule only checks `bc.left() instanceof ChangeCase`. If a user writes `"GEORGI" == TO_UPPER(first_name)` (ChangeCase on the right side), the rule will not fire. While a commutativity normalization rule elsewhere in the optimizer may handle this, it's worth confirming that such normalization exists for `BinaryComparison` before this rule runs. Without it, the optimization is silently skipped for the right-operand form.

#GY09Y: The `matchesCase` method uses `Character.getType(cp)` which is locale-independent, while `process` uses locale-sensitive `toUpperCase(locale)`/`toLowerCase(locale)`. For most locales this is fine, but for locales with special case mappings (e.g., Turkish where `'i'.toUpperCase()` → `'İ'`), a literal like `"I"` would pass `UPPER.matchesCase("I")` (no lowercase), yet `TO_UPPER("i")` in Turkish produces `"İ"` ≠ `"I"`. The resulting `InsensitiveEquals(field, "I")` would then need to correctly handle this locale-specific mapping. This is a very narrow edge case, but worth a comment or assertion documenting the assumption that `InsensitiveEquals` handles locale-aware case folding consistently with `toUpperCase(locale)`.

#B1F9E: The test method names `testReplaceCaseWithInsensitiveMatchUpperTrue` and `testReplaceCaseWithInsensitiveMatchUpperFalse` are ambiguous — "True/False" could refer to the `matchesCase` result, the truthiness of the final condition, or whether the optimization fires. In this case, both tests use `"VALÜe"` (which contains lowercase), so `matchesCase` returns `false` for both. The "True" test actually verifies the condition is always true (full scan), while "False" verifies it's always false (empty result). Consider renaming to something like `...UpperAlwaysTrue` / `...UpperAlwaysFalse` to make the intent clearer.
