#ZM3Q6, #2R48V: The refactoring of `planConcreteIndices` changes behavior subtly. The old code traversed the **entire** fragment (both sides of any logical `Join` within a fragment) to collect concrete indices:
```java
f.fragment().forEachUp(EsRelation.class, r -> indices.addAll(r.index().concreteIndices()));
```
The new `forEachFromRelation` skips the right side of any `Join` node *within* a fragment:
```java
node -> node instanceof Join join ? List.of(join.left()) : node.children()
```
For `planOriginalIndices` this is correct (it should only return FROM-clause indices). However, for `planConcreteIndices`, if a logical `Join` ever appears inside a fragment (rather than being represented as a top-level `LookupJoinExec`), the right-side index would now be silently excluded from the concrete index set. If such a plan shape is impossible in the current planner, this is fine, but it would be worth a brief comment in `forEachFromRelation` clarifying that the inner `Join` skip is intentional for both callers, or splitting the logic if `planConcreteIndices` should include both sides.

#MM1ME: The new test `lookupIndexInFromRepeatedRowBug` uses a lookup index (`languages_lookup_non_unique_key`) in the `FROM` clause and then performs a `LOOKUP JOIN` on another lookup index. The expected output shows 4 rows all with `language_name = English` but different `country` values (including `null`). This is a good regression test.
