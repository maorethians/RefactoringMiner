#Z9VGJ, #X6X2G: **Testability regression: `SleepFunction` replaced by hardcoded `Thread.sleep`**
In `#Z9VGJ`, the injectable `threadSleep.apply(interval.millis())` is replaced with a direct `Thread.sleep(interval.millis())`. Previously, tests could inject a no-op `SleepFunction` to bypass the sleep entirely (as the old `detect(Writer)` public method did internally, but tests calling `innerDetect` directly could pass a no-op). Now every test that exercises `innerDetect` (see `#X6X2G`) will actually sleep for `interval.millis()`. If the test interval is non-trivial, this adds real wall-clock delay to the test suite. Consider keeping a `SleepFunction` (or a `TimeProvider`/`Clock` abstraction) as a parameter so tests can still short-circuit the wait, or at minimum ensure the test interval is set to 0/1 ms.

#T6MD6, #X6X2G: **No test coverage for the new `logLocalCurrentThreads` method**
`#T6MD6` introduces `logLocalCurrentThreads`, which is the primary new public API in this chapter. The only test change (`#X6X2G`) is a mechanical signature update to an existing test. There is no test that:
- Verifies the per-thread log splitting behavior (header as one entry, each thread as a subsequent entry).
- Confirms that `threadElementsSnapshotCount(1)` results in exactly one stack capture (no repeated sampling).
- Exercises the `catch (Exception e)` path.
A unit test that calls `logLocalCurrentThreads` with a mock logger and asserts the number and content of log calls would guard against regressions in the splitting logic.

#JW1MT, #Z9VGJ, #J3TFS: **`onNextThread` invoked inside the `synchronized (mutex)` block**
In `#JW1MT`, `innerDetect` is called within `synchronized (mutex)`. The new `onNextThread` callbacks (in `#Z9VGJ` and `#J3TFS`) perform logging I/O (in the `logLocalCurrentThreads` use case) while the mutex is held. If the log appender is slow (e.g., writing to a remote sink or a blocked file), this extends the critical section and can block other threads that need the `HotThreads` instance. While the existing code already writes to the `Writer` inside the lock, the new callback adds an additional I/O sink (the logger) that the caller controls. Consider documenting this constraint or invoking `onNextThread` outside the synchronized region (e.g., by collecting per-thread strings and flushing after the lock is released).
