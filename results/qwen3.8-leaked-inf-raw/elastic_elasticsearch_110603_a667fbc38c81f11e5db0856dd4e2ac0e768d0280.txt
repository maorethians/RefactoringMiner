#XD8JM: The multiple-values flag is created as a `StoredField` (which writes into Lucene's stored-fields section), while the timestamp value is created as a `LongField` with `Field.Store.NO`. Both are only used as in-memory markers looked up via `getByKey` during `postParse` — neither needs to be persisted. Using a non-stored field for the flag (e.g., `new LongField(key, 0L, Field.Store.NO)`) would be consistent with the value field and avoid any unnecessary stored-field overhead in the `ParsedDocument`.

#XD8JM, #HT7Q1, #0VYRT: There is an inconsistency in how the document is accessed: `DateFieldMapper.indexValue()` and `DataStreamTimestampFieldMapper.postParse()` use `context.doc()`, while `TsidExtractingIdFieldMapper.createField()` uses `context.rootDoc()`. For a top-level field like `@timestamp` these resolve to the same object, but mixing the two accessors across the three call-sites that read/write the same keys makes it harder to reason about correctness if the parsing context ever changes. Picking one convention (preferably `rootDoc()`, since the old code used it and it is the more explicit choice) would reduce ambiguity.
