#7XJAN: The change from returning an unresolved attribute with a descriptive message to throwing `IllegalStateException` has two concerns:
1. **Lost user-facing guidance**: The previous message included "to disambiguate use quotes or qualifiers", which is actionable advice for the user. The new message drops this hint, making it harder for users to resolve the ambiguity.
2. **Exception type**: `IllegalStateException` is conventionally reserved for internal state violations (e.g., calling a method before initialization). For a user-input validation error encountered during analysis, a domain-specific exception (or at minimum an `EsqlException`/`AnalysisException`) would be more appropriate and would be handled more predictably by the error-reporting layer. If the caller of `maybeResolveAgainstList` does not explicitly catch `IllegalStateException`, this will surface as an unexpected internal error rather than a clean query error.

#YG05S: The double cast `(List<Alias>) (List) mergeOutputExpressions(...)` with `@SuppressWarnings("unchecked")` is a code smell that hides a type-safety gap. If `mergeOutputExpressions` is a shared utility, consider overloading it or providing a typed variant that returns `List<Alias>` directly, so the caller doesn't need to suppress the warning. At minimum, a brief comment explaining *why* the raw cast is necessary (e.g., the method's generic signature is `List<?>`) would help future readers.

#37DXE: `unionFieldAttributes` is now an instance field on `ResolveUnionTypes`. If this rule instance is ever shared across concurrent analyses (e.g., cached in a rule list that is reused), the mutable instance field introduces a data race. If the framework guarantees one instance per analysis, this is fine, but it would be safer to either (a) document that assumption explicitly, or (b) keep the list as a local variable passed into `doRule` via a parameter, avoiding the shared mutable state entirely.
