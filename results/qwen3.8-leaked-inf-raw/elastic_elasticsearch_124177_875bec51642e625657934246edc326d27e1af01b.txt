#1BBF7, #4637K, #ZXBW4, #QKNV7: The regex patterns `REPLACE_LP` and `REPLACE_LEFT_BRACKET` use `([\s,]*)` (zero or more) as the left boundary, which means the pattern can match `LP` as a trailing substring of a longer token name. For example, if a token named `SOME_LP` appeared at the end of an error message, the regex would match the `LP` portion and incorrectly replace it with `'('`. While this is unlikely in the ES|QL grammar, a safer left boundary would be `([\s,])` (one or more) combined with an alternative for start-of-string, or using `\b` word boundaries:
```java
private final Pattern REPLACE_LP = Pattern.compile("\\bLP\\b");
private final Pattern REPLACE_LEFT_BRACKET = Pattern.compile("\\bOPENING_BRACKET\\b");
```
This would eliminate the risk without changing the replacement logic.

#QKNV7: The tests only cover the case where the token name appears at the very end of the error message (followed by `$`). It would be valuable to add a case where the token appears mid-message, e.g. `expecting LP or OPENING_BRACKET`, to verify the `AFTER_REGEX` correctly handles the comma/space separator and that both replacements work in a single message. This would also exercise the interaction between the two `replaceAll` calls (the second pattern running on the output of the first).
