#QNWQ5: The `findLookupIndexNames` method's third walk captures the right-side `EsRelation` indices of **all** `Join` nodes within any `FragmentExec`, not just LOOKUP JOINs:
```java
physicalPlan.forEachDown(
    FragmentExec.class,
    fragmentExec -> fragmentExec.fragment()
        .forEachDown(
            Join.class,
            join -> join.right().forEachDown(EsRelation.class, esRelation -> lookupIndexNames.add(esRelation.index().name()))
        )
);
```
If a non-lookup join (e.g., a regular hash join) ever appears in a fragment with an `EsRelation` on its right side, its index would be incorrectly excluded from the concrete index set, causing the "expected concrete indices with data node plan but got empty" assertion to fire. Consider filtering by join type (e.g., checking that the `Join` is specifically a LOOKUP JOIN) to avoid this.

#JD2JD: The `validateTypes` method performs a strict string equality check between `fieldType.typeName()` and `inputDataType.typeName()`. While the TODO acknowledges this is incomplete, the error message could be more actionable for users. Currently it reads:

LOOKUP JOIN match and input types are incompatible: match[integer], input[keyword]
