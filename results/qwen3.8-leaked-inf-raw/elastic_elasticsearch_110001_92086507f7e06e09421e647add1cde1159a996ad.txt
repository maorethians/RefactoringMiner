#NBB41, #Z6FEX, #TG7Z6, #NX55E, #21T64, #PR14J, #4FDGD, #2JBF8, #45287, #X266R, #DZV78, #WEZZQ, #3ZA90, #R9YM8, #V41TP, #YXVK7: The core logic change replaces a strict bidirectional equality check (`containsInAnyOrder`) with a one-directional subset check (`set.containsAll(...)`). This is a correctness regression in the test:
- **Original**: `assertThat(resultList, containsInAnyOrder(values))` — fails if the result is missing expected values **or** contains extra unexpected values.
- **New**: `if (false == set.containsAll(Arrays.asList(values)))` — only fails if the result is missing expected values. If the result contains *extra* values (e.g., duplicates that weren't deduplicated, or spurious entries), `containsAll` returns `true` and the assertion is silently skipped.
For example, if the aggregation incorrectly returns `[1.0, 1.0, 2.0]` instead of `[1.0, 2.0]`, the `TreeSet` collapses it to `{1.0, 2.0}` and `containsAll` passes — masking the duplicate bug. This is especially concerning given that the `@AwaitsFix` annotation is being removed from `ValuesIntAggregatorFunctionTests` (diff #45287), suggesting the test is being made more lenient to paper over an underlying issue rather than verifying the fix.
If the intent is to tolerate duplicates in the result, a clearer approach would be to assert `set.containsAll(expected)` **and** `expectedSet.containsAll(set)` (i.e., set equality), or simply assert `set.size() == expectedSet.size()` alongside `containsAll`. As written, the test can no longer detect over-production of values.

#Z6FEX, #PR14J, #NX55E, #2JBF8, #X266R, #WEZZQ, #R9YM8, #YXVK7: Using `TreeSet` for `Double` and `Float` result values changes the equality semantics from `equals()` to `compareTo()`. Specifically, `Double.compare(-0.0, 0.0) != 0` while `Double.equals(-0.0, 0.0)` is `true`. This means the `TreeSet` will retain both `-0.0` and `0.0` as distinct elements, whereas the original `containsInAnyOrder` (which uses `equals()`) would treat them as the same. While this is an unlikely edge case in practice, it is a subtle behavioral difference worth being aware of, particularly for the `ValuesFloat` and `ValuesDouble` test classes.

#Z6FEX, #PR14J, #NX55E, #2JBF8, #X266R, #WEZZQ, #R9YM8, #YXVK7: Minor style note: the Yoda condition `if (false == set.containsAll(...))` is less idiomatic in Java than `if (!set.containsAll(...))`. The negated form is clearer and avoids the unusual reversed operand order.
