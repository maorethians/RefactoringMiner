#FY57Z, #ET4M5: The `Runnable` calls `threadPool.getThreadContext().putHeader(...)` inside `execute()`. This is correct because `getThreadContext()` resolves to the current thread's context at call time (the master thread). However, be aware that if the framework wraps `execute()` in a `ThreadContext.StoredContext` that is later restored, the header you put will be discarded after `execute()` returns. If the deprecation-tracking logic reads the header *after* `execute()` completes (e.g., in a `finally` block or a subsequent listener callback on a different thread), the header will no longer be present. Confirm that the consumer of the header reads it within the `execute()` call stack.

#ET4M5: Moving `Priority.IMMEDIATE` from the call site into the constructor is a reasonable simplification since there is only one caller. Just note that if a future caller needs a different priority, the parameter will need to be re-introduced. This is a minor maintainability trade-off and is acceptable given the current single-use context.

#FY57Z: The guard `Strings.hasText(xOpaqueId)` ensures the lambda is only created when the header is non-blank, and the `threadContextUpdater != null` check in `execute()` is the correct defensive pattern. No issue here.
