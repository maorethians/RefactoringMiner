#1WZXR, #E6SD1, #C66PC: The change broadens the caught exception from `ResourceAlreadyExistsException` to its parent `ElasticsearchException` in both threads of `testDuplicateDownsampleRequest`, and then un-mutes the test. This is a reasonable pragmatic fix if the actual exception thrown at runtime is a different `ElasticsearchException` subclass (or a wrapped variant) rather than exactly `ResourceAlreadyExistsException`.
However, catching the base `ElasticsearchException` makes the test less precise: it will now pass even if the duplicate request fails for an unrelated reason (e.g., a permission error, a validation failure, or a transient cluster issue). A slightly more robust approach would be to catch `ElasticsearchException` but assert on the exception type or message inside the catch block, e.g.:
```java
} catch (ElasticsearchException e) {
    // optionally: assert that e is a ResourceAlreadyExistsException or carries the expected reason
    firstFailed.set(true);
}
```
This preserves the flexibility needed to un-mute the test while still guarding against the test passing for the wrong reason. If the broader catch is intentional because the server-side behavior has changed to throw a different exception type, a brief comment explaining which exception is now expected would help future readers.
