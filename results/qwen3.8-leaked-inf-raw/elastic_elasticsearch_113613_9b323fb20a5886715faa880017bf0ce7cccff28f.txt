#Y5J3A: The `IntStack.push()` and `IntStack.pop()` now call `stack.resize(...)` unconditionally on every operation. In the original code, growth was only triggered when `size >= stack.length`. Since `IntStack` is used in AVL tree rotations (a hot path called on every insert/delete), the per-operation overhead of a virtual `resize` call plus a circuit breaker atomic adjustment (via `MemoryTrackingTDigestArrays.adjustBreaker`) may be measurable. Consider whether the breaker adjustment for the stack's logical size truly needs to happen on every push/pop, or whether it could be batched (e.g., adjust only on `close()` and on actual capacity growth).

#4BGZP, #S5G82, #QBX46, #A5E9N: In `ComparisonTests`, `releaseData()` is called at the end of each test method. If any assertion in the middle of the test fails, `releaseData()` is never reached, leaking the circuit breaker allocation. A `try/finally` (or try-with-resources) pattern would ensure cleanup regardless of test outcome:
```java
public void testRandomDenseDistribution() {
    loadData(() -> random().nextDouble());
    try {
        // ... assertions ...
    } finally {
        releaseData();
    }
}
```

#M54JY: In the `read` method, the `TDigestState` is constructed inside the try block. If `in.readString()` succeeds (TDigestState is created) but `in.readVLong()` throws, the catch block rolls back `SHALLOW_SIZE` and rethrows. This is correct. However, if the code *after* the try/catch (reading `n` centroids) throws, the `TDigestState` object (with its breaker-adjusted SHALLOW_SIZE) is left dangling — the caller must handle cleanup. This is the existing contract (caller closes on failure), but it's worth ensuring all callers of `TDigestState.read` wrap it in a try/catch that closes the state on exception.

#N9APZ: `InternalIntAvlTree` is a non-static inner class of `AVLGroupTree`, so it holds an implicit reference to the enclosing instance. Combined with `AVLGroupTree.tree` pointing back to it, this creates a reference cycle. This is harmless for GC (the cycle is collected when no external reference exists), but it does mean the `IntAVLTree` base class's `SHALLOW_SIZE` (computed via `RamUsageEstimator.shallowSizeOfInstance(IntAVLTree.class)`) does not account for the synthetic `this$0` field that the JVM adds for inner classes. The actual shallow size of `InternalIntAvlTree` is slightly larger than `IntAVLTree.SHALLOW_SIZE`. This is a minor inaccuracy in the breaker accounting.
