#FPGEB, #JG551: The depth counter is incremented *before* the `try` block, so if the limit check throws, the counter is left incremented and never decremented (the `finally` is never reached). In practice this is harmless because a `ParsingException` terminates the parse and the builder instance is discarded, but it's a subtle invariant break. A slightly more robust structure would be:
```java
expressionDepth++;
try {
    if (expressionDepth > MAX_EXPRESSION_DEPTH) {
        throw new ParsingException(...);
    }
    return typedParsing(this, ctx, Expression.class);
} finally {
    expressionDepth--;
}
```
This guarantees the counter is always restored, even if the exception is somehow caught by an outer handler that reuses the builder.

#FPGEB: The error message references `ctx.getParent().getText()`. In ANTLR parse trees the root node's parent is `null`. While an `expression` context should always have a parent in a valid ESQL statement, a defensive null-check (or using `ctx.getText()` directly) would avoid a potential `NullPointerException` masking the intended `ParsingException`.

#FPGEB, #JG551: The error messages embed the full text of the offending expression or query (`ctx.getParent().getText()` / `ctx.getText()`). At the 500-level depth limit, this text can be several kilobytes long. Consider truncating (e.g., first 100–200 characters with an ellipsis) to keep error messages and log lines manageable, especially since these messages may be surfaced to end users or aggregated in monitoring systems.
