#T2ADD: The new `computeOutput` static method only handles `LEFT` joins and throws `UnsupportedOperationException` for all other join types (`RIGHT`, `FULL`, `INNER`). The previous `computeOutput()` instance method supported all four types. If `Join` is instantiated with a non-LEFT `JoinType` anywhere else in the codebase (e.g., in other exec plans or future features), this will be a hard runtime failure. Consider either:
- Keeping the other join-type branches (even if simplified), or
- Adding a clear comment/assertion at the `Join` construction sites that only LEFT is supported, so the constraint is documented at the point of use rather than discovered at runtime.

#3MWTG: The old code handled `localRelation == null` by falling back to `Expressions.asAttributes(matchFields)`. The new code throws `IllegalStateException`. If any code path calls `Lookup.output()` before the analysis phase has resolved the local relation (e.g., during plan serialization, explain, or a partial analysis pass), this will now throw where it previously returned a best-effort output. Please confirm that `output()` is never invoked before `localRelation` is set, or restore a graceful fallback.

#2SZKN, #KBFFD, #KZ9S2, #27126: The deserialization constructors all use the pattern `(List<Attribute>) (List) in.readNamedWriteableCollectionAsList(NamedExpression.class)`. This is an unchecked downcast: the wire format still declares `NamedExpression`, so a non-`Attribute` `NamedExpression` (e.g., a `Literal` or `UnresolvedNamedExpression`) would pass the cast silently and only fail later with a `ClassCastException` at the first `.name()` or `Attribute`-specific call. Since the PR's intent is to guarantee these are always `Attributes`, consider:
- Updating the serialization to write/read as `Attribute` directly (a new `readAttributeCollectionAsList` or similar), or
- Adding a runtime validation loop after the cast that throws a descriptive `IllegalStateException` if any element is not an `Attribute`, so the failure is immediate and clear.

#NYPKW: The added guard `a instanceof ReferenceAttribute == false` in `makeReference` is a good fix to prevent double-wrapping. However, note that this changes behavior for any existing caller that previously relied on `makeReference` to normalize all attributes into `ReferenceAttribute` instances (including ones that were already `ReferenceAttribute`). If downstream code does an `instanceof ReferenceAttribute` check and expects a *fresh* instance (e.g., for identity-based deduplication), the now-passthrough behavior could subtly change results. Please verify no caller depends on the old "always wrap" semantics.
