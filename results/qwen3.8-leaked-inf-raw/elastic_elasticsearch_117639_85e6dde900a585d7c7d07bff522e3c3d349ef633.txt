#KXKDZ, #HR0YN, #GASMM, #3YKAK: The capability rename from `JOIN_LOOKUP` to `JOIN_LOOKUP_V2` is consistent across all four sites (enum definition, multi-cluster IT import/skip, and CSV test guard). No issues here.

#GMBH8: The rewritten `computeOutput` changes the column-ordering semantics for non-match fields that appear on both sides. Previously, a right-side field sharing a name with a left-side field (but not being a match field) would replace the left field *in place* (preserving the left field's position). Now, such a field is appended after all primary-side fields. For LOOKUP JOIN this is unlikely to matter in practice (lookup tables typically contain only the key plus the desired lookup columns), but for general `Join` plans it is a subtle ordering shift. Since the capability is bumped to V2 this is an intentional breaking change, but it may be worth a one-line note in the release notes or the V2 capability description so downstream consumers are aware.

#GR3BZ: The resolved `JoinConfig` now carries the core join type (`LEFT`) directly instead of wrapping it in a `UsingJoinType`. This is a simplification and makes the `LEFT.equals(joinType)` check in `computeOutput` (#GMBH8) work correctly. However, if any other code path still inspects `config.type() instanceof UsingJoinType` after resolution (e.g., in the physical planner or in serialization/deserialization), it will no longer match. Worth confirming that no such check remains in the codebase outside this chapter.

#MSS2X: `surrogate()` now calls `output()`, which delegates to `computeOutput()` and in turn calls `config.matchFields().stream()`. The Javadoc added in #CRTB5 warns that `output()` "must be called only on resolved plans." If `surrogate()` can ever be invoked on a LookupJoin whose config still holds unresolved references (e.g., during a partial planning pass), this would throw or produce incorrect results. If the call-site guarantees resolution, this is fine; otherwise a guard or assertion would be prudent.

#1WKV7, #F01AN: Removing the `BinaryPlan.computeReferences()` override (which called `output()`) and relying on the base `QueryPlan.computeReferences()` (which calls `expressions()`) is the right call, especially given the new Javadoc in #F01AN explicitly forbidding `output()` on unresolved plans. No issues.

One minor observation: in `basicOnTheDataNode` (#RS65K), the `WHERE emp_no >= 10091 AND emp_no < 10094` filter is applied *after* the `LOOKUP JOIN`. This means the join is executed against all employees and then filtered. If the intent is to verify that the join works correctly with a bounded input, placing the `WHERE` before the `LOOKUP JOIN` would be a stronger test (it would confirm the join doesn't depend on unbounded input). The current placement is still valid, just noting the distinction.
