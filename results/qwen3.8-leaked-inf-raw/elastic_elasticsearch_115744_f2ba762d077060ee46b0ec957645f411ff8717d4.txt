This removes coverage for the grouped aggregation path when doc values *are* available (i.e., the `airports` data source with `useDocValues = true`). The non-grouped test (`testSpatialTypesAndStatsUseDocValues`) still covers both cases, but the grouped variant with doc values is no longer exercised. Consider restoring the `true` case or adding a comment explaining why it was dropped.

#T8AH5: In `SearchContextStats`, the `min` and `max` methods perform I/O (iterating leaf readers, calling `PointValues.getMinPackedValue`/`getMaxPackedValue`), store the result in the cache, but then unconditionally return `null` (the actual `return stat.min;` is commented out). This means every call pays the cost of scanning all leaf segments for a value that is discarded. Since this is a new class (extracted from the old `SearchStats`), consider either:
- Returning the computed value (removing the `// return stat.min;` comment and the `return null;`), or
- Skipping the computation entirely (just `return null;` without the `doWithContexts` call) until the TODO is resolved.
As-is, it does unnecessary work on every invocation.

#S1D0K: In `LucenePushdownPredicates.DEFAULT`, the `isIndexed` method delegates to `attr.field().isAggregatable()`, with a TODO questioning whether this is semantically correct (since `isAggregatable` typically means "has doc values" rather than "is indexed"). This is the fallback used when no `SearchStats` is available (e.g., in `PlannerUtils.detectFilter` for the `@timestamp` filter). If a field is indexed but has no doc values, `isAggregatable()` would return false, and the spatial pushdown would be incorrectly skipped. Consider whether the DEFAULT should be more permissive (e.g., always return `true` for `isIndexed`) to avoid missing valid pushdown opportunities, or document more clearly that this is a conservative approximation.
