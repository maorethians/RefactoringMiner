#JD2JD: The error message concatenates `inputDataType` (a `DataType` enum) directly into the string, which will invoke `toString()`. However, the comparison logic uses `inputDataType.typeName()`. If `DataType.toString()` returns the enum constant name (e.g., `INTEGER`) while `typeName()` returns the wire name (e.g., `integer`), the error message will be inconsistent with the actual type name shown for the match field. Consider using `inputDataType.typeName()` in the message for consistency:
```java
"LOOKUP JOIN match and input types are incompatible: match[" + fieldType.typeName() + "], input[" + inputDataType.typeName() + "]"
```

#31VBP: The second `forEachDown` block adds the right-side index of *any* `Join` node found under a `FragmentExec` to the exclusion set, without checking whether it is specifically a lookup join. In the current architecture this is safe (only lookup joins are planned on data nodes), but if a non-lookup join were ever planned on a data node, its right-side index would be incorrectly excluded from concrete indices. A guard checking the join type (or the index mode) would make this more robust:
```java
join -> join.right().forEachDown(EsRelation.class, esRelation -> {
    if (esRelation.index().indexNameWithModes().get(esRelation.index().name()) == IndexMode.LOOKUP) {
        lookupIndexNames.add(esRelation.index().name());
    }
})
```
