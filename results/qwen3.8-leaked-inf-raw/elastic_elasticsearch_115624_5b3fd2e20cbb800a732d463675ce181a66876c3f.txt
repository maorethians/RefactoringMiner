#GZWR9: In the new `MvExpand` branch, `limitSource.fold()` is cast to `int` without a null check:
```java
var limitVal = (int) limitSource.fold();
```
If the limit expression is not a foldable literal (e.g., a `Parameter` that hasn't been resolved, or any non-`Literal` expression), `fold()` returns `null` and the unboxing cast will throw a `NullPointerException`. While in practice the optimizer pipeline likely guarantees the limit is a resolved literal by the time this rule fires, a defensive guard (or at minimum an `assert`) would make the failure mode clearer if an invariant is ever violated upstream. For example:
```java
Object folded = limitSource.fold();
if (folded == null) {
    return limit; // cannot push a non-constant limit past MvExpand
}
var limitVal = (int) folded;
```
This also aligns with the existing pattern in the same rule where non-foldable limits are simply left in place.
