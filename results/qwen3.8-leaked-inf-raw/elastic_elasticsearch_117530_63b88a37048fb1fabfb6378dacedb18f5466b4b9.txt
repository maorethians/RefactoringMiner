#JMX3V, #TWJKA: Inconsistent overflow handling: `EndpointStats.add` uses `Math.addExact` (throws `ArithmeticException` on overflow), but `StatsCounter.addTo` in the Azure `RequestMetricsRecorder` uses plain `+` (silently wraps around). The S3 path (`#K428D`) goes through `EndpointStats.add` and will throw, while the Azure non-stateless path will silently produce incorrect values on overflow. For consistency, `StatsCounter.addTo` should also use `Math.addExact`, or `EndpointStats.add` should be relaxed.

#FQ5PW: `assertAllRequestCountsAreZero` only asserts `requests() == 0` but not `operations() == 0`. While logically `operations <= requests` always holds (so `requests == 0` implies `operations == 0`), asserting both fields makes the test self-documenting and guards against a future implementation bug where the invariant could be violated.

#1HSA7, #Q7GQA: The REST API serialization in `RepositoryStatsSnapshot.toXContent` only emits `operations`, making the API response lossy with respect to `requests`. The test in `#Q7GQA` compensates by assuming `operations == requests` when parsing the response. This is a deliberate BWC choice, but it means the new `requests` dimension is invisible to REST API consumers. Consider whether a new field (e.g., `request_counts` as an object with both fields) should be added for the new transport version, or at minimum document this limitation in the `EndpointStats` Javadoc.
