#T0EK8: The pushdown logic is sound, but the cast `var limitVal = (int) limitSource.fold();` will throw a `NullPointerException` if `fold()` returns `null` (e.g., if the limit expression is a non-foldable parameter in some edge-case plan). Consider adding a guard or at minimum a comment documenting the invariant that `limit.limit()` is always a foldable `Literal` at this point in the optimizer pipeline. If the invariant is guaranteed by the rule's preconditions, a brief comment would help future readers.
Additionally, the condition `mvxLimit < 0` is interesting — a negative limit is semantically "no limit" in some contexts. If that's the intended sentinel, a short comment would clarify the intent versus a simple `null` check.

#H13AS: The guard `mvExpand.limit() >= 0` auto-unboxes the `Integer`. Since you already checked `!= null` in the same `&&` chain, this is safe. However, note that a limit of `0` will produce a `LimitExec` that emits zero rows. If `limit 0` is a valid user query, this is correct; if it's not expected to reach the planner, you might want to treat `0` the same as `null` (skip the wrap) to avoid a no-op `LimitExec` in the physical plan. Minor, but worth a conscious decision.

#KV2FE, #SYMCP: The design of not serializing the `limit` field (assert-null on write, hardcode-null on read) is clean and avoids wire-format changes. The assertion in `writeTo` is a good safety net. One suggestion: the comment in the deserialization constructor (`// we only need this on the coordinator`) is helpful, but consider also noting *why* it's safe to drop — i.e., that the `Mapper` will re-attach a `LimitExec` on the coordinator before the plan is shipped, so data nodes never see a bare `MvExpand` that relied on the embedded limit. This prevents a future refactor from accidentally removing the `Mapper` wrap without noticing the serialization gap.
