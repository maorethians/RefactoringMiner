#W6EDY, #WKQEE, #XV2FX, #03W6C: The `ignoreLons` method uses a direct floating-point equality check (`v == 180`). While this is acceptable when the values are known to be exactly `180.0` (e.g., hardcoded test fixtures), it will silently fail to match values that are mathematically 180 but differ by the last ULP due to prior arithmetic (e.g., `360.0 / 2.0` is fine, but `180.0 + 0.0 - 0.0` or a round-trip through a different representation is not guaranteed). If the lons in the test data are always literal `180.0` constants, this is fine. If they can arrive via computation, consider a small epsilon comparison or documenting the assumption.
Additionally, the method is a coarse gate: if *any* longitude in the array is 180, the entire array is flagged for ignoring. If the intent is to skip only the offending point(s) rather than the whole geometry, the current logic would over-filter. If the intent is indeed to bail out of the test case entirely when the antimeridian is involved, the name `ignoreLons` is slightly misleading — something like `containsAntimeridian` or `hasLonAt180` would make the "all-or-nothing" semantics clearer to a future reader.
