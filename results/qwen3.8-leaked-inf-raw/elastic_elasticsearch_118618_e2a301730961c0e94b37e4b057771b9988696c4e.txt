#6W5WQ, #W5QTJ: The change replaces `ElasticsearchTimeoutException` with `ElasticsearchStatusException` carrying `RestStatus.REQUEST_TIMEOUT`. This is a reasonable refactor, but it is a **type-level breaking change** for any caller that specifically catches `ElasticsearchTimeoutException` (e.g., `catch (ElasticsearchTimeoutException e)` or `instanceof` checks). Since `ElasticsearchStatusException` is not a subclass of `ElasticsearchTimeoutException`, such code will silently stop catching this failure. If this exception propagates beyond the inference plugin's internal sender into user-facing or cross-plugin code paths, please verify no downstream handler relies on the old type. If the scope is strictly internal, the change is fine.

#4PJZT, #ESEX4, #6C1FA, #P7YW9: The new assertion `assertThat(thrownException.status().getStatus(), is(408))` uses a magic number. Consider using `RestStatus.REQUEST_TIMEOUT.getStatus()` instead so the test stays in sync if the constant ever changes and the intent is immediately readable:
```java
assertThat(thrownException.status().getStatus(), is(RestStatus.REQUEST_TIMEOUT.getStatus()));
```
This is a minor maintainability nit, not a correctness issue.
