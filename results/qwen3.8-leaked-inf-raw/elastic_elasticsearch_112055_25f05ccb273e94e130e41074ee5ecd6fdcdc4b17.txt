#KMSHF: The `unsignedLongMedianOf` method uses `Arrays.sort(values, 0, count)` which sorts by **signed** long ordering. However, the values stored in the array are unsigned long bit patterns. When values span the signed/unsigned boundary (e.g., some values ≥ 2⁶³ and some < 2⁶³), the sort order is incorrect, producing a wrong median.
For example, with unsigned values `[0x7FFFFFFFFFFFFFFF, 0x8000000000000000, 0x8000000000000001]`:
- Correct unsigned sort: `[0x7FFF..., 0x8000..., 0x8000...01]` → median = `0x8000000000000000`
- Signed sort: `[0x8000..., 0x8000...01, 0x7FFF...]` → median = `0x8000000000000001` (wrong)
The same issue exists in `finishUnsignedLong` (which calls `unsignedLongMedianOf` on the deviations array) and in `ascendingUnsignedLong`. The fix would be to sort using `Long.compareUnsigned` or to flip the sign bit before sorting (e.g., `values[i] ^= Long.MIN_VALUE` before sort, then flip back).

#HS5AJ: The "Custom double overflow" test case uses values `[-Double.MAX_VALUE, Double.MAX_VALUE/4, Double.MAX_VALUE/4]`. The median is `Double.MAX_VALUE/4`, and the deviation for `-Double.MAX_VALUE` is `Double.MAX_VALUE/4 - (-Double.MAX_VALUE)` which overflows to `Infinity`. This will trigger the `assert Double.isFinite(doubles.values[i])` in `MvMedianAbsoluteDeviation.finish(Doubles)` when assertions are enabled (as they typically are in test runs), causing the test to fail with an `AssertionError` rather than validating the expected `0.` result. The test data or the assert needs to be reconciled.
