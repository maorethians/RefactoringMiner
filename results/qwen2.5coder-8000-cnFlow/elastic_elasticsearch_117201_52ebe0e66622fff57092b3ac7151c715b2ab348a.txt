#2ZE6G, #12DMQ: The test cases cover a specific scenario where nested fields and fields with the same name exist in different contexts. However, there is no explicit check for the case where both indices are queried without any filtering or sorting on the nested field. It would be beneficial to add a test case that verifies the behavior when querying both indices without specifying `process.parent.command_line` or `Responses.process.pid`.

#2ZE6G, #12DMQ: In both test methods, the error messages checked in assertions are quite specific ("Unknown column [Responses.process.pid]"). While this is fine for now, it might be more robust to check for a substring that indicates an unknown column error rather than the exact message. This way, if the error message changes slightly in future versions, the tests won't break.

This assumption should be clearly documented or handled more gracefully if the capability is not enabled. Consider adding a comment explaining why this assumption is made and what happens if it's not true.

#NG9G0, #040NK: The removal of the `allNested` method and the associated logic to filter out nested fields directly in the `mergedMappings` method is a significant change. The new approach uses the `filters("-nested")` call on the `FieldCapabilitiesRequest`. This change assumes that the Elasticsearch server will correctly interpret this filter to exclude nested fields, which may not be immediately clear or well-documented behavior. It's important to ensure that this filter works as expected and is tested thoroughly.
