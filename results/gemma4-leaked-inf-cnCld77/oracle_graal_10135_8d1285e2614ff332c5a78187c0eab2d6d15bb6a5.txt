#RVHE9: The logic for flushing the compilation queue when `CompilationActivityMode` is `STOP_COMPILATION` iterates over all queued targets and cancels them if the queue size is greater than one. While this could be expensive if the queue is very large, it effectively happens only once per "Stop" event (as subsequent calls will find a nearly empty queue), making the performance impact acceptable given that this occurs during an exceptional system state.
The use of `System.currentTimeMillis()` for calculating the retry delay is acceptable here as the interval (default 1000ms) is large enough that minor clock drifts or jumps are unlikely to significantly impact the functionality.

#RKHFW: The use of a `MethodHandle` in a static block to access `HotSpotJVMCIRuntime.getCompilationActivityMode()` is a clean way to handle backward compatibility with older JVMCI runtimes that may not provide this method, ensuring the system defaults gracefully to `RUN_COMPILATION`.

#RVHE9: The logic for allowing exactly one target to remain in the queue during `STOP_COMPILATION` mode is well-documented via comments, explaining its purpose in triggering HotSpot code cache sweeps. This prevents confusion regarding why a full flush isn't performed when `size == 1`.
