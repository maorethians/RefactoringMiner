#ZQ1R4, #YFJJN: The `limit` field added to `MvExpand` is not serialized in `writeTo` and is explicitly set to `null` when read from `StreamInput`. Furthermore, the assertion `assert limit == null;` in `writeTo` will cause a crash (when assertions are enabled) if any optimized plan containing an `MvExpand` with a limit is serialized. If this field is intended only for use on the coordinator during physical mapping, it should be clearly documented why it's omitted from serialization and why the assertion exists given that the optimizer actively populates this field.

#9T1V4, #RWZPP: There is a logical redundancy in how limits are handled when pushed past `MvExpand`. The rule in `PushDownAndCombineLimits` transforms the plan into a structure where an `MvExpand` (with an internal limit) is the parent of a `Limit` node: `MvExpand(limit=N) -> Limit(N) -> Child`. 
When this is mapped to a physical plan in `Mapper.java`, the `Limit` node becomes a `LimitExec`, and the `MvExpand` (because it has a limit) is wrapped in another `LimitExec`. This results in two identical `LimitExec` operators wrapping the same operation: `LimitExec(N, MvExpandExec(LimitExec(N, ...)))`. Since `MvExpandExec` does not appear to use the limit internally for optimization (it's only used by the mapper to wrap it), one of these limits is redundant.

#9T1V4: The cast `(int) limitSource.fold()` assumes that the result of `fold()` is always an `Integer`. If a `Limit` node can be constructed with a non-constant expression that cannot be folded into an integer, this will throw a `ClassCastException`. It is safer to check if the result is an instance of `Integer` before casting.
