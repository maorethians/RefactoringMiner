#Y0M91: The logic in `unsignedLongAsLongExact` is inverted. A signed long representing an unsigned value is representable as a positive signed long if and only if it is non-negative (`l >= 0`). The current implementation throws an `ArithmeticException` when the value is representable and attempts to return a value (via `twosComplement`) when it should throw an overflow exception.

#1260F: In `unsignedDifference`, calling `NumericUtils.unsignedLongSubtractExact(a, b)` when `a >= 0` and `b < 0` will trigger an `ArithmeticException`. This is because `unsignedLongSubtractExact` performs an unsigned comparison (`x < y`), and since $a$ (positive) is numerically smaller than $b$ (negative interpreted as a large unsigned value), the check fails. However, the absolute difference between any two signed longs always fits within an unsigned long range $[0, 2^{64}-1)$ and should not result in an overflow exception here.
