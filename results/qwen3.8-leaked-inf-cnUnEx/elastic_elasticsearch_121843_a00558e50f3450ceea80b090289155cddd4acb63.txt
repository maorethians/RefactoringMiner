#9NZM8: The new `getEsqlQueryTask` method conflates two distinct failure modes into a single `null` return: (1) the task genuinely doesn't exist, and (2) the user lacks access to the task. In the old code (visible in `#G6KR5`'s removed lines), access denial explicitly threw `ResourceNotFoundException`. Now both cases fall through to `getResultsAction.execute(...)`. If `TransportEsqlAsyncGetResultsAction` does not independently enforce the same access check, this is a privilege-escalation path: an unauthorized user could trigger the stop flow and still receive results via the get-results action. Even if the downstream action does check security, the error semantics change from a clear 404 to whatever the get-results action returns, which may leak information about task existence.
Additionally, the `IOException` is silently swallowed with no logging. At minimum this should be logged at `debug` or `warn` level so that transient I/O failures during task lookup are diagnosable rather than indistinguishable from a missing task.

#G6KR5: The new flow calls `exchangeService.finishSessionEarly(...)` and, in its completion callback, either registers a completion listener on the task or immediately calls `getResultsAction.execute(...)`. There is no timeout or fallback if the task never reaches a completed state (e.g., the query thread is stuck). The old code had the same theoretical risk with `EsqlRefCountingListener`, but the old code at least had a 1-second `waitForCompletionTimeout` in the null-listener fallback path. Consider whether a timeout or a `try/finally` guard is warranted here to avoid a permanently hung client request.
Also, `markAsPartial()` is now called *before* `finishSessionEarly`. In the old code it was called inside the `EsqlRefCountingListener` block, after the listener was registered. If `finishSessionEarly` throws synchronously (e.g., `removeExchangeSourceHandler` returns null and the listener is invoked on a different thread), the partial flag is already set but the session was never actually finished. This is a minor ordering concern but worth confirming that `markAsPartial` is idempotent and safe to set even when the subsequent finish fails.

#HSVG2: The simplification of `execute` is clean. However, note that the old code registered the listener in `asyncListeners` *before* calling `innerExecute`. This meant that even if `innerExecute` threw synchronously, the listener was already registered and could be cleaned up. In the new code, if `innerExecute` throws, the `listener` is never completed (since `ActionListener.run` wraps the call, it should route to `onFailure` — please confirm that `ActionListener.run` handles synchronous exceptions from the lambda). If it does, this is fine; if not, the caller's listener would be silently dropped.

#M4JC0: The logger is added but only used in `#G6KR5` at `debug` level. This is fine, but given the security-related null-return in `#9NZM8`, a `debug` log for the "no task present" path is the only trace of what happened. Consider whether `warn` is more appropriate for the access-denied case (which is currently indistinguishable from not-found).
