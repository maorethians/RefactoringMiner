#BBARN: In `readMappingFile`, when a key from `typeMapping` is not found in the mapping's `properties` node, it is silently ignored (the `if (propertiesNode.has(key))` guard simply skips it). Since this is test infrastructure, a typo in a type-mapping key (e.g., `"clinet_ip"` instead of `"client_ip"`) would be silently dropped, and the test would run against the unmodified mapping — likely producing a confusing failure far from the root cause. Consider logging a warning or throwing an `IllegalArgumentException` when a type-mapping key is absent from the mapping, so misconfigurations surface immediately.

#5W338: The schema-parsing logic was changed from `indexOf(':')` (split on the *first* colon only) to `split(":")` (split on *every* colon, taking `header[1]` as the type). For all current ESQL type names this is equivalent, but it is a narrower contract: if a type name ever contained a colon, the old code would preserve it in `typeName` while the new code would truncate it to the segment between the first and second colon. Using `split(":", 2)` would preserve the original "split-on-first-colon" semantics at no cost and make the intent explicit.
