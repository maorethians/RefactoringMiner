#XRJ1W, #0P2CT: Calling `addIgnoredFieldMissingValue(null)` is a code smell that obscures intent and creates a latent NPE risk. In `#0P2CT`, the `else` branch (when `arrayFieldMissingValue == null`) does `assert ignoredFieldWithNoSource != null` — in production builds without assertions, a `null` would be added to `ignoredFieldsMissingValues`, causing a downstream NPE in `parseDocForMissingValues` when it calls `field.name()`.
While the current call site in `#XRJ1W` is safe (because `maybeCloneForArray` guarantees `arrayFieldMissingValue` is set), the API contract is fragile. Consider either:
- Splitting into two methods: `addIgnoredFieldMissingValue(NameValue)` for the non-array case and `markArraySourceForRecording()` for the array case, or
- Making the parameter non-nullable and having the array case use a separate no-arg method.
This would make the two distinct use-cases explicit and eliminate the null-passing pattern.

#P314X: The updated test is significantly weaker than the original. The old test verified that the cloned parser actually contained the same data (`assertEquals(data, dataInParser(tuple.v1().parser()))`). The new test only checks the `recordedSource` flag:
```java
assertFalse(context.getRecordedSource());
DocumentParserContext parser = XContentDataHelper.cloneSubContextWithRecordedSource(context);
assertTrue(parser.getRecordedSource());
```
Since `cloneSubContextWithRecordedSource` now simply wraps the *same* parser (no serialization/re-parsing), it would be valuable to at least verify that the returned context's parser is still positioned correctly and can read the expected token. For example, asserting `parser.parser().currentToken()` or reading the next token and checking its value would guard against regressions in the `switchParser` wiring.

#GWVYK: The `parseDocForMissingValues` method is the most complex piece in this chapter. The nested while-loop with `path`/`fieldName` bookkeeping is correct but difficult to follow. A few observations:
1. The inner `while (currentToken != FIELD_NAME)` loop handles START_OBJECT/START_ARRAY/END_* tokens but silently falls through for value tokens (VALUE_NUMBER, VALUE_STRING, etc.) — it just advances. This works, but a reader might wonder if a value token is being "lost." A brief comment clarifying that scalar values are simply skipped when they don't match a target field would help.
2. The early `break` when `fields.isEmpty()` exits the outer loop, but the parser is left mid-stream. This is fine since the parser is discarded afterward, but it's worth noting that the method does not consume the full document.
3. Consider extracting the "decide whether to descend or skip" logic (the `parentNames.contains(...)` check) into a small helper to reduce the nesting depth of the inner loop.
