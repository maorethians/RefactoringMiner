#K0H38: Looking at the two diffs in this chapter:
**#K0H38** – The condition change removes the `Resolvables.resolved(groupings)` guard and instead filters groupings to only resolved ones inside the loop. This is a correct and well-motivated improvement: previously, if *any* grouping was unresolved, the entire aggregate-resolution step was skipped, even when some groupings *were* resolved and could help resolve aggregate expressions. Now partial resolution is possible.
One minor point: `groupings.stream().filter(Expression::resolved).toList()` allocates a new intermediate list on every call. Since this is in an analysis-phase loop (not a hot data path), the cost is negligible, but a simple `if (e.resolved() == false) continue;` inside the existing `for` loop would avoid the allocation and the stream overhead entirely:
```java
for (Expression e : groupings) {
    if (e.resolved() == false) {
        continue;
    }
    Attribute attr = Expressions.attribute(e);
    if (attr != null) {
        resolved.put(attr, attr);
    }
}
```
This is a style/performance nit, not a correctness issue.

#9YT9Y: **#9YT9Y** – The test covers a good matrix of scenarios (resolved/unresolved columns in both the aggregate argument and the grouping, plus a `BUCKET` case that exercises a type-inference error alongside the unknown-column error). Using `randomFrom` over the aggregate function list is a reasonable way to keep per-run cost low while still rotating coverage across runs.
One observation: the test asserts on error *messages* but does not directly assert that the resolution step was *attempted* (i.e., that a resolvable aggregate in the presence of an unresolved grouping is still resolved). For example, `STATS avg(emp_no) by foobar` will report the `foobar` error regardless of whether the resolution block ran or was skipped, because `emp_no` is already resolved. A test where the aggregate *depends* on a resolved grouping to resolve (e.g., `STATS avg(x) by x = emp_no, foobar`) would more directly exercise the new code path where the block now runs despite an unresolved grouping being present. The existing case `STATS agg(x) by foobar, x = emp_no` partially covers this, but the assertion only checks the error text, not whether `x` was successfully resolved in the aggregate.
