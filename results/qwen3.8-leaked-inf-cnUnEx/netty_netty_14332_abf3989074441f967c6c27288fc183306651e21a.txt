#Q1ZJ4, #5NTRZ: `bufferQueue.offer(self)` returns `false` when the fixed-capacity queue is full, and the return value is ignored. In that case the `AdaptiveByteBuf` is silently dropped: its reference count is never decremented and the object (along with any backing `Chunk` it still references) is leaked. Under a burst of concurrent releases this can happen. Consider at minimum logging a warning, or falling back to `self.release()` when `offer` fails:
```java
@Override
public void recycle(AdaptiveByteBuf self) {
    if (!bufferQueue.offer(self)) {
        // Queue full – avoid leaking the buffer.
        self.release();
    }
}
```

#5BH18: If `allocate(size, sizeBucket, maxCapacity, buf)` throws (e.g. `OutOfMemoryError` from `newChunkAllocation`, or an unexpected `RuntimeException` from `readInitInto`), the buffer created by `newBuffer()` is never released or returned to the queue. The old code guarded against this with a `try/finally` in the caller (see the removed block in #8J6MS). A `try/catch` (or `try/finally`) around the `allocate` call that releases the buffer on failure would restore that safety net:
```java
AdaptiveByteBuf buf = newBuffer();
try {
    allocate(size, sizeBucket, maxCapacity, buf);
    return buf;
} catch (Throwable t) {
    buf.release();
    throw t;
}
```
This applies to both the lock-free and locked branches.

Before this ships, it would be good to either validate the value under realistic load (e.g. measure the peak number of in-flight buffers per magazine) or add a brief comment explaining the reasoning behind 4096 so a future reader doesn't treat it as arbitrary.
