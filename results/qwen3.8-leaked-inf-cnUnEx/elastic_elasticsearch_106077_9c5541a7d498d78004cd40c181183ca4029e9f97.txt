#MZNTS: `Mapping#withFieldsBudget` hardcodes `MergeReason.MAPPING_RECOVERY`. If this method is ever called from a non-recovery code path (e.g., a test helper or a future caller that sets a fields budget outside of recovery), the reason would be semantically incorrect. Consider whether the caller should supply the reason instead, or add a brief comment documenting that this method is exclusively for the recovery path.

#ACVMT: `DocumentParserContext#createDynamicMapperBuilderContext` uses `MergeReason.MAPPING_UPDATE` as the reason for building mappers during dynamic mapping discovery at index time. This is a distinct scenario from a user-initiated mapping update. If any mapper's `build` or `merge` logic branches on the reason, it will see `MAPPING_UPDATE` here even though the trigger is a document write with dynamic mapping. Consider whether a dedicated reason (e.g., `MAPPING_DYNAMIC`) would be more accurate, or at minimum add a comment explaining why `MAPPING_UPDATE` is the intended choice in this context.
