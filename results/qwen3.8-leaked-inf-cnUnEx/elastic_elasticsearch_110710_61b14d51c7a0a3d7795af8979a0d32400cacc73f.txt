#W4C82: In `handleResponse`, when `response.hasFailures()` is true, the code schedules a retry for the failed nodes and then falls through to submit the successful results to the task queue. This is correct ("carry on and read what we can"), but note that `scheduleRetry` will re-query *all* failed nodes via `queryNodesFeatures`, which re-adds them to `pendingNodes`. If the same node fails repeatedly, this creates an unbounded retry loop with a fixed 30-second interval and no backoff. Given the `@UpdateForV9` annotation indicating this class is temporary and will be removed in v9, this is acceptable, but a simple exponential backoff or a max-retry cap (with a final error log) would reduce log noise and transport load in a pathological scenario (e.g., a node that is permanently unreachable but still in the cluster state).
