#ST374, #E73EK, #FWMNB, #M688R, #D5C3D: **Wire protocol / backward-compatibility concern:** Moving `encoder` from `HighlightBuilder.doWriteTo` (end of the stream) into `AbstractHighlighterBuilder.writeTo` (between `numOfFragments` and `highlighterType`) changes the on-the-wire serialization order. During a rolling upgrade, a node running the old code will interpret the `encoder` slot as `highlighterType` (and vice-versa), corrupting the deserialized state. I don't see a `TransportVersions` gate around the new `encoder` read/write positions. If this is intentional, please confirm that a new transport version is introduced and that both the write and read paths are version-gated so that mixed-version clusters can interoperate safely.

#WQXSS: **Parent-to-child constant reference:** `AbstractHighlighterBuilder.tagsSchema(...)` now references `HighlightBuilder.DEFAULT_PRE_TAGS`, `HighlightBuilder.DEFAULT_POST_TAGS`, `HighlightBuilder.DEFAULT_STYLED_PRE_TAG`, and `HighlightBuilder.DEFAULT_STYLED_POST_TAGS`. This inverts the expected dependency direction (parent depending on a concrete child). Consider moving these four constants up to `AbstractHighlighterBuilder` (or a shared constants holder) so the parent is self-contained and any future subclass doesn't need to know about `HighlightBuilder`'s internals.
