#WPNDY: The `toXContent` method uses `bytesIngested > 0 && bytesProduced > 0` as the guard condition, meaning **neither** field is emitted if either value is zero. This is problematic for the drop/failure scenario: a pipeline that ingested 1000 bytes but produced 0 (all documents dropped) will have `bytesIngested > 0` internally, yet the API response will show no byte stats at all. This is inconsistent with the `Stats` class, which always emits all fields.
Consider emitting each field independently:
```java
if (bytesIngested > 0) {
    builder.field("ingested_in_bytes", bytesIngested);
}
if (bytesProduced > 0) {
    builder.field("produced_in_bytes", bytesProduced);
}
```
This way, a pipeline that ingested bytes but dropped all documents still reports `ingested_in_bytes`, which is meaningful operational data.

#WC4B5: The version id `8_656_00_0` is valid Java (equals 8 656 000) but the underscore grouping is unconventional compared to the typical three-digit grouping (e.g. `8_656_000`). This is a minor readability nit, but worth aligning with the project's existing convention for transport version ids to avoid confusion when scanning the list.
