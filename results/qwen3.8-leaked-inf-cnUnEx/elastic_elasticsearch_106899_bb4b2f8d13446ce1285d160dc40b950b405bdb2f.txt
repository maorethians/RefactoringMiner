#2X5B0: The `process` method's early-exit check `str.length < substr.length` compares byte lengths. While this is a valid fast-path (a shorter byte sequence cannot contain a longer one), it's worth noting that for multi-byte UTF-8 characters this is a looser check than a code-point comparison. This is fine as an optimization, but the comment or naming could make the intent clearer.

#2X5B0, #DBEQM: The test coverage has a notable gap: all test cases (both the parameterized suppliers and the explicit `test*` methods) use `start = 0`. The following paths in `Locate.process` / `indexStart` are never exercised:
- `start > 1` (e.g., `process("a tiger", "ti", 2)` should return 3, since searching from position 2 still finds "ti" at code-point index 2 → result 3)
- Negative `start` (e.g., `process("a tiger", "er", -2)` should search from the last 2 code points)
- `start` beyond the string length (should clamp and return 0)
- `start == null` (the `LocateNoStartEvaluator` path via `toEvaluator`)
I'd recommend adding explicit test cases for at least one negative `start`, one `start > 1`, and one out-of-range `start` to validate the `indexStart` clamping logic.
Additionally, the `supplier` helper computes the expected value as `1 + value.indexOf(substrValue)` without accounting for the `start` parameter. Since all suppliers hardcode `start = 0`, this is currently correct, but if `start` were varied, the expected-value computation would need to incorporate it.
