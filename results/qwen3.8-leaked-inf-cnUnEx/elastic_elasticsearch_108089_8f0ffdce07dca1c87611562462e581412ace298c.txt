#1VVZJ: The error message embeds `ctx.getParent().getText()`, which for a deeply nested expression (the exact scenario that triggers this) can be a very long string — potentially thousands of characters of repeated sub-expressions. This bloats exception messages in logs and error responses. Consider truncating the text (e.g., first ~100 chars + `"..."`) or using a shorter identifier such as the rule name (`ctx.getClass().getSimpleName()`) to keep the message bounded.

#DDTT0, #YVSFY, #TWMSK, #WE4Y9, #6YAVN: The boundary offsets in the tests (e.g., `MAX_EXPRESSION_DEPTH / 2 - 1` for casts, `MAX_EXPRESSION_DEPTH - 2` for binary ops, `MAX_EXPRESSION_DEPTH / 2 - 1` for parentheses) are tightly coupled to the internal parse-tree structure of each grammar rule. A brief inline comment on each explaining *why* that particular offset yields the boundary (e.g., "each `::type` cast adds 2 expression nodes, so N casts → 2N+1 depth") would make it much easier for a future maintainer to adjust these when the grammar evolves, rather than having to reverse-engineer the relationship.
