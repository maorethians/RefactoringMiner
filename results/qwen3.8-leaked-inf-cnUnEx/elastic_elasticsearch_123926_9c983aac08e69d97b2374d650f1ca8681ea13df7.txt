#WK6GP: The Javadoc for `createClient` still references the old class:
```java
@return An {@link OriginSettingClient} which uses the origin provided by {@link SystemIndexMigrationInfo#getOrigin()}.
```
Since this method now lives on `SystemResourceMigrationInfo`, the `@link` should point to `SystemResourceMigrationInfo#getOrigin()` (or simply `#getOrigin()`). As written, the Javadoc link is stale and will resolve to the wrong class.

#ZEXTX, #CHB01: The `origin` field is assigned without a null check (`this.origin = origin;`), unlike every other required field in the constructor which uses `Objects.requireNonNull`. The `SystemResourceDescriptor.getOrigin()` contract does not declare `@Nullable`, and downstream callers like `SystemResourceMigrationInfo.createClient()` pass the result directly into `new OriginSettingClient(baseClient, this.getOrigin())`. If a plugin ever constructs a `SystemDataStreamDescriptor` with a null origin (which the constructor currently permits), this will silently produce a client with a null origin header. Consider either adding `Objects.requireNonNull(origin, "origin must be specified")` or annotating the interface method with `@Nullable` and guarding the callers.

#QRKQB: `getIndices` uses `metadata::getIndexSafe`, which throws `IndexNotFoundException` if a backing index is missing from the metadata. This is then consumed by `needToBeMigrated` (diff #Q3PQR), which contains a null-check (`if (indexMetadata == null) return false;`) that becomes dead code for the data-stream path because the exception is thrown before the null check is reached. If a backing index is transiently absent (e.g., during a concurrent cluster-state update), the migration will fail with an unhandled `IndexNotFoundException` rather than gracefully skipping that index. Consider using `metadata::index` (which returns null) and filtering out nulls, consistent with how `SystemIndexMigrationInfo.getIndices` works.

#D7ZCN: The `nodeSettings` override is a no-op:
```java
@Override
protected Settings nodeSettings(int nodeOrdinal, Settings otherSettings) {
    return Settings.builder().put(super.nodeSettings(nodeOrdinal, otherSettings)).build();
}
```
It wraps the parent's result in a new `Settings.Builder` and immediately builds it, producing an equivalent `Settings` object. If no additional settings are needed, this override can be removed. If it was added as a placeholder for future settings, a brief comment explaining the intent would help.

#3ETWE: The polling loop in `checkDataStreamMigrationStatus` reschedules itself every 1 second with no upper bound on iterations or a wall-clock timeout. If the `ReindexDataStream` persistent task hangs (e.g., a stuck shard allocation), this will generate an unbounded stream of status requests on the generic thread pool. Consider adding a maximum retry count or an overall deadline (e.g., 10 minutes) after which the migration is marked as failed, to prevent a stuck task from consuming resources indefinitely.

#D6FWV: Changing `allowRestrictedIndices(false)` to `allowRestrictedIndices(true)` for the `internal_user` role broadens its access to system data streams and their backing indices. This is presumably required for the migration path, but it also means the internal user can now read/write/delete any restricted index (not just the ones being migrated). If the intent is to grant access only during migration, a more scoped privilege set or a time-limited grant would reduce the attack surface. At minimum, a comment explaining why full restricted-index access is needed here would aid future security reviews.
