#KVHGG, #28SXB: The `types()` method maps type-name strings via `DataType.fromTypeName`, which returns `null` for unknown names (it's a simple `Map.get`). If any key in `typesToIndices` is not a recognized type name, the resulting `Set<DataType>` will contain `null`. In `#28SXB`, the call `imf.types().stream().allMatch(predicate)` will then throw a `NullPointerException` when the predicate is invoked on `null`. Consider filtering out nulls or asserting non-null in `types()`:
```java
return typesToIndices.keySet().stream()
    .map(DataType::fromTypeName)
    .filter(Objects::nonNull)
    .collect(Collectors.toSet());
```

#8PJ1J: The change from `UnsupportedAttribute` (with an `UnsupportedEsField` carrying the original type name) to a bare `UnresolvedAttribute` with `null` qualifier and no `id` loses two things: (1) the original type information that was embedded in `UnsupportedEsField`, and (2) the `NameId`. If downstream rules or error reporting rely on the `id` or the original type to produce a meaningful diagnostic, this will degrade the user-facing error. If this is intentional (e.g., the literal should be re-resolvable by a later rule), a brief comment explaining why "unresolved" is preferred over "unsupported" here would help future readers.

#E7TTX: The previous code explicitly skipped `EsRelation` nodes with the comment *"Leave esRelation as InvalidMappedField so that UNSUPPORTED fields can still pass through."* Removing that guard means `EsRelation` will now also be transformed by `checkUnresolved`, converting its `InvalidMappedField` into an `UnsupportedAttribute`. If any downstream logic (e.g., `FieldExtractExec` generation or the `EsRelation` output-set matching in `#33B14`) still expects to find `InvalidMappedField` inside an `EsRelation`, this will break. Please confirm that no later rule or exec-plan builder relies on `EsRelation` retaining `InvalidMappedField` instances.

#0X6BJ: The new guard condition
```java
Resolvables.resolved(stats.groupings()) == false || Resolvables.resolved(stats.aggregates()) == false
```
is logically correct (De Morgan of "both fully resolved"), but it iterates the groupings list and then the aggregates list separately. If either list is empty, `Resolvables.resolved` returns `true` (vacuous truth), which is the desired behavior. No issue, but be aware that this now triggers the resolution block even when only *one* of the two lists has unresolved entries, whereas the old `expressionsResolved()` may have had a different granularity. Make sure the resolution logic inside the block is idempotent for the already-resolved list.

#96QSY: Removing the `p.resolved() ||` short-circuit means `doRule` will now be applied to nodes that were previously considered fully resolved. This is likely intentional (the old check was too aggressive and prevented union-type resolution on some nodes), but it also means `doRule` will run on more nodes, including those whose children are all resolved. Ensure `doRule` is safe to call on an already-resolved plan (i.e., it's a no-op in that case) to avoid unnecessary work or accidental mutation.
