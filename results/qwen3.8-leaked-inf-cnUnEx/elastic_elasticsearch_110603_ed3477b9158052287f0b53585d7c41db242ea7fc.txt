#0KTA1, #S02V5: The old code in both `postParse` and `TsidExtractingIdFieldMapper` consistently used `context.rootDoc()` to access the `@timestamp` field. The new code in `postParse` (#0KTA1) switches to `context.doc()`, while `TsidExtractingIdFieldMapper` (#S02V5) keeps `context.rootDoc()`. Although `postParse` is invoked at the root level so `doc()` and `rootDoc()` are equivalent in practice, the inconsistency is a latent risk: if the call-site contract for `postParse` ever changes, or if a future refactoring introduces a nested context, the `doc()` lookup would silently miss the key. Using `context.rootDoc()` in `#0KTA1` would match the old behavior, match `#S02V5`, and make the intent (always read from the root document) explicit.

#VZ0QM: The two keyed entries use different Lucene field types as pure data carriers: a `LongField` (which by convention implies indexed + doc-values) for the timestamp value, and a `StoredField` (which implies stored) for the multi-value flag. Since `onlyAddKey` explicitly does *not* add the field to the document's field list, none of those Lucene-level semantics apply. Using `LongField` and `StoredField` here is misleading to a reader who expects those types to carry their usual indexing/storage implications. A lightweight `IndexableField` (or a small dedicated holder) would make it clearer that these are map values, not Lucene fields. This is a minor readability concern, not a correctness bug.
