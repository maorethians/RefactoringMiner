#57Q0K: The boundary check `topicMetadata.getReserveTime() > 0` treats a reserve time of `0` the same as the sentinel value `-1` (falling back to the global config). However, the attribute is defined with `min = -1`, which implies `0` is a valid, distinct value. If a user explicitly sets the reserve time to `0` (meaning "no retention / immediate cleanup"), it will silently fall back to the global `tieredStoreFileReservedTime` instead. Consider using `>= 0` to allow `0` as a valid per-topic override, or document that `0` is intentionally treated as "use default" and adjust the attribute's `min` to reflect that.

#73B8Z: If `metadataStore.addTopic(...)` or `metadataStore.updateTopic(...)` throws a runtime exception (e.g., a database connectivity issue), the exception propagates out of `updateTopicConfig` and the topic config is never persisted. This means a transient tiered-store metadata failure blocks all topic config updates, even for topics that don't use tiered storage attributes. Consider wrapping the metadata-store calls in a try-catch that logs the error and decides whether to fail the entire update or proceed with the config update (leaving metadata reconciliation to a later retry), depending on the desired consistency guarantee.
