#9T1V4: The condition `mvxLimit < 0` is a defensive guard, but a negative limit value is semantically invalid in ESQL. Silently overwriting it (rather than throwing or asserting) could mask a bug upstream that produced a corrupt limit. Consider replacing the `< 0` check with an `assert mvxLimit == null || mvxLimit >= 0` to fail fast in development, and simply checking `mvxLimit == null || mvxLimit > limitVal` for the actual overwrite condition.

#RWZPP: The guard `mvExpand.limit() >= 0` mirrors the optimizer's defensive check, but since the optimizer only ever sets non-negative values (and the deserialization path always produces `null`), this branch is effectively dead for the `< 0` case. More importantly, when `mvExpand.limit()` is `0`, this creates a `LimitExec` with limit `0` (i.e., "return zero rows"). Verify this is the intended semantics — a `LIMIT 0` in ESQL should indeed produce zero rows, but it's worth confirming that `MvExpandExec` followed by `LimitExec(0)` doesn't cause any edge-case issues in the execution engine (e.g., division by zero in progress reporting, or empty-iterator assumptions in downstream operators).

#H9HS1, #P1YFQ: The design of not serializing the `limit` field (hardcoding `null` on read, asserting `null` on write) is intentional since it's a coordinator-only optimization artifact. However, the `assert limit == null` in `writeTo` will be a no-op in production (where assertions are disabled). If a `MvExpand` with a non-null limit is ever serialized in a production code path (e.g., plan caching, distributed planning), the limit would be silently dropped without any warning. Consider adding a `if (limit != null) { throw new IllegalStateException(...); }` guard instead of (or in addition to) the assert, to make the invariant explicit in all environments.
