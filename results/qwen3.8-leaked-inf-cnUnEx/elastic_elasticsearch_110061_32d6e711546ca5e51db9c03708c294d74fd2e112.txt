#PC4H2, #H1J49, #823CJ, #SDV97, #RN7JM: The removal of `synchronized` from `pauseExecution()` while `start()` remains `synchronized` creates an asymmetric locking situation. Since both methods mutate the compound state (`isRunning` + `schedules`), they can now interleave:
```
start():       isRunning.set(true)
pauseExecution(): isRunning.set(false)
pauseExecution(): schedules.clear()
start():       schedules.putAll(startingSchedules)   // re-populates schedules while isRunning == false
```
The final state is `isRunning == false` but `schedules` is non-empty. While `checkJobs()` will skip due to the flag, the invariant "paused ⇒ no schedules" is broken. If `start()` is later called again, it will `putAll` over already-present entries, which is fine, but the intermediate state is confusing and the debug log in `add()`/`remove()` will report "engine is running: false" while schedules exist.
Consider either:
- Keeping `synchronized` on both (or neither) to preserve mutual exclusion, or
- Documenting that the two methods are expected to be called from a single thread / lifecycle controller, and removing `synchronized` from `start()` as well for consistency.

#RN7JM: When the engine is paused mid-iteration (the `break` path), the code falls through to `if (events.isEmpty() == false) { notifyListeners(events); }`, delivering the partially accumulated events. This is likely intentional (those schedules had already passed their trigger time), but it is worth confirming: if the caller of `notifyListeners` assumes a "complete batch" semantic, a partial batch delivered during a pause could be surprising. If partial delivery is acceptable, a brief comment at the `break` site would make the intent explicit for future readers.
