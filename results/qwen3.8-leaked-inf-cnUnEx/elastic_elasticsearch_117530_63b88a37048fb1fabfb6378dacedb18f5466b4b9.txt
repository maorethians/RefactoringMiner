#M6PBP: The lambda parameter is `si` (the `StreamInput` passed by `readMap`), but the body reads from the captured outer `in`. While these happen to be the same object in the current implementation, this is fragile and misleading. If the `readMap` implementation ever delegates to a sub-stream or the reader is reused in a different context, this would silently read from the wrong stream. Use `si.readLong()` instead.

#B139D: The legacy format historically represented the operation count (in Azure: `counter.add(1)` per operation; in S3: `counter.add(requestCount)` per operation). Writing `v.requests()` (which includes retries) into a slot that legacy peers interpret as "operation count" will overstate the number of operations. For example, an `EndpointStats(10, 13)` would serialize as `13` to a legacy node, which would then report 13 operations when only 10 occurred. Consider writing `v.operations()` to preserve the semantic meaning of the legacy field.

#HRVTD: The record explicitly overrides `equals` and `hashCode`, but records already generate these from their components. The manual implementations are functionally identical to the auto-generated ones and add maintenance surface for no benefit. They can be removed.

#1JPC3: This serializes only `operations()` as a flat long, while `EndpointStats.toXContent()` (defined in #HRVTD) serializes both fields as a nested object. The snapshot API is intentionally lossy for BWC (as acknowledged in #0VAVJ), but the inconsistency between the two serialization paths for the same type may confuse API consumers. If the flat representation is the intended wire format for this endpoint, consider adding a brief comment explaining why `requests` is omitted here, or alternatively use `EndpointStats.toXContent()` to expose both fields and let the API evolve.

#D902Z: This only asserts `requests() == 0`. While logically `requests == 0` implies `operations == 0` (since each operation produces at least one request), the S3 path in #YM7NQ shows a case where `operations` is incremented but `requests` is not (null response). In that scenario, `operations` could be non-zero while `requests` is zero. Adding an assertion on `operations()` as well would make the test more robust against that edge case.

#YM7NQ: `operations` is incremented unconditionally, but `requests` is only incremented when `response != null`. This means `operations` can exceed `requests`, which contradicts the `EndpointStats` Javadoc ("requests: The number of calls (including retries)") implying requests ≥ operations. If this is intentional (operations = attempts, requests = actual HTTP calls), the Javadoc in #HRVTD should be updated to clarify that `requests` may be less than `operations` in edge cases (e.g., null responses).

#0VAVJ: This is a reasonable BWC workaround, but it means all downstream assertions in the metering tests (#9MNTD, #4J6TE, #ZPDPN) that check `requests()` are actually checking the same value as `operations()`. The tests pass trivially for the `requests` assertion since it's the same number. Consider whether the test framework should skip the `requests` assertion when the value was parsed from the lossy API, to avoid false confidence.
