#7QPKR: The `Netty4CloseNotifyHandler` is added to the pipeline without a name:
```java
ch.pipeline().addLast(new Netty4CloseNotifyHandler(ch, sslHandler));
```
Every other handler in this pipeline is registered with a string name (`"ssl"`, `"chunked_writer"`, `"decoder"`, `"aggregator"`, `"pipelining"`, etc.). An unnamed handler is harder to identify in pipeline dumps, harder to remove or replace programmatically, and inconsistent with the surrounding code. Consider adding a name like `"close_notify_handler"`.

#M3C0N: The `inFlyRequests` counter can go negative, which would permanently prevent the connection from being closed. The counter is incremented in `channelRead` when an `HttpRequest` is seen, and decremented in `write` when a `LastHttpContent` is seen. However, the handler sits *after* the `header_validator` in the inbound pipeline. If the validator rejects a request and the pipeline still emits an error response (e.g. 400/401), that response passes through `write` and decrements `inFlyRequests` without a matching increment from `channelRead`. Once the counter is negative, the `inFlyRequests == 0` check in both the constructor listener and `flush` will never be true, so the connection is never closed — a resource leak.
Consider guarding the decrement:
```java
if (msg instanceof LastHttpContent && inFlyRequests > 0) {
    inFlyRequests--;
}
```
Or, more robustly, track in-flight requests with a mechanism that cannot go below zero (e.g. a `Math.max(0, inFlyRequests - 1)` pattern), and add an assertion or log warning if the counter would go negative so the mismatch is visible during development.
