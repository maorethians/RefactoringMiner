#EBC2B: In `LogicalPlanBuilder.plan()`, after building the full plan tree, only the **root** node is checked for `MetricsAware` and registered:
```java
if (p instanceof MetricsAware ma) {
    metrics.command(ma);
}
```
For a pipeline like `FROM idx | EVAL … | STATS … | KEEP … | EVAL …`, the plan is a chain where the root is the last `EVAL`. The inner `FROM`, `EVAL`, `STATS`, `KEEP` nodes are children and are never passed to `metrics.command()`. Yet the integration tests in `#R4R9Z` still expect all of them (e.g. `FROM: 1, EVAL: 2, STATS: 1, KEEP: 1`). The old code collected every node via `plan.forEachDown(p -> add(commands, p.commandName()))`. If no other code path registers the inner nodes, the command counts will be wrong for any multi-command query. Please verify that every `MetricsAware` node in the pipeline is actually reaching `PlanningMetrics.command()` — either by traversing the built tree here, or by calling `metrics.command()` inside each command's visitor method as the node is created.

#9TTDA: `functionName(Class)` performs a linear scan over `defs.values()` on every call. This is invoked from `PlanningMetrics.function(Class)` (`#PS068`), which in turn is called from `ExpressionBuilder.castToType` (`#36E4Q`) for **every** cast expression in the query. With a large function registry and many casts, this becomes O(casts × functions). Consider maintaining a reverse `Map<Class, String>` alongside `defs` for O(1) lookup.

#Y065A: `PlanningMetrics.command()` throws a `QlIllegalArgumentException` when `metricName()` returns `null`. The `MetricsAware` default never returns null, but `UnresolvedRelation.metricName()` (`#DMX0F`) delegates to the `commandName` field, which is explicitly set to `null` in `#ENYZX` (METRICS relation) and `#CG8GE` (JOIN relation) to opt out of counting. If such a node ever reaches `command()`, the query will fail with an exception rather than simply being skipped. Since the intent of setting `commandName` to `null` is "don't count this," a `null` guard that silently returns (or checks before calling `command()`) would be more robust than throwing.
