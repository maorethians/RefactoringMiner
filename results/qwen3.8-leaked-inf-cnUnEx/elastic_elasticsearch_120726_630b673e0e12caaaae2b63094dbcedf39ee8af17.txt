#V01KT: Two issues in `wrapSingleValueQuery`:
1. **Potential NPE from `searcher()` returning null.** The `SearchExecutionContext.searcher()` method is documented to return `null` when no index reader is available (e.g., during percolation). If it returns null, `singleValueQuery.rewrite(null)` will throw a `NullPointerException`, which is *not* caught by the `catch (IOException e)` block. A null-check on the searcher (or a broader catch) is needed.
2. **Silent exception swallowing.** The `catch (IOException e)` block discards the exception with only a `TODO` comment. At minimum, the exception should be logged (e.g., via a logger) so that transient I/O failures are diagnosable in production. Silently falling through to the `BooleanQuery` path on an I/O error could mask real cluster issues.

#V01KT, #Q8W7W: **Performance: redundant per-position rewrite.** `wrapSingleValueQuery` is invoked for every position where `onlySingleValues` is true. Each invocation constructs a new `SingleValueMatchQuery` and calls `rewrite`, which iterates over all `LeafReaderContext`s in the index reader. The outcome (whether the field is fully indexed and thus a `MatchAllDocsQuery`) depends only on the `field` and the `searcher`, not on the row position. For a lookup join over many rows this becomes O(rows × leaves) where it could be O(leaves). Consider computing the "fully indexed" check once (e.g., lazily in the `QueryList` constructor or a cached field) and reusing the result.
