#ZZ2A4: The semantic shift from `totalTargetAllocations()` to `getTaskParams().getNumberOfAllocations()` is reasonable: it prevents the autoscaler from treating a deployment as "empty" (and thus downscaling to zero) merely because adaptive scaling has temporarily driven the target to 0, while the user still has a live deployment requesting allocations.
One thing to verify: `getTaskParams()` is called on every assignment in the stream. If there is any code path (e.g., a deserialized or partially-built `TrainedModelAssignment`) where `taskParams` could be `null`, this would throw an NPE where the old code would not. Based on the builder shown, `taskParams` is always set, so this is likely safe, but a defensive null-check or an `Objects.requireNonNull` in the getter would make the invariant explicit.

#NMYD8: The test correctly exercises the "model allocation exists but no ML node is present" path and asserts both total and node capacity. Two minor observations:
1. `modelBytes` is set to `400` (bytes), yet the assertion expects memory `greaterThan(TEST_JOB_SIZE)` (200 MB). This works because the decider applies a minimum node size, but the gap between the input (400 B) and the expected output (> 200 MB) is large enough that a reader might wonder whether the constant is a typo. A brief inline comment (e.g., `// 400 bytes model; minimum node memory still applies`) would make the intent clearer.
2. The test asserts `processors().count()` equals `2.0`, which matches `threadsPerAllocation = 2` with `numberOfAllocations = 1`. This is correct, but it would be more robust to derive the expected value from the same constants used in the `TaskParams` constructor (e.g., `equalTo(2.0 * 1)`) so the assertion stays in sync if the parameters are ever adjusted.
