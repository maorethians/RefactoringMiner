#7RQZC: The test can pass vacuously: if none of the 50 iterations triggers a `StackOverflowError` (e.g., on a JVM with a large stack size), the `catch` block never executes and the test completes with zero assertions. Consider tracking whether at least one exception was thrown and asserting at the end of the loop, e.g.:
```java
boolean caught = false;
for (int i = 0; i < 50; i++) {
    // ...
    try {
        physicalPlan(query);
    } catch (ParsingException | org.elasticsearch.xpack.esql.parser.ParsingException e) {
        caught = true;
        assertThat(e.getMessage(), containsString("causing stack overflow"));
    }
}
assertThat("Expected at least one stack-overflow exception", caught, is(true));
```
This makes the test fail loudly if the guard is accidentally removed or the query is no longer large enough to trigger the condition.

#K443E, #ENBVS, #RS0FS: Catching `StackOverflowError` is fragile: the JVM specification does not guarantee that a `catch` block will execute after a `StackOverflowError` has been thrown, because the stack may already be exhausted and the catch handler itself needs stack frames. In practice this usually works for simple handlers like these, but it is not a reliable safety net. A more robust long-term fix would be to convert the recursive traversals (`forEachDown`, `forEachUp`) to an explicit work-stack (iterative) implementation, which eliminates the unbounded recursion that causes the overflow in the first place. If the iterative rewrite is out of scope for this PR, the current approach is a reasonable stopgap, but it would be worth adding a brief comment at each catch site noting that this is a best-effort guard and that the underlying recursion should eventually be made iterative.
Additionally, the identical try/catch/throw block is now repeated in three places. Extracting a small helper (e.g., `private static <T> T guardStackOverflow(Supplier<T> action, Node node)`) would reduce duplication and make it easier to apply a consistent message or future change in one location.
