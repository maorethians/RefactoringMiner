#6RFM3: When reusing a previously destroyed chunk, the code returns the existing `PoolChunk` object directly without resetting its internal state (`freeBytes`, `runsAvail`, `runsAvailMap`, `subpages`, `cachedNioBuffers`). This is correct only if `destroyChunk` is guaranteed to be called exclusively when the chunk is in a fully-freed state (all pages returned, initial run restored). If there is any code path where a chunk can be destroyed while still holding allocated pages or subpage references, the reused chunk would carry stale state into the next allocation cycle. Consider either:
- Adding an explicit reset (e.g., calling a `reset()` method that re-initializes the fields the constructor sets), or
- Adding an assertion in `newChunk` that verifies `chunk.freeBytes == chunkSize` before returning the reused chunk, to make the invariant explicit and catch violations in tests.

#P5FB2: The new logic computes the bit-length of the full shifted value and then masks the *result* to `HISTO_MAX_BUCKET_MASK`. For sizes above 1 MiB (e.g., 2 MiB → shifted value 255 → bit-length 8 → `8 & 7 = 0`), the bucket index wraps around to 0, which is the same bucket as the 8 KiB minimum. The comment documents the upper band as 1 MiB, so this is presumably a caller contract. However, a defensive `Math.min` or a saturating clamp (e.g., `Math.min(bitLength, HISTO_MAX_BUCKET_MASK)`) would make the method robust against unexpected inputs rather than silently mapping them to the wrong bucket.
