#XT08W: **Critical: Missing `return` after the sorted-ascending branch causes double-append.**
In `processDoubles`, `processInts`, and `processLongs`, when `valuesBlock.mvSortedAscending()` is `true`, the code appends a result to the builder and then **falls through** to the unsorted code path, which appends a *second* result. For example in `processDoubles`:
```java
if (valuesBlock.mvSortedAscending()) {
    // ... appends a value ...
}
// No return/else — execution continues here and appends ANOTHER value
var values = new double[valueCount];
// ... sorts and appends again ...
```
The sorted-ascending block should end with a `return;` (or the unsorted code should be in an `else` branch). As written, every sorted-ascending position produces two values in the output block, corrupting the result.

#XT08W: **Wrong value indices in the sorted-ascending fast path.**
In all three `process*` methods, the sorted-ascending branch uses raw indices without the `firstValueIndex` offset:
```java
// processDoubles (same pattern in processInts, processLongs)
builder.appendDouble(valuesBlock.getDouble(0));                    // should be firstValueIndex
builder.appendDouble(valuesBlock.getDouble(valueCount - 1));       // should be firstValueIndex + valueCount - 1
valuesBlock.getDouble(lowerIndex)                                  // should be firstValueIndex + lowerIndex
valuesBlock.getDouble(upperIndex)                                  // should be firstValueIndex + upperIndex
```
In a multivalued block, position `p`'s values start at `firstValueIndex`, not at 0. Using bare indices reads values from the wrong position (or out of bounds for later positions). The unsorted path correctly uses `firstValueIndex + i`, confirming the intent.

#XT08W: **`foldable()` ignores the `percentile` argument.**
```java
@Override
public boolean foldable() {
    return field.foldable();
}
```
If `percentile` is a non-foldable expression (e.g., a column reference) but `field` is a literal, this returns `true`, incorrectly signalling that the whole expression can be constant-folded. It should be:
```java
return field.foldable() && percentile.foldable();
```

#XT08W: **Inner-switch `default` cases report the wrong type in the error message.**
In `toEvaluator`, the nested switches on `percentile.dataType()` throw:
```java
default -> throw EsqlIllegalArgumentException.illegalDataType(field.dataType());
```
Since the outer switch already validated the field type, the `default` here is reached because the *percentile* type is unexpected. The message should reference `percentile.dataType()` so the user sees which argument is actually invalid.
