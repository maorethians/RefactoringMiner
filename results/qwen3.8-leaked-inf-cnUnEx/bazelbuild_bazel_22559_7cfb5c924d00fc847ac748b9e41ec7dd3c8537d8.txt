#E60YX: In #E60YX, the early return `if (!SandboxStash.gotInstance()) { return; }` causes `sandboxExecRoot.createDirectoryAndParents()` to be skipped when `SandboxStash` has not been initialized. In the previous code (visible in the removed lines), `createDirectoryAndParents()` was called unconditionally after `takeStashedSandbox`. #E60YX, #FBXKT: In #E60YX, the final stash assembly does:
```java
main.dirEntries().put(SandboxStash.getWorkspaceName(), stashContentsMap.get(PathFragment.EMPTY_FRAGMENT));
```
If `inputs.getFiles()` and `inputs.getSymlinks()` are both empty and no output directories exist, `stashContentsMap` will be empty and `get(PathFragment.EMPTY_FRAGMENT)` returns `null`. This `null` is then stored in `dirEntries()`, which will cause an NPE later when `cleanRecursivelyWithInMemoryStashes` (#FBXKT) iterates over `dirEntries()` and calls methods on the value. A null-check or a default `StashContents.create()` should be used.

Checking an `Optional` for `null` before calling `.isPresent()` is contradictory. If the method can return `null`, it should not return `Optional` (use `@Nullable StashContents` instead). #AQQDB, #E60YX, #YDRTC: In #AQQDB, the `@SuppressWarnings("AutoValueImmutableFields")` annotations acknowledge that the maps are mutable. The code in #E60YX and #YDRTC relies on this mutability (e.g., `stashContentsMap.get(parent).filesToPath().put(...)`). This makes the "immutable" value object effectively mutable, which is fragile: any future change to use `ImmutableMap` or a defensive copy in the AutoValue builder will silently break the put-based mutation pattern. Consider making the builder methods explicit (e.g., `withFile(...)`, `withDirEntry(...)`) or documenting the mutability contract clearly on the class.
