#QFDS5: The test `testSuppressedDeletionErrorsAreCapped` may not reliably exercise the cap. The number of blobs is `randomList(1, maxNoOfDeletions * maxBulkDeleteSize, ...)` where `maxNoOfDeletions = 20`. The number of delete requests is `ceil(numBlobs / maxBulkDeleteSize)`. For the cap (10) to actually be hit, we need more than 10 requests, i.e., `numBlobs > 10 * maxBulkDeleteSize`. However, the minimum blob count is 1, and `maxBulkDeleteSize` can be as high as 10, yielding just 1 request. In that case the assertion `lessThan(10)` passes trivially without ever testing the cap. Consider setting the minimum blob count to `(S3BlobStore.MAX_DELETE_EXCEPTIONS + 1) * maxBulkDeleteSize` to guarantee the cap is exercised:
```java
var minBlobs = (S3BlobStore.MAX_DELETE_EXCEPTIONS + 1) * maxBulkDeleteSize;
var blobs = randomList(minBlobs, maxNoOfDeletions * maxBulkDeleteSize, ESTestCase::randomIdentifier);
```

#JPEZ4: The `useOrMaybeSuppress` method performs a non-atomic read-then-write on the `AtomicReference`:
```java
var deletionExceptions = aex.get();
if (deletionExceptions.count < MAX_DELETE_EXCEPTIONS) {
    aex.set(new DeletionExceptions(..., deletionExceptions.count + 1));
}
```
While this is safe under the current sequential `forEachRemaining` iteration, the use of `AtomicReference` signals an intent for thread-safe access. If this code path is ever invoked concurrently (e.g., if `deletePartition` is parallelized), two threads could read the same count and both write, losing an increment. Consider either documenting the single-threaded precondition on the method, or using `AtomicReference.updateAndGet(...)` to make the update atomic.
