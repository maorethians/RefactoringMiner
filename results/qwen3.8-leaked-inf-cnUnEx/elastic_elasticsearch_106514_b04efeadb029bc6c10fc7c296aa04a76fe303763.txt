#WP6NY: In `AliasActionResult.buildRemoveError`, the error is constructed as:
```java
new AliasesNotFoundException((action.getOriginalAliases()))
```
If `getOriginalAliases()` returns `null` (which is possible if the action was deserialized from an older transport version where `originalAliases` wasn't set, or if the action was constructed without calling `aliases()`), the resulting message would be `"aliases null missing"` and `setResources("aliases", null)` could cause a downstream NPE. Consider guarding with a fallback, e.g.:
```java
String[] aliases = action.getOriginalAliases();
new AliasesNotFoundException(aliases != null ? aliases : new String[0])
```

#3JFVY: The exception type is changed from `ResourceNotFoundException` to `AliasesNotFoundException`. Since `AliasesNotFoundException` does not extend `ResourceNotFoundException` (its constructor calls `super(msg)` with a single argument, unlike `ResourceNotFoundException`'s `super(msg, args)`), any internal code or plugin that specifically catches `ResourceNotFoundException` from this code path will no longer intercept it. If this is intentional (to provide a more specific exception type), it's fine, but it's worth confirming no downstream catchers rely on the old type.

#581T2: In the data-stream `REMOVE` branch, when `nonBackingIndices` is non-empty the code falls through to the regular-index loop, and `numAliasesRemoved` accumulates counts from both data-stream and regular-index aliases. The final `AliasActionResult.build(action, numAliasesRemoved)` then only uses the count to decide success vs. error (0 → error). The actual number of aliases removed is not exposed in the response. If a user removes 3 aliases across data streams and indices, the response only says "success" without indicating how many were actually removed. This may be acceptable, but it's a loss of information compared to what the counter already tracks.

#XASK5: The `removeAlias` method previously always returned `AcknowledgedResponse.TRUE` in `onResponse`, masking any per-action errors. Now it passes through the full `IndicesAliasesResponse`. This is a behavior change: callers that previously saw `acknowledged=true` unconditionally will now potentially see `errors=true` with action-level details. Verify that all callers of `removeAlias` (e.g., in `SearchApplicationIndexService`) handle the new error path correctly, since they previously had no reason to check for errors.
