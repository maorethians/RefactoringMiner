#W982J: The `resolvedPipelineCache` is keyed by `indexRequest.index()`, but there is no null-check on that value before calling `HashMap.computeIfAbsent`. If `indexRequest.index()` were ever `null`, this would throw a `NullPointerException`. While in practice bulk items should always carry a non-null index, a defensive guard (or an early `continue`/skip) would make the intent explicit and avoid a hard crash in an edge case.
Additionally, the cache key is only `indexRequest.index()`, but `resolveStoredPipelines` also depends on `originalRequest` (the `actionRequest`). If two bulk items share the same `indexRequest.index()` but have different `originalRequest` objects whose `index()` differs (e.g., an alias vs. a concrete index in an upsert scenario), the second item would incorrectly receive the first item's cached `Pipelines`. Consider whether the cache key should incorporate `actionRequest.index()` as well, or add a comment/assertion documenting the assumption that they are always equal.

#EJ6VS: When `requestPipeline != null`, the call `indexRequest.setPipeline(requestPipeline)` is a no-op—it sets the field to the value it already holds. The branch can be simplified to:
```java
if (requestPipeline == null) {
    indexRequest.setPipeline(resolvedPipelines.defaultPipeline);
}
```
This removes the misleading impression that something is being "set" in the first branch and makes the intent (only override when the caller did not specify a pipeline) clearer.

#TW4MC: The test covers rollover-on-write = true with a matching V1 template, but does not cover the case where rollover-on-write is true and **no** template matches. In that path, `resolveStoredPipelines` falls through to `Pipelines.NO_PIPELINES_DEFINED` (noop pipelines). A test asserting that `hasPipeline(indexRequest)` is `false` (or that both pipeline fields equal `NOOP_PIPELINE_NAME`) would guard against a regression where the rollover branch accidentally falls back to metadata lookup.
