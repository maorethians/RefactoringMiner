#C3WA1: No issues. `String.isEmpty()` is a clear and equivalent replacement for `length() == 0`.

#6GX73: The null-safety of `context.sourceToParse().id()` is guarded only by an `assert`. In production builds (where assertions are disabled), a null ID would propagate into `Base64.getUrlDecoder().decode(null)` and surface as a bare `NullPointerException` with no context about why the routing hash could not be resolved. Consider replacing the assert with an explicit null check that throws a `DocumentParsingException` (or similar) with a descriptive message, consistent with the error the removed test in `#QQD59` was asserting on. This keeps the failure mode informative regardless of JVM flags.
Additionally, `Base64.getUrlDecoder().decode(...)` will throw an `IllegalArgumentException` if the ID is not valid Base64-URL. If the ID is guaranteed to be Base64-URL by construction this is fine, but a brief comment noting that invariant would help future readers.

#QQD59: Removing `testParseWithDynamicMappingNullId` eliminates the only test that exercised the "routing hash is null in time_series mode" path. The new fallback logic in `#6GX73` (deriving the routing hash from the first 4 bytes of the Base64-decoded ID) is a new code path that should be covered by a test verifying:
1. A document with a null routing hash but a valid ID produces the expected `SortedDocValuesField` value.
2. A document with both null routing hash and null ID fails with a clear error (matching whatever exception the production code throws).
Without such a test, the behavioral change from "throw a parsing exception" to "derive from ID" is unverified.
