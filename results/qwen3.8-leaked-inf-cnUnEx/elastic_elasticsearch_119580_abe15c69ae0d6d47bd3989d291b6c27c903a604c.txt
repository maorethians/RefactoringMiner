#CVDFJ: The transport version ID `8_826_00_0` follows the existing pattern. No issues.

#CHG61, #W8BQ7, #XNMTB: When writing to an older transport version, all three classes construct a temporary `EsIndex` with an empty mapping (`Map.of()`) to maintain wire compatibility. This is correct since the receiving side's `EsIndex.readFrom` will read the (empty) mapping and the attributes are serialized separately. However, this means the old-format receiver will hold an `EsIndex` with a permanently empty mapping. If any downstream code on the old-format node calls `index().mapping()` expecting real field data, it will get an empty map. This is presumably acceptable since the attributes carry the field info, but it's worth confirming no old-format code path depends on the mapping being populated.

#VM6KA, #ZT1P3, #09G9D, #CBDSE, #9P1Y7, #QFQVV, #VZS6J, #QT9Z0: Naming inconsistency: `EsStatsQueryExec` renames its field to `indexName`, while `EsRelation`, `EsQueryExec`, and `EsSourceExec` all use `indexPattern`. Since these represent the same concept (the user-facing index pattern, which may contain wildcards or comma-separated lists), using a consistent name across all plan nodes would reduce confusion for readers navigating between classes.

#2ZCVR: The guard `keepAllFields || allAttributes.isEmpty()` correctly prevents an `IndexOutOfBoundsException` when the mapping is empty (which is now the common case since mappings are no longer serialized). Good defensive addition.

#XJ9J2: The new test validates serialization size for an index pattern resolving to 100 concrete indices. The index names are generated as `"partial-.ds-index-service-logs-2025.01.01-000" + i` for `i` in `[0, 99]`, producing names like `...0000` through `...00099`. All are unique, so the map will have exactly 100 entries as intended.
