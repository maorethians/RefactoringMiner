#YPQ8R: The spin-wait replacement for `acquireShared(-1)` is well-motivated by the deadlock-detection concern, and `Thread.onSpinWait()` is the correct Java 9+ idiom for this pattern. One observation: this converts a blocking (parked) wait into a busy-wait that consumes a full core for the duration of the wait. In the expected case the wait is extremely short (another thread is mid-completion), so this is fine. Just be aware that if the completing thread is ever delayed (e.g., by a long GC pause or a slow `onResponse` callback), the spinning thread will burn CPU rather than sleeping. Given the stated rationale (avoiding false-positive deadlock detection in same-pool scenarios), this trade-off is reasonable, but it's worth confirming that no code path in the `COMPLETING` state can block for a non-trivial duration.

#39AVG: The test correctly exercises the concurrent-completion-from-same-pool scenario and the `assumeTrue` guard for assertions is appropriate. Two minor points:
1. The test has no explicit assertion that the futures were actually completed (e.g., checking `future.isDone()` after the loop). The implicit "no exception / no hang" assertion is sufficient for a regression test against deadlock detection, but a final check like `assertTrue(futureReference.get().isDone())` would make the test's success criterion explicit and guard against a scenario where the spin-wait silently never exits (which would only be caught by a test timeout).
2. The `safeSleep(1)` between creating new futures is a timing heuristic to let workers drain the current future. Under heavy CI load this could occasionally be too short, meaning two "generations" of futures overlap. This is unlikely to cause a false failure (the workers simply complete whichever future they grab), but it does mean the test's coverage of the exact 4-threads-on-one-future contention is probabilistic rather than guaranteed. Acceptable for a stress/regression test, just noting it.
