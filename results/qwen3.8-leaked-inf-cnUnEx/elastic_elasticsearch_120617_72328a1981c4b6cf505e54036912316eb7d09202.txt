#5KG2C: The FLS test asserts only on the column structure (which fields are visible) but never checks the returned `values`. Since the `other` field has no indexed data, all values would be `null`, making a value assertion low-value here. However, for `fls_user2` and `fls_user4`, the `org` column *does* have data (e.g., `"sales"` for `x=40.0`). Adding a value assertion (e.g., `assertThat(respMap.get("values"), equalTo(List.of(List.of(40.0, 40.0, "sales"))))`) would guard against a regression where the correct columns are reported but the underlying join produces wrong or missing values.

#RCM5Y, #4C8YZ: The LOOKUP-mode validation (single-index check, mode check) was moved from `resolveIndex` (analysis phase) to `LookupJoin.postAnalysisVerification` (post-analysis phase). This is a reasonable centralization, but it has a side effect: during analysis, an `EsRelation` is now constructed for LOOKUP-mode targets even when they resolve to multiple indices or a non-LOOKUP-mode index. Any code that inspects the plan between analysis and post-analysis verification (e.g., plan serialization, metrics collection, or other visitors) will see a structurally valid `EsRelation` where previously it would have seen an `UnresolvedRelation`. If no such intermediate consumers exist, this is fine; otherwise, the error surface shifts from "unresolved index" to "post-analysis failure," which may be less intuitive for users reading error messages.
