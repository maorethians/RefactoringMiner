#4707G, #WA7R7: The new methods accept a `MessageSelector` parameter but do not validate it for null before passing it to `getSubscriptionData`. Looking at the `getSubscriptionData` implementation (shown in the dependency), it only guards against a null `mq` and then immediately calls `messageSelector.getExpression()` / `messageSelector.getExpressionType()`, which will throw a raw `NullPointerException` if `messageSelector` is null. Given that the existing `pullSyncImpl` and `pullAsyncImpl` paths do validate their inputs (null mq, negative offset, non-positive maxNums), it would be consistent and more defensive to add a null check for `messageSelector` here, e.g.:
```java
if (messageSelector == null) {
    throw new MQClientException("messageSelector is null", null);
}
```
This gives callers a clear, typed exception instead of an opaque NPE deep in the call stack.

#E91SM: The Javadoc `@return` tag references `{@code PullRequest}`, but the method's return type is `PullResult`. This should be corrected to `{@code PullResult}` to avoid confusing readers.
