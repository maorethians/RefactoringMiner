#P60ZD, #RCAN4, #40WAF: The `pooledChunkAllocations` counter is only incremented in `allocateNormal`. If the `allocateSmall` code path can also trigger creation of a new `PoolChunk` (e.g., when no existing subpage/chunk has capacity for a small allocation), those chunk allocations will not be counted. This would cause `numChunkAllocations()` to undercount and `numActiveChunks()` to report an incorrect (too low) value. Please verify whether `allocateSmall` (or any other allocation path) can create new chunks, and if so, ensure the counter is incremented there as well.

#3FK04: The test only covers the scenario where a chunk is allocated but never deallocated (`numChunkDeallocations == 0`). There is no test that exercises the chunk-destruction path — i.e., a scenario where all buffers in a chunk are released and the chunk is actually destroyed, verifying that `numChunkDeallocations` increments and `numActiveChunks` drops to 0. Adding such a case would guard against regressions in the `freeChunk` increment logic (e.g., the `destroyChunk` condition or the `!finalizer` interaction).
