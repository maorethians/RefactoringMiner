#QFJ7B, #K4E9D, #Y8BGJ: The `indexPatterns` in the `ComposableIndexTemplate` is set to the data stream name itself (e.g., `.test-system-data-stream`). For data streams, the index patterns in the template should match the *backing indices* (e.g., `.test-system-data-stream*`), not the data stream name. Using the data stream name as the pattern will not match any backing index (which would be named like `.test-system-data-stream-000001`). The TODO comment acknowledges this uncertainty, but if the pattern is wrong, the template won't apply to the backing indices and the tests may not be exercising the intended code paths.

#TDW5X: The stream pipeline calls `currentState.metadata().getProject().dataStreams()` twice (once in `filter`, once in `map`). Extracting it to a local variable would improve readability and avoid the repeated navigation:
```java
Map<String, DataStream> dataStreams = currentState.metadata().getProject().dataStreams();
return featureStatesToRestore.stream()
    .map(systemIndices::getFeature)
    .filter(Objects::nonNull)
    .flatMap(feature -> feature.getDataStreamDescriptors().stream())
    .map(SystemDataStreamDescriptor::getDataStreamName)
    .filter(dataStreams::containsKey)
    .map(dataStreams::get)
    .collect(Collectors.toUnmodifiableSet());
```

#NAMTK: The refactored call `dataStreams.stream().map(project.dataStreams()::get).collect(Collectors.toSet())` could introduce a `null` element into the set if a resolved name is not present in the project's data streams map. The original code had an `assert dataStream != null` in the loop body; the new `deleteDataStream` method also has an assert, but in production (where asserts are disabled) this would result in a `NullPointerException` at `dataStream.getIndices()`. Consider filtering out nulls or using a more explicit lookup to make the failure mode clearer:
```java
dataStreams.stream()
    .map(project.dataStreams()::get)
    .filter(Objects::nonNull)
    .collect(Collectors.toSet())
```
