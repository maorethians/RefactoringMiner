#M83VB, #CS5W2, #YHZQG, #TQXB6, #CGNC4: The new `getWatchHistory()` helper calls `ensureGreen(HistoryStoreField.DATA_STREAM)` on every invocation. Since all call sites invoke this inside `assertBusy`, each retry iteration will block for up to 30 seconds (the default timeout of `ensureGreen`) before either succeeding or throwing. This significantly changes the retry semantics compared to the original code, which would fail fast on a missing hit count and let `assertBusy` retry quickly. If the data stream is not yet created, `ensureGreen` may throw immediately (which is fine for `assertBusy`), but if it exists and is in a non-green state, the test will stall for 30 s per iteration. Consider whether `ensureGreen` should be called once *before* the `assertBusy` block at each call site, or whether a shorter timeout / a lighter "index exists" check would be more appropriate inside the retry loop.

#YHZQG, #TQXB6, #CGNC4: The original code in these three tests used the index pattern `.watcher-history*` (no dash before the wildcard), while the new shared helper uses `.watcher-history-*`. The two patterns differ: `.watcher-history*` would also match an index named exactly `.watcher-history`, whereas `.watcher-history-*` requires at least one character after the dash. In practice the backing indices almost certainly always carry a suffix (e.g. a date), so this is unlikely to cause a real problem, but it is a silent behavioral change. Worth confirming that no test fixture or setup creates an index matching only the shorter pattern.

#YHZQG, #TQXB6: The original code called `.setSize(0)` on the search request (a common optimization to skip fetching source documents when only the hit count matters). The shared helper does not set a size, so the default of 10 documents is fetched on every retry iteration. This is a minor test-performance regression; if the helper is intended to be general-purpose, consider either documenting the default size or providing an overload that accepts a size parameter.
