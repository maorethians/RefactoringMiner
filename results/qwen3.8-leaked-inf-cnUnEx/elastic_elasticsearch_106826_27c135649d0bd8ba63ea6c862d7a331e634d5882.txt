If a task ID ever contained a comma, the output would be ambiguous. This is unlikely in practice for Elasticsearch transform IDs, but worth being aware of.

The use of `String.join(", ", ...)` for both `failedTasks` and `failedReasons` is appropriate and consistent with the `MessageFormat` placeholders `{0}` and `{1}`.

Consider using `TransformMessages.getMessage(TransformMessages.CANNOT_STOP_SINGLE_FAILED_TRANSFORM, "failed-task", "task has failed")` for the single-task assertion to maintain a single source of truth, similar to the previous approach.

#WSRKA, #9HRH2, #R89VZ, #EFTW4, #KQ300, #6K17S: Switching from `matchesRegex` to `startsWith` in the integration tests is a reasonable maintainability trade-off, since the exact bulk-indexing failure message can vary across versions. However, note that `startsWith` only validates the prefix of the reason/message. If a regression introduced a truncated or malformed message that happened to share the same prefix, the test would still pass. This is an acceptable risk given the context, but worth noting.
