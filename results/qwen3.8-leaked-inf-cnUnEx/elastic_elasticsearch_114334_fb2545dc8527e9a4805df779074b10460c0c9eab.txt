#JE5T7, #XTGC9, #A3H7F, #3XA9T: Max uses `field().dataType().noText()`, but Min, Top, and Values each inline the same logic as `DataType t = field().dataType(); return t == TEXT ? KEYWORD : t;`. Since `noText()` was introduced in this very PR to encapsulate exactly this rule, the three inline copies are redundant and will diverge if the TEXT→KEYWORD policy ever needs to change (e.g., to also handle `SEMANTIC_TEXT`). For consistency and a single source of truth, all four should use `noText()`.

#Z6MZ4, #3WJ1S: Removing `entry(TEXT, ToString::new)` from `EsqlDataTypeConverter` means an explicit cast like `1::text` will no longer resolve to a converter. The test in `#3WJ1S` previously mapped TEXT→KEYWORD before the lookup, so it exercised the `::text` path; now it simply skips TEXT via the `converterFunctionFactory(...) == null` guard. This leaves the `::text` cast path untested. If the parser/analyzer is expected to rewrite `::text` to `::keyword` upstream, a test asserting that rewrite would be valuable. If it is *not* expected to, then `::text` will now fail at analysis time, which is a user-facing breaking change worth an explicit test (or at minimum a comment in the capability description) to document the behavior.
