#BS4TA: The `getDeclaredVersions()` method has a logic error in the modifier check:
```java
if (false == Modifier.isStatic(mod) && Modifier.isFinal(mod) && Modifier.isPublic(mod)) {
    continue;
}
```
This only skips fields that are *non-static AND final AND public*. It does NOT skip fields that are, for example, `static` but not `final`, or `public` but not `static`. The intent is clearly to only process `public static final` fields. The condition should be:
```java
if (Modifier.isStatic(mod) == false || Modifier.isFinal(mod) == false || Modifier.isPublic(mod) == false) {
    continue;
}
```
As written, a `public static` (non-final) field of type `SqlVersion` would be incorrectly included in the version list.

#BS4TA: Two issues in `getNextVersion`:
1. The error message says `"couldn't find any released versions before [" + version + "]"` but this method finds the *next* (later) version. It should say "after".
2. There is no guard against a negative `binarySearch` result (version not found in the list). If `index` is negative, the check `index >= DECLARED_VERSIONS.size() - 1` is false, and the code proceeds to `DECLARED_VERSIONS.get(index + 1)`, which will either return the wrong element (e.g., `get(0)` when `index == -1`) or throw an `ArrayIndexOutOfBoundsException`. Compare with `getPreviousVersion` which correctly handles this via `if (index < 1)`.

#BS4TA: `getAllVersions()` returns the internal `DECLARED_VERSIONS` list directly. Since it is a `static final` field holding a mutable `ArrayList`, any caller can mutate the shared list. Consider returning `Collections.unmodifiableList(DECLARED_VERSIONS)` or `List.copyOf(DECLARED_VERSIONS)` to prevent accidental mutation.

#BG122, #R5HVG: `BaseRestSqlTestCase` defines its own `getServerCompatVersion()` and `SERVER_COMPAT_VERSION` that are logically identical to `SqlVersionUtils.SERVER_COMPAT_VERSION` (diff #8V8YQ). This duplicates the try/catch fallback logic. Prefer reusing `SqlVersionUtils.SERVER_COMPAT_VERSION` directly to keep a single source of truth for the "server compat version" concept.

#6HNT2: The old code stripped a `-SNAPSHOT` suffix before parsing:
```java
String jdbcDriverVersion = System.getProperty(DRIVER_VERSION_PROPERTY_NAME, "").replace("-SNAPSHOT", "");
```
The new code removes that workaround:
```java
String jdbcDriverVersion = System.getProperty(DRIVER_VERSION_PROPERTY_NAME, "");
JDBC_DRIVER_VERSION = jdbcDriverVersion.isEmpty() ? CURRENT : SqlVersion.fromString(jdbcDriverVersion);
```
If a test environment sets `jdbc.driver.version` to a value like `8.16.0-SNAPSHOT`, `SqlVersion.fromString` may fail where the old code succeeded. If this is intentional (i.e., the property is guaranteed to be a clean SemVer in all supported environments), consider adding a brief comment noting that assumption, or retaining the `.replace("-SNAPSHOT", "")` as a safety net.

#XAN62: The loop calls `SqlVersions.getNextVersion(version)` on each iteration. If the version list ever changes such that the version just before `INTRODUCING_VERSION_COMPATIBILITY` is the last entry in the list, `getNextVersion` will throw (as noted in the `getNextVersion` issue above). A `while`-loop with an explicit bounds check or using `getPreviousVersion` in reverse would be more robust, but given the current fixed version list this is low-risk.
