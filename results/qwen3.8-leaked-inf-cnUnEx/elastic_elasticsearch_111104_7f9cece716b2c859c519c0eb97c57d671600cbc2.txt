#CKG9MA9KBPH7, #1TM0E5Y42260, #R5PDNCTR8TVG: The new `Async-running` header uses `String.valueOf(boolean)` → `"true"` / `"false"`, while the pre-existing `X-Elasticsearch-Async-Is-Running` header (checked in the test via `supportsAsyncHeaders`) uses the `"?1"` / `"?0"` convention. Two headers conveying the same semantic with different value formats in the same response can be confusing for API consumers and for the test assertions that check both. Consider aligning the value format, or documenting the intentional difference.

#FVEHM70KTJHF: In the "still running" branch for text formats, `initialValues` is set to `null` for CSV and TSV but left as an empty `String` for TXT. Both paths ultimately skip the later `assertEquals(initialValues, result)` comparison (null → skip, empty string → `.isEmpty()` guard skips), so the behavior is correct. However, the asymmetry makes the intent harder to follow. Setting `initialValues = null` uniformly across all three text formats (or leaving it as-is uniformly) would make the "discard the partial body" intent consistent.

#NCYK1F2X1RAY: The new constructor calls `restRequest.param("id")`, which marks the parameter as consumed in `RestRequest`. If any downstream code in the request pipeline also calls `restRequest.param("id")` or `restRequest.hasParam("id")` expecting the parameter to still be available, it will get `null` / `false`. Verify that no other handler or filter in the async-get path relies on reading the `id` parameter after the listener is constructed.
