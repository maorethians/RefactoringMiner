#6310A: Removes the `BinaryPlan.computeReferences()` override that returned `Expressions.references(output())`.
This is a significant behavioral change. The old implementation returned references covering *all* output columns of the join. The new inherited implementation (from `QueryPlan`) is not shown here, but per the Javadoc in #CP3WV it "must not rely on calls to `output()`". If the parent's default collects references only from child plans and config expressions (match/left/right fields), then `join.references()` will no longer include all output columns. Any downstream logic that uses `plan.references()` for column pruning, field resolution, or index resolution on a `Join` node may silently lose columns. Please verify that no caller depends on the old "all output columns" semantics.

#17YXX, #CP3WV: Javadoc additions clarifying `output()` and `computeReferences()` contracts. Good documentation, no issues.

#CJW50: Rewrites `Join.computeOutput` to filter match-field names from the non-dominant side before merging.
The filtering logic is correct for SQL `USING` semantics (LEFT preserves left-side join key, RIGHT preserves right-side join key). However, the `mergeOutputAttributes` method is not defined anywhere in this chapter. Its ordering and conflict-resolution behavior is critical here: for a LEFT join, the call is `mergeOutputAttributes(rightOutputWithoutMatchFields, leftOutput)`. If this method places the first argument before the second (analogous to the old `merge`), the output column order changes from "left columns first, then right" to "right columns first, then left". Please confirm the intended column ordering matches what the test expectations (e.g., #KQ0EE) and downstream consumers expect.

#NSX49, #1JEDR, #BA3FK, #2JNNB, #7P7C1, #WAPHZ, #FPV36, #KCGXS, #C5009: Systematic removal of the `output` field from `LookupJoin` and all its usages (constructors, `replaceChildren`, `info`, `hashCode`, `equals`). The `hashCode`/`equals` now inherit from `Join`, which hashes `config + left + right`. Since `output` was a pure function of those three, equality semantics are preserved. Clean.

#6Z3NX: `surrogate()` now uses `config()` directly instead of constructing a new `JoinConfig` with forced `LEFT` type.
This is safe given the analyzer enforces `LEFT` for `LookupJoin`, but it removes a defensive invariant. If a `LookupJoin` were ever constructed with a non-LEFT type (e.g., via deserialization or a future code path), the surrogate would silently produce a different join type. Consider adding an assertion or keeping the explicit `LEFT` to make the invariant explicit.
