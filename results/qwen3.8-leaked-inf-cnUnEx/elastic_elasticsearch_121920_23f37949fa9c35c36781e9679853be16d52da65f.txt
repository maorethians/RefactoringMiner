#A91RP, #3KYB6: The `bytes` field in `MemoryAccountingBytesRefCounted` and `accumulatedBytesInLeaf` in the `FetchPhaseDocsIterator` are both `int`, while the `CircuitBreaker` API (`addEstimateBytesAndMaybeBreak`, `addWithoutBreaking`) operates on `long`. The `account(int bytes, ...)` method also takes `int`. Since `this.bytes` accumulates across all `account()` calls for the lifetime of the ref-counted object (i.e., all documents in a leaf until the `SearchHit` is released), a leaf with a very large total source size could overflow `int` (~2 GB). Using `long` throughout would be consistent with the `CircuitBreaker` contract and eliminate this risk. The `Consumer<Integer>` / `Supplier<Integer>` types would also need to become `Consumer<Long>` / `Supplier<Long>`.

#SCY82: Passing `memAccountingBufferSize = 0L` to `FetchPhase.execute` for inner hits makes the condition `accumulatedBytesInLeaf >= memAccountingBufferSize` always true (since `accumulatedBytesInLeaf` starts at 0). This means `enoughBytesOrLastDocInLeaf` is true for every single document, causing a `MemoryAccountingBytesRefCounted` object and a `LeakTracker.wrap(...)` to be allocated per document, even though the breaker is a `NoopCircuitBreaker` and all accounting is a no-op. For a fetch with many inner hits this is unnecessary allocation overhead. Consider passing a sentinel value (e.g. `Long.MAX_VALUE`) so the size-based condition is never met, or introducing an explicit "accounting disabled" flag that short-circuits the object creation in `prepareNonNestedHitContext`.

#WP7PB: The Javadoc contains two typos: "accummulate" should be "accumulated" and "executiong" should be "execution".
