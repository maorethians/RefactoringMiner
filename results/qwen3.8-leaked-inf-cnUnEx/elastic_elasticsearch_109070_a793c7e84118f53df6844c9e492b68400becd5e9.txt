#6F9AC: The fix to use `Integer.MAX_VALUE` as the split limit is correct — it preserves trailing empty strings that `String.split` would otherwise discard. This matters for version ranges like `"8.0.0-"` (open-ended upper bound).

#C98EW: **Bug: `ip.offset` is not accounted for in the byte-masking step.**
The `System.arraycopy` correctly uses `ip.offset` as the source position:
```java
System.arraycopy(ip.bytes, ip.offset, prefix.bytes, 0, fullBytes);
```
But the subsequent masking step reads from the wrong index:
```java
prefix.bytes[fullBytes] = (byte) (ip.bytes[fullBytes] & lastByteMask);
```
This should be:
```java
prefix.bytes[fullBytes] = (byte) (ip.bytes[ip.offset + fullBytes] & lastByteMask);
```
`BytesRef` objects frequently carry a non-zero `offset` (e.g., when they are a view into a larger backing buffer from a block or network read). The existing tests pass only because `EsqlDataTypeConverter.stringToIP` produces a `BytesRef` with `offset == 0`. In production, this will silently mask the wrong byte.

#YV8VY: **Potential NPE when `IpPrefix.process` returns `null`.**
`process` returns `null` when `prefixLength < 0` or `prefixLength > 128`. Both `eval` overloads call `result.appendBytesRef(IpPrefix.process(...))` without a null check. If the input `prefixLength` is out of range (e.g., a negative literal or a value > 128 that passed type resolution as an integer), `appendBytesRef(null)` will likely throw a `NullPointerException` inside the builder.
Suggested fix in both `eval` methods:
```java
BytesRef result = IpPrefix.process(ipBlock.getBytesRef(...), prefixLengthBlock.getInt(...));
if (result == null) {
    result.appendNull();
} else {
    result.appendBytesRef(result);
}
```
(or equivalent for the vector variant).
