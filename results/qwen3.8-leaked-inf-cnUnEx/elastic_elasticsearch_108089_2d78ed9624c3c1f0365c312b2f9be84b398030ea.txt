#1VVZJ, #63968: The depth counter is incremented *before* the `try/finally` block, so if the `> MAX_EXPRESSION_DEPTH` check throws, the counter is left in an incremented state and never decremented:
```java
expressionDepth++;
if (expressionDepth > MAX_EXPRESSION_DEPTH) {
    throw new ParsingException(...);   // counter is never rolled back
}
try {
    return typedParsing(this, ctx, Expression.class);
} finally {
    expressionDepth--;
}
```
In practice this is harmless because the `ParsingException` aborts the entire parse. However, it makes the invariant "depth is always balanced" depend on the exception propagating uncaught. A slightly more robust pattern would move the check inside the `try` block:
```java
expressionDepth++;
try {
    if (expressionDepth > MAX_EXPRESSION_DEPTH) {
        throw new ParsingException(...);
    }
    return typedParsing(this, ctx, Expression.class);
} finally {
    expressionDepth--;
}
```
This guarantees the counter is always restored regardless of how the exception is handled upstream, and keeps the "increment/decrement" pairing atomic. The same applies to `queryDepth` in `visitCompositeQuery`.

#1VVZJ: The error message references `ctx.getParent().getText()`. For a deeply nested expression (which is exactly the scenario this guard protects against), the parent's text can be extremely long, producing a very large error string. Consider truncating or using a shorter identifier (e.g., `ctx.getText()` of the immediate node, or just the rule name) to keep the error message bounded.
