#AWXXJ: In `parseDocForMissingValues`, after encoding a matched field's value, the code does:
```java
parser.nextToken();  // Advance the parser to the value to be read.
result.add(leaf.cloneWithValue(XContentDataHelper.encodeToken(parser)));
parser.nextToken();  // Skip the token ending the value.
```
The comment "Skip the token ending the value" implies `encodeToken` does not advance the parser past the value. However, `encodeToken` is also used in the existing `parseNonDynamicArray` `else`-branch to encode entire objects (e.g., disabled objects), where it must serialize the full subtree. If `encodeToken` internally consumes the full value (advancing the parser past it), then the second `parser.nextToken()` here would skip an additional token, corrupting the parse position for subsequent iterations. Conversely, if it does not advance, then encoding a complex value (object/array) from just the START token would produce incomplete output — yet the test in `#HNN4W` expects full objects/arrays to be captured.
Please verify the parser position contract of `XContentDataHelper.encodeToken` and confirm the advancement logic here is correct for both simple values and nested objects/arrays. If `encodeToken` does advance the parser, the second `nextToken()` should be removed; if it does not, the encoding of complex values needs a different mechanism (e.g., `cloneSubContext` + `encodeXContentBuilder`).

#5BE15, #97VX9: The array-deferral logic in `addIgnoredFieldFromContext` checks:
```java
parentArrayField != null
    && parent != null
    && parentArrayField.equals(parent.fullPath())
    && parent instanceof NestedObjectMapper == false
```
This only triggers when the *immediate* parent's full path equals the tracked top-level array name. For a document like `{"a": [{"b": [{"c": 1}]}]}`, the inner array's elements have parent `"a.b"`, which does not equal `"a"`, so they fall into the immediate-encoding `else` branch. This means nested arrays always use the old clone-and-encode path while the outer array uses deferred encoding. If the intent is that *all* array elements at any depth should be deferred (to avoid the "ignored source takes precedence" issue mentioned in the Javadoc), this condition may be too narrow. If it's intentional that only the top-level array is deferred, the Javadoc on `addIgnoredFieldFromContext` ("In case of nested arrays… all array elements get recorded in ignored source") is misleading — nested array elements are *not* recorded via `ignoredFieldsMissingValues`.
