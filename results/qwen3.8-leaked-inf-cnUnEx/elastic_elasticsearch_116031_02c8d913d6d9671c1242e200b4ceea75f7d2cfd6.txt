#W982J: The `resolvedPipelineCache` is keyed solely by `indexRequest.index()`, but `resolveStoredPipelines` also depends on `actionRequest` (the original request). Specifically, `resolvePipelinesFromMetadata` uses `originalRequest.index()` as a separate lookup path (for upserts modeled differently). If two entries in the same bulk have the same `indexRequest.index()` but different `actionRequest.index()`, the second entry would incorrectly reuse the first entry's cached resolution. While in the current codebase `actionRequest.index()` and `indexRequest.index()` are typically identical, the cache key should either include both indices or the code should document/assert this invariant to prevent a latent correctness bug if the relationship ever changes.

#EJ6VS: When `requestPipeline` is non-null, the code calls `indexRequest.setPipeline(requestPipeline)` which is a no-op (setting the field to its current value). The branch can be simplified to only act when the pipeline is absent:
```java
if (indexRequest.getPipeline() == null) {
    indexRequest.setPipeline(resolvedPipelines.defaultPipeline);
}
indexRequest.setFinalPipeline(resolvedPipelines.finalPipeline);
indexRequest.isPipelineResolved(true);
```
This removes the redundant write and makes the intent ("only fill in the default if the caller didn't specify one") clearer.
