#AS5KT: The core change replaces `Expressions.references(p.expressions())` with `p.references()`. This is a semantically more correct choice: `QueryPlan.references()` is the plan's canonical API for its input requirements (and its Javadoc explicitly states it "Excludes generated references"), whereas `Expressions.references(p.expressions())` ad-hoc collects references from the plan's expressions, which can include both inputs and outputs. Using the plan's own API is more consistent with the rest of the codebase and also benefits from the `lazyReferences` caching in `QueryPlan`, avoiding a fresh `AttributeSet` allocation on every iteration of the `forEachDown` traversal.
One thing worth confirming: the guard clause `planRefs.names().contains(alias.name())` is meant to protect legitimate self-referencing patterns like `RENAME id = id` or `STATS id = MAX(id)`. Since `p.references()` excludes generated references, verify that in those cases the *input* `id` (the one inside `MAX(id)` or the source of the rename) is still present in `p.references()`. If a particular plan implementation's `computeReferences()` were to treat the alias name as "generated" and exclude it, the guard would no longer fire and the UnresolvedAttribute would be incorrectly removed. Given the capability flag `FIX_STATS_BY_FOLDABLE_EXPRESSION_2` targets a specific regression, this is likely already covered by the associated test, but it's the key behavioral delta to be aware of.
