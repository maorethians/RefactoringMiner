#BDPYD: The `parseDocForMissingValues` method has a path-tracking issue:
The `path` list is only appended to when a `START_OBJECT`/`START_ARRAY` is encountered with a non-null `fieldName`, but it is unconditionally popped on every `END_OBJECT`/`END_ARRAY`. For objects that are *elements of an array* (which have no field name), the corresponding `END_OBJECT` still pops the path, corrupting it for subsequent siblings. For example, given `{"arr": [{"x":1}, {"target": 2}]}` with target `"arr.target"`, after the first element's `END_OBJECT` the path is incorrectly emptied, so `"target"` in the second element resolves to `"target"` instead of `"arr.target"`.
In the current call sites the target is always resolved at the `FIELD_NAME` level (encoding the next token as the whole structure), so this latent bug is not triggered today. However, the method is general-purpose and would silently fail if a future use case requires locating a leaf *inside* a later array element.

#G15RZ: Two concerns:
1. A full `RootDocumentParserContext` is constructed (allocating a `LuceneDocument`, computing nested-doc limits, etc.) solely to obtain a parser for `parseDocForMissingValues`, which only calls `context.parser()`. Passing the `XContentParser` directly (or a lighter wrapper) would avoid the unnecessary allocation.
2. This second pass re-parses the entire document source. For large documents with only one or two missing-value fields, this is a non-trivial cost incurred on every index operation. Consider whether the `parentNames` skip optimization is sufficient, or whether a more targeted extraction (e.g., using the original parser's position recorded during the first pass) would be preferable.
