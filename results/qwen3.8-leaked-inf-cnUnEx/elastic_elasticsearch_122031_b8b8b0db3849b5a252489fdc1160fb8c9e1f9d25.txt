#0KQ5D: The `response.isEmpty() == false` guard for logging hot threads is imprecise. The `/_tasks` response will always contain a `"nodes"` key (e.g. `{"nodes": {}}`), so `response.isEmpty()` will be `false` even when the assertion is about to pass. This means `hotThreads()` will be called and a warning logged on every successful iteration, adding unnecessary HTTP overhead and noise to the test output. A more targeted check would be to inspect whether the `"nodes"` value is a non-empty map before logging, e.g.:
```java
Object nodes = response.get("nodes");
if (nodes instanceof Map && ((Map<?, ?>) nodes).isEmpty() == false) {
    logger.warn("search still running, hot threads:\n{}", hotThreads());
}
```

#KM0Z6: The nested `assertBusy` pattern (outer 1-minute timeout wrapping an inner default 10-second timeout) is intentional per the Javadoc, but it means the total wall-clock time can exceed the outer timeout by up to the inner timeout (≈ 70 s in the worst case). More importantly, the inner `assertBusy` will exhaust its full 10-second retry budget on every outer iteration before the outer loop gets a chance to back off and retry. This makes the effective polling cadence coarser than the outer timeout suggests. Consider whether a single `assertBusy` with a 1-minute timeout and the hot-threads logging inside the lambda would achieve the same goal with simpler semantics and a tighter time bound.
