#9MN5T, #708CD: The second traversal in `findLookupIndexNames` walks `Join.right()` for *any* `Join` node in the fragment, not just LOOKUP JOINs. If a future plan shape introduces a non-lookup join whose right side is an `EsRelation`, those indices would be incorrectly excluded from the concrete-indices check in `#0RS18`. Consider narrowing the traversal to only match the specific join type used for LOOKUP JOINs on the data node (e.g., checking a join type discriminator or the `LookupJoinExec`-derived node type).

#0DQF2, #0NP45: The `validateTypes` method performs a strict string equality check between `fieldType.typeName()` and `inputDataType.typeName()`. This will reject queries where the types are semantically compatible but have different names (e.g., `integer` vs `long`, or `keyword` vs `text` in certain contexts). While the TODO acknowledges future implicit conversion support, consider whether the initial strict check should at least log a warning or include a more actionable error message suggesting which types are acceptable for the given field. As-is, a user who writes `LOOKUP JOIN ... ON int_field = long_field` gets a generic "incompatible" message without guidance on what would work.

#P8RRX: Replacing `fieldNames` with `Set.of("*")` is a behavioral change: previously, only the fields referenced in the query were used for lookup index resolution; now all fields are considered. If the lookup index has many fields, this could cause unnecessary field resolution work or, in edge cases, surface errors for fields that exist in the index but are not relevant to the query. The comment justifies this with the current syntax limitation, but it would be helpful to add a brief note that this is intentionally broader than the ENRICH path (which still uses `fieldNames`) to avoid confusion for future maintainers comparing the two code paths.
