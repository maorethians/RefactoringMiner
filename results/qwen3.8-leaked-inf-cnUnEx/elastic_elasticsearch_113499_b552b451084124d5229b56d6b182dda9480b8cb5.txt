#YGVPT: The `keyedIgnoredValuesFieldFullPath` field can be `null` (set to `null` in `#BQN1X` when `ignoreAbove == Integer.MAX_VALUE`). In `addField`, the code dereferences it inside the `value.length() > ignoreAbove` guard:
```java
if (value.length() > ignoreAbove) {
    if (context.documentParserContext().mappingLookup().isSourceSynthetic()) {
        fields.add(new StoredField(keyedIgnoredValuesFieldFullPath, bytesKeyedValue));
    }
    return;
}
```
This is safe *only* because `String.length()` (an `int`) can never exceed `Integer.MAX_VALUE`. The null-safety relies entirely on the implicit invariant that `ignoreAbove == Integer.MAX_VALUE` implies the branch is unreachable. A defensive `assert keyedIgnoredValuesFieldFullPath != null` or an explicit null check would make the contract explicit and protect against future refactoring that might reorder or modify the guard condition.

#YGVPT: The key validation (SEPARATOR check) has been moved *before* the `ignore_above` early-return. Previously, a value exceeding `ignore_above` would return before the key was ever validated. Now, a document containing a key with `\0` *and* a value exceeding `ignore_above` will throw `IllegalArgumentException` where it previously indexed successfully (silently ignoring the value). This is a behavioral change that could break existing indices on reindex. If intentional, it's a reasonable tightening, but it's worth confirming it won't cause regressions for users with edge-case data.

#GV5GH: The comparator `Comparator.comparing(IndexableField::name).thenComparing(IndexableField::binaryValue)` will throw `NullPointerException` if any `IndexableField` in the comparison has a null `binaryValue()`. While stored fields always have a binary value, the method signature `IndexableField::binaryValue` is not guaranteed non-null for all field types. Using `Comparator.nullsLast(Comparator.naturalOrder())` for the second key would make this robust:
```java
Comparator.comparing(IndexableField::name)
    .thenComparing(IndexableField::binaryValue, Comparator.nullsLast(Comparator.naturalOrder()))
```

#A45Q6: The merge logic in `DocValuesWithIgnoredSortedKeyedValues.next()` uses `ignoredCandidate.compareTo(currentFromDocValues) <= 0` to decide which value to emit. This means if an ignored value is byte-identical to a doc value, the ignored copy is emitted first. While this shouldn't occur in practice (a value is either in doc values *or* stored as ignored, never both), the `<=` rather than `<` is worth a brief comment to document the tie-breaking intent, since it affects the output ordering in the synthetic source.

#P0R13: The `write()` method mutates `ignoredValues` to `List.of()` after consuming it into the `TreeSet`. This "consume-once" semantics means a second call to `write()` for the same document would silently drop the ignored values. The `reset()` method also sets it to `List.of()`, which is consistent, but the dual mutation sites (in `write()` and `reset()`) make the lifecycle slightly harder to reason about. Consider whether the reset in `write()` is necessary given that `reset()` is the documented lifecycle hook, or add a brief comment explaining why it's cleared here.
