#2B020, #1HKDY, #7JRNV: The three diffs consistently gate the legacy POP path behind `!brokerConfig.isPopConsumerKVServiceEnable()`, which is a clean way to route POP consumers to the standard offset path when the KV service is active. The logic is sound.

#7JRNV: The removal of the `pullOffset = brokerOffset` fallback is a behavioral change worth calling out. In the old POP path (now guarded by `!isPopConsumerKVServiceEnable()`), if both `popBufferMergeService.getLatestOffset(...)` and `offsetManager.queryOffset(...)` return a negative value, `pullOffset` will remain negative and flow into whatever downstream calculation `getAvailableMsgCount` performs (e.g., `brokerOffset - pullOffset`). A negative `pullOffset` will inflate the available-message count rather than yielding zero.
Notably, the sibling method `getConsumerLagStats` (#2B020) still retains the `pullOffset = brokerOffset` fallback in its POP branch. If the intent is that "no offset found → treat as fully caught up (lag = 0 / available = 0)", then #7JRNV should keep the fallback for consistency. If the intent is to signal an unknown/invalid state via a negative value, then #2B020 should also drop its fallback and callers should guard against negative offsets. Either way, the two methods now disagree on how to handle the "no offset anywhere" case for the same consumer, which is likely to produce confusing metrics.
Please confirm the intended semantics and align the two methods, or add a brief comment explaining why `getAvailableMsgCount` intentionally omits the fallback.
