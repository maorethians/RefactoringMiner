#EJWNX, #2XFNV: **Unit conversion bug:** The parameter `maxTaskProcessingQuantumMs` is in milliseconds, but when a non-zero value is provided, it is assigned directly to `maxTaskProcessingQuantumNs` (nanoseconds) without conversion. The default constant `DEFAULT_MAX_TASK_PROCESSING_QUANTUM_NS` is correctly converted via `TimeUnit.MILLISECONDS.toNanos(...)`, but the user-supplied value is not.
For example, if a caller passes `1000` (intending 1000 ms), the field will hold `1000` nanoseconds instead of `1_000_000_000` nanoseconds, making the time budget effectively zero.
The fix should be:
```java
this.maxTaskProcessingQuantumNs =
        ObjectUtil.checkPositiveOrZero(maxTaskProcessingQuantumMs, "maxTaskProcessingQuantumMs") == 0 ?
                DEFAULT_MAX_TASK_PROCESSING_QUANTUM_NS
                : TimeUnit.MILLISECONDS.toNanos(maxTaskProcessingQuantumMs);
```

#PC2PV: The call `runAllTasks(maxTaskProcessingQuantumNs)` now passes a time-based budget (nanoseconds) where previously a task-count limit (`maxTasksPerRun`, an `int`) was passed. This is a semantic change to the `runAllTasks` contract. Please verify that the `runAllTasks` implementation (and any callers or overrides outside this chapter) has been updated to interpret the parameter as a time quantum in nanoseconds rather than a maximum task count, and that the Javadoc for that method reflects the new meaning.
