#Q84DW: The error message `"Failed to parse object: expecting value token but found [%s]"` is misleading when this guard is triggered from `extractArray` (i.e., the offending token is inside an array, not an object). A caller reading the message would look for an object-parsing issue. Consider a context-neutral phrasing such as `"expecting a value token but found [%s]"` (dropping the "Failed to parse object" prefix), or passing the enclosing context into the method.

#MY02Y: Comparing binary TSID values via `BytesRef.toString()` is fragile: `toString()` decodes the byte array as UTF-8, which is a lossy/undefined transformation for arbitrary binary data. Two distinct byte sequences could theoretically map to the same decoded string (e.g., different invalid-UTF-8 replacement patterns). For a distinctness assertion on binary data, compare the raw bytes instead, e.g.:
```java
List<byte[]> tsids = docs.stream()
    .map(doc -> doc.rootDoc().getBinaryValue("_tsid").bytes)
    .distinct()
    .collect(Collectors.toList());
```
or use `Arrays.equals`-based deduplication. This makes the test robust regardless of the binary content.
