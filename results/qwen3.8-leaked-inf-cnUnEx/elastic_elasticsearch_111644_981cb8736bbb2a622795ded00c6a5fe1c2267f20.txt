#CWST9, #HAP8A: The new guard `if (lastUsedCell == mean.length - 1)` correctly prevents an `ArrayIndexOutOfBoundsException` in the `else` branch (where `lastUsedCell++` would go out of bounds). However, note that this guard silently overrides the "force first and last centroid to never merge" rule set two lines above. When the cell array is full, the first and last incoming centroids will be merged into the last cell, which can degrade tail-quantile accuracy. This is an acceptable safety trade-off, but it may be worth a brief comment noting that this intentionally relaxes the first/last-centroid preservation guarantee when the buffer is exhausted.

#6KCHQ: The stress test is useful for catching the out-of-bounds scenario that the new guard in `#HAP8A` addresses. Two minor observations:
1. The quantile assertions are very loose for a uniform distribution on `[0, 3_600_000]`. The true 0.00001 quantile is ≈ 36, yet the bound is `< 100_000`; the true 0.99999 quantile is ≈ 3,599,964, yet the bound is `> 3_000_000`. Tightening these (e.g., `< 1_000` and `> 3_500_000`) would make the test more meaningful while still leaving room for t-digest approximation error.
2. 10 million `add()` calls in a single test can be slow in CI. Consider whether a smaller input size (e.g., 100k) with the same compression factor would still exercise the "cell array full" path, or add a `@Slow` / `@AwaitsFix` annotation if the project uses one.

#8GX27: Relaxing the tolerance from `0.2` to `0.25` is a reasonable fix for a flaky assertion, but it would be helpful to have a brief note (in the commit message or a nearby comment) explaining *why* the tolerance needed to increase—e.g., whether it's related to the `useAlternatingSort` default change or the new merge guard—so future readers understand the sensitivity of this assertion.
