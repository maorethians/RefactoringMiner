#39TYV, #7P34R, #4XYVB, #NTJ1G, #5VZQC: The `skipInnerHits` field is added to `SearchSourceBuilder` with a getter and setter, but it is not included in `SearchSourceBuilder`'s own serialization protocol (it is serialized separately by `ShardSearchRequest`). This means that after deserialization on a data node, `source.skipInnerHits()` will always return `false`, while `request.skipInnerHits()` correctly returns the transmitted value. Any code path that reads `source.skipInnerHits()` post-deserialization will silently get the wrong answer. Consider either (a) documenting the field as transient/internal-only, or (b) removing the field from `SearchSourceBuilder` entirely and passing the flag as a separate constructor parameter to `ShardSearchRequest`, to avoid the appearance of a serializable property that isn't.

#0SCF9, #7VK1J, #1S2DF, #1BVR7: `skipInnerHits(true)` is set both in `CompoundRetrieverBuilder.createSearchSourceBuilder` (unconditionally) and again in each child's `extractToSearchSourceBuilder` (guarded by `compoundUsed`). Since `createSearchSourceBuilder` always calls the child with `compoundUsed=true`, the child's assignment is always redundant. Pick one owner of this flag to avoid confusion about which layer is responsible for setting it. If the children's `extractToSearchSourceBuilder` is the canonical setter (because it's a public API that could be called from other contexts), then the unconditional set in `createSearchSourceBuilder` is the one to remove.

#E39XP: The `instanceof AbstractQueryBuilder` check silently skips any `QueryBuilder` that does not extend `AbstractQueryBuilder`, meaning inner hits defined on such a builder would be dropped without any warning. While in practice most query builders extend `AbstractQueryBuilder`, a silent no-op here could mask a real bug. Consider adding a debug/log statement for the skipped case, or asserting that all entries are `AbstractQueryBuilder` instances during development.
