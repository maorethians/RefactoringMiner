#TM62A: The test `testMustRewrite` now passes `VECTOR_DIMENSION` as the `k` parameter (previously it was `numCands`). While this doesn't affect the test's correctness (the rewrite is triggered by dimension mismatch before k/numCands matter), using a dimension constant as a result-count parameter is semantically confusing and could mislead future readers. Consider using a more neutral value like `1` or `10` to make the intent clearer.

#5KH4K: The test `testKLessThanNumCands` covers the `numCands < k` validation, but there is no corresponding test for the `k < 1` boundary (e.g., `k = 0` or `k = -1`). Adding a small test case for that path would improve coverage of the validation logic in the constructor.

#XYGH9: When `k` is set, it is used as `requestSize` to compute `adjustedNumCands` (when `numCands` is null), and also passed directly to the Lucene query as the final merge limit. This means `k` implicitly bounds the per-segment candidate collection to `min(NUM_CANDS_MULTIPLICATIVE_FACTOR * k, NUM_CANDS_LIMIT)`. This is reasonable, but it may be worth a brief code comment at the `requestSize = k` assignment explaining that `k` doubles as the basis for the default `numCands` derivation, since the dual role is not immediately obvious.
