#TT2RG: The catch block assumes the `ResponseException` response body always contains an `error_message` field at the top level. If the server returns a different error shape (e.g., a 500 with a different body structure), `ObjectPath.evaluate(responseBody, "error_message")` will throw an `IOException` that obscures the original failure. Consider adding a guard or a more descriptive assertion message so that unexpected error responses produce a clearer test failure than a raw `IOException` from path evaluation.

#757HF: The `assertThat` call has the actual value and the matcher reversed relative to the project's convention. The standard pattern is `assertThat(actual, equalTo(expected))`, which yields a failure message like `"actual was X, expected keyword"`. Here it reads `assertThat("keyword", equalTo(mappingValue))`, producing the less intuitive `"keyword was not equal to <mappingValue>"`. Swapping to:
```java
assertThat(
    "incorrect k8s.pod.name field in mapping:" + mapping,
    ObjectPath.evaluate(mapping, "properties.k8s.properties.pod.properties.name.type"),
    equalTo("keyword")
);
```
makes the failure output show the actual (wrong) value first, which is easier to diagnose.
