#CF847, #CJW50: The output column ordering for LEFT joins changes significantly. The old code produced: `leftOutput` first, then `rightOutput` (with right overriding on name conflicts). The new code produces: `rightOutput` (minus match fields) first, then `leftOutput` (with left overriding on name conflicts).
For example, with `left = [id, a, b]` and `right = [id, c, d]`:
- Old result: `[right.id, left.a, left.b, right.c, right.d]`
- New result: `[right.c, right.d, left.id, left.a, left.b]`
This is a behavioral change in column ordering that could break any consumer (tests, downstream plan nodes, or user-facing column positions) that relied on the previous "left-first" ordering. If this reordering is intentional, it would be worth a brief note in the commit message or a comment explaining the new ordering rationale.

#CF847, #K6N7D: The analyzer now stores a plain `LEFT` join type in the config instead of wrapping it in `UsingJoinType`. In `EsqlSession.fieldNames` (#K6N7D), the branch:
```java
if (join.config().type() instanceof JoinTypes.UsingJoinType usingJoinType) {
    keepJoinReferences.addAll(usingJoinType.columns());
}
```
will no longer fire for lookup joins. While the field *names* are still captured via `matchFields` (since USING columns share names on both sides), this creates a silent coupling: if the right-side key attributes ever diverge in name from the left-side ones (e.g., after a future rename or aliasing change), they would silently drop out of `keepJoinReferences`. Consider whether the `rightFields` from the config should also be added to `keepJoinReferences` as a safety net, or add a comment explaining why `matchFields` alone is sufficient.

#6Z3NX: The `surrogate()` method previously forced the join type to `LEFT` when constructing the normalized `Join`:
```java
JoinConfig newConfig = new JoinConfig(LEFT, cfg.matchFields(), cfg.leftFields(), cfg.rightFields());
```
The new code passes `config()` directly. While the analyzer (#CF847) currently rejects non-LEFT types with an error, this removes a defensive guarantee. If a future code path constructs a `LookupJoin` with a non-LEFT type (bypassing the analyzer), `surrogate()` would now propagate it instead of normalizing to LEFT. A brief assertion or comment noting the invariant would make the dependency explicit.
