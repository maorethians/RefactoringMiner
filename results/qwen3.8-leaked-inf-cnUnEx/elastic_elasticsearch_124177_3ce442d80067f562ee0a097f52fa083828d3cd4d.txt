#9J41C, #27TGF, #6XMWW, #MJ3TG: The boundary regex `(^|[\\s,])` / `([\\s,]|$)` only matches when the token name is adjacent to whitespace, a comma, or a string boundary. ANTLR error messages can also present token names inside set notation or adjacent to other punctuation, e.g. `expecting { 'LP', 'RP' }` or `expecting 'LP'`. In those cases the character immediately before/after the token name is `'` or `{`/`}`, which the regex does not cover, so the replacement would silently be skipped. If the current tests pass, the specific ANTLR version in use may not produce those forms, but the fix is fragile against ANTLR version upgrades or different error-message templates. Consider broadening the boundary to something like `(^|[^A-Za-z0-9_])` / `([^A-Za-z0-9_]|$)` to match any non-identifier character, or to explicitly include the characters ANTLR actually uses (`'`, `{`, `}`, `,`, whitespace).

#27TGF, #6XMWW, #MJ3TG: Only `LP` and `OPENING_BRACKET` are handled. If ANTLR reports other tokens by symbol name in error messages (e.g. `RP`, `CLOSING_BRACKET`, or any future token), they will leak through. A more maintainable approach would be to build the replacement list from a single map (token-name → display-character) and iterate over it, so adding a new token is a one-line change rather than a new `Pattern` field plus a new `matcher`/`replaceAll` block.

#9J41C, #K2SDV, #27TGF, #6XMWW: `BEFORE_REGEX`, `AFTER_REGEX`, `BEFORE_REPLACEMENT`, `AFTER_REPLACEMENT`, `REPLACE_LP`, and `REPLACE_LEFT_BRACKET` are all immutable and shared across instances. Declaring them `static final` (or moving them to a companion/constants class) makes the intent clearer and avoids re-creating the `Pattern` objects per parser instance.
