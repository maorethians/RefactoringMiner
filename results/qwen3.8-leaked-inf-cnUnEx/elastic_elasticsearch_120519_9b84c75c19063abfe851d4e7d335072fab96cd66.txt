#HEXW9: The condition `queryList.block.getValueCount(queryPosition) == 1` reaches into the `protected` field `block` of `QueryList` from a sibling class in the same package. While this compiles (same-package access to `protected`), it bypasses the `QueryList` API and couples `EnrichQuerySourceOperator` to the internal representation of `QueryList`. If `QueryList` later wraps or transforms the block (e.g., for caching, lazy evaluation, or a different backing store), this access would silently break the contract. Consider adding a `getValueCount(int position)` method to `QueryList` that delegates to `block.getValueCount(position)`, and calling that instead.

#J3MVA, #8J0NN: The capability `JOIN_LOOKUP_SKIP_MV` is declared but I don't see it being checked anywhere in the code path that leads to `LookupFromIndexService` passing `true` for `skipMultiValues`. If the intent is to gate this behavior behind the capability (so that older clients or mixed-version clusters don't unexpectedly change semantics), the check should be applied before the `true` is passed — for example in the query planner or in `LookupFromIndexService`'s constructor. As written, `LookupFromIndexService` unconditionally enables the skip behavior regardless of the capability state.
