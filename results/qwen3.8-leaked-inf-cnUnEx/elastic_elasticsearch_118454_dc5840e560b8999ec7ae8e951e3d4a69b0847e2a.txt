#NK6R7, #8WBBE: Both concrete classes add an identical `fold()` that delegates to `EvaluatorMapper.super.fold()`. Looking at the `EvaluatorMapper.fold()` default implementation (provided as a dependency), it creates an evaluator whose `eval` method calls `e.fold()`, where `e` is the expression supplied by `toEvaluator`. If `toEvaluator` supplies the same `RLike`/`WildcardLike` instance, the call chain becomes:
`RLike.fold()` → `EvaluatorMapper.super.fold()` → evaluator.eval() → `e.fold()` → `RLike.fold()` → …
This would be infinite recursion. The Javadoc on `EvaluatorMapper.fold()` says the evaluator "will always call `Expression#fold`," which reinforces this concern. Please verify that `toEvaluator` does not feed the same expression back into the lambda, or that there is a guard preventing the re-entrant call. If `e` is guaranteed to be a *child* expression (e.g., the field), the recursion risk is gone, but the evaluator's `eval` would then only return the folded field value rather than the regex-match `Boolean`, which would be a type/logic mismatch with the `(Boolean)` cast.
