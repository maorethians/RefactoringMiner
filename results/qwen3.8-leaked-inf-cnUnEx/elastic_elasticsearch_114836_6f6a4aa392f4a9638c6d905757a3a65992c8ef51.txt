#ERT8G, #MFTP9, #VGVS5: The `if (leftCount == 1 && rightCount == 1)` block should be followed by `else` before the nested `for` loops, consistent with `distancePointDocValuesAndConstant` (#VGVS5) and `distanceSourceAndSource` (#MFTP9). As written, the single-value case computes the distance twice — once in the `if` and once in the loops. While not a correctness bug (the second computation yields the same value and `value < distance` is false), it's wasteful and inconsistent with the sibling methods.

#XYF3W, #BR14Y, #YWP6D, #K1M99, #F26NT: The `@Evaluator` annotation for `processCartesianPointDocValuesAndSource` lacks `warnExceptions`, unlike its Geo counterpart `processGeoPointDocValuesAndSource` (#YWP6D) which declares `warnExceptions = { IllegalArgumentException.class }`. Consequently, the generated evaluator in #BR14Y has no try/catch around the call to `StDistance.processCartesianPointDocValuesAndSource(...)`. Since `fromBytesRef` (which parses WKB geometry) can throw `IllegalArgumentException` for malformed input, an uncaught exception would propagate and abort the query. Compare with #K1M99 (GeoPointDocValuesAndSource) and #F26NT (CartesianSourceAndSource), both of which properly wrap the call in try/catch. The annotation should be:
```java
@Evaluator(extraName = "CartesianPointDocValuesAndSource", warnExceptions = { IllegalArgumentException.class })
```

#RST93, #4B9TK, #CDXDY, #QQYRX, #BR14Y, #K1M99, #F26NT, #BF1ZZ: In the single-block evaluators (e.g., #RST93), the null check is:
```java
boolean allBlocksAreNulls = true;
if (!leftBlock.isNull(p)) {
    allBlocksAreNulls = false;
}
if (allBlocksAreNulls) {
    result.appendNull();
    continue position;
}
```
This is logically equivalent to `if (leftBlock.isNull(p))` — the intermediate boolean adds no value for the single-block case. More importantly, when `leftBlock` is NOT null but `getValueCount(p) == 0` (which is what `isNull` checks), the code proceeds to `StDistance.processCartesianPointDocValuesAndConstant` which handles `valueCount < 1` by appending null. This is correct but the `allBlocksAreNulls` pattern is misleadingly named for the single-block case — it's just checking one block. This is a minor readability concern; the pattern makes more sense in the two-block evaluators (#BR14Y, #K1M99, #F26NT, #BF1ZZ).
