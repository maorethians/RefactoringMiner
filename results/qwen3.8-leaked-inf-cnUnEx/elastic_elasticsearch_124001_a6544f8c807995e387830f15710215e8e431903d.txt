#BGD1E: The refactored single-pass loop changes the score-attribute handling subtly. The old code used `forEach` and added **every** attribute matching `_score`:
```java
plan.output().forEach(attr -> {
    if (attr instanceof MetadataAttribute ma && ma.name().equals(MetadataAttribute.SCORE)) {
        attributes.add(ma);
    }
});
```
The new code keeps only the **last** one found (since `score` is overwritten on each match) and adds a single instance. If the plan can ever carry more than one `_score` attribute, this is a behavioral regression. If it's guaranteed to be at most one, consider adding a brief comment or an assertion to document that invariant, so a future reader doesn't wonder why the loop overwrites rather than accumulates.
Additionally, the old tsid/timestamp lookup matched on `attr.name()` alone (no `instanceof` guard), while the new code requires `attr instanceof MetadataAttribute`. If a non-`MetadataAttribute` node could ever carry the name `_tsid` or `@timestamp`, the new code would silently skip it and the subsequent `IllegalStateException` would fire. This is likely safe in practice, but the tightening of the type check is worth a deliberate confirmation.

#SB2G4: Two observations on the `hasScoring` detection:
1. **Global flag applied per-fragment.** `hasScoring` is a single boolean computed across the entire plan, but it is then applied uniformly inside `transformUp(FragmentExec.class, …)`. If one fragment needs scoring and another does not, the non-scoring fragment still gets a `must` clause for the user filter, causing unnecessary scoring work. A per-fragment determination (e.g., checking whether the specific fragment's subtree contains a SCORE attribute) would be more precise.
2. **Two-pass detection is hard to follow.** The first pass walks the whole plan for `EsQueryExec.hasScoring()`, and the second (only if the first found nothing) walks `FragmentExec → fragment → EsRelation.output()` for a SCORE attribute. Since `EsQueryExec` is itself an `EsRelation`, the second pass is effectively a fallback for non-`EsQueryExec` relations (e.g. an `EsSourceExec` that survived optimization). Consider consolidating into a single traversal over `EsRelation` and checking `output()` uniformly, which would eliminate the need for the `hasScoring()` helper on `EsQueryExec` in this context and make the intent clearer.
