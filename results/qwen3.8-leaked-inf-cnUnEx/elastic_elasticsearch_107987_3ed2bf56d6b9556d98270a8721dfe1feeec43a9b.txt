#42A8K, #F6E8V: The `equals` method has a copy-paste bug: `tableName` is compared against `lookup.matchFields` instead of `lookup.tableName`. This means two `Lookup` nodes with different table names but the same match fields would incorrectly compare as equal.
```java
return Objects.equals(tableName, lookup.matchFields)  // should be lookup.tableName
    && Objects.equals(matchFields, lookup.matchFields)
    && Objects.equals(localRelation, lookup.localRelation);
```

#HFFJ1: In the `else` branch, the code resolves against `localOutput` again instead of `childrenOutput`. The comment says "check also the child output by resolving to it" but the code passes `localOutput`:
```java
// check also the child output by resolving to it
else {
    ne = maybeResolveAttribute(ua, localOutput);  // should be childrenOutput
}
```
This means if a match field is not found in the local relation, it will never be resolved against the child's output, defeating the purpose of the lookup join (matching fields from the main query against the lookup table).

#ABGW4: The loop bound is hardcoded to `10` instead of using `count`, and the `finally` block's guard `tables.size() != count` will be true whenever `count < 10`. This means the finally block closes all the `Block` resources, and then the method returns a map containing closed blocks. The loop should be `for (int i = 0; i < count; i++)`.
```java
int count = between(1, 10);
...
for (int i = 0; i < 10; i++) {  // should be: i < count
    tables.put(randomAlphaOfLength(i + 1), randomColumns());
}
```

#8ZPFC: The `Lookup` → `HashJoinExec` mapping passes `null` and `emptyList()` for all meaningful fields (`tableName`, `matchFields`, `matchValues`, `mergeValues`). The commented-out lines confirm this is a placeholder. Any query that reaches the physical planning phase with a `Lookup` node will hit NPEs or produce incorrect plans. This should either be a clear `UnsupportedOperationException` or the full mapping should be implemented before merging.

#GN7XH: The `ReplaceLookupWithJoin` optimizer rule hardcodes the join condition to `Literal.TRUE`, which produces a cross join (cartesian product) rather than an actual equi-join on the match fields. This will produce incorrect results (every row joined with every row in the lookup table) rather than matching on the specified columns. The condition should be constructed from `lookup.matchFields()`.

#VS06G: When a duplicate table name is detected, `tables.put(name, columns)` has already replaced the old entry with the new one. The code then closes the old columns and throws, but the new `columns` remain in the map with no way for the caller to clean them up (the exception propagates). This is a resource leak of the newly added columns' underlying `Block` memory.
