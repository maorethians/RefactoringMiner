#SNEZ0: The test method `testVisitGeoShapeWrap` calls `SpatialEnvelopeVisitor.visit(geometry, false)`, which disables longitude wrapping. This makes it functionally identical to `testVisitGeoShapeNoWrap` (except for the `hasAlt` parameter difference in geometry generation). The test name implies it exercises the wrapping code path, but it does not. This is likely a copy-paste error — the call should be `visit(geometry, true)` to actually test the wrapping logic. As written, the wrapping branch in `GeoPointVisitor.getResult()` (the `wrapLongitude == true` path) is never exercised by the shape-level tests.

#C1SAG: In `GeoPointVisitor.visitRectangle`, the method records only the min and max x values via `visitLongitude(minX)` and `visitLongitude(maxX)`, losing the directional span of the rectangle. Consider a geo rectangle from longitude -170 to 170 (a 340° span). The visitor records `minNegX=-170, maxNegX=-170, minPosX=170, maxPosX=170`. In `getResult()`, the unwrapped width is 340 and the wrapped width is 20, so it returns `Rectangle(170, -170, ...)` — a 20° box crossing the dateline. However, that 20° box does **not** contain the original 340° rectangle. The minimum bounding box of the input geometry should be the input itself.
This is a fundamental limitation of the accumulate-min/max visitor pattern: it cannot distinguish a rectangle that explicitly spans the "long way" from one that spans the "short way." One possible mitigation is to track whether any visited rectangle has a span > 180° and, if so, suppress the wrapping optimization in `getResult()`.

#SNEZ0: `testVisitCartesianPoints` and `testVisitGeoPointsNoWrapping` initialize their tracking variables with `Double.MAX_VALUE` / `-Double.MAX_VALUE`, while `testVisitGeoPointsWrapping` (and the implementation itself) uses `Double.POSITIVE_INFINITY` / `Double.NEGATIVE_INFINITY`. The tests still pass because `randomFloat()` and `randomPoint()` always produce finite values, but the inconsistency is confusing and could mask a bug if a test were ever modified to include `NaN` or infinite coordinates. Aligning all three tests to use `POSITIVE_INFINITY` / `NEGATIVE_INFINITY` would match the implementation and make the intent clearer.
