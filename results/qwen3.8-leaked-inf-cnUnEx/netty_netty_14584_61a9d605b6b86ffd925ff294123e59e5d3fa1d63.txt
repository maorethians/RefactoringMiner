#6V64K: The Javadoc directly above this field is now stale and misleading. It states:
- "The default size is {@link NettyRuntime#availableProcessors()}"
- "the maximum number of magazines is twice this"
- "the maximum amount of memory … is 5 * {@link NettyRuntime#availableProcessors()} * {@link #MAX_CHUNK_SIZE} bytes"
With the `Math.min(2, …)` cap, the effective default is `min(2, availableProcessors())`, the max magazine count is at most 4, and the memory bound is at most `5 * 2 * MAX_CHUNK_SIZE`. The comment should be updated to reflect the new cap so that readers are not led to believe the old (uncapped) sizing still applies.

#6V64K: The `Math.min(2, …)` wrapper silently clamps the value of the `io.netty.allocator.centralQueueCapacity` system property to 2, even when an operator explicitly sets a higher value (e.g. `=16`). There is no log warning or documentation of this upper bound. Consider either:
1. Logging a warning when the requested value exceeds the cap (similar to how `SystemPropertyUtil.getInt` warns on parse failures), or
2. Documenting the cap in the Javadoc so that users of the system property are aware of the effective maximum.
Without one of these, the override appears to work but is silently ignored, which can be confusing during capacity tuning.
