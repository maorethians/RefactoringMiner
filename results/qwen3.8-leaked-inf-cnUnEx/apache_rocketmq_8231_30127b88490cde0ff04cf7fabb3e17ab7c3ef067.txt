#QR74G, #0R09S: When `StringUtils.isNotBlank(request.getGroup().getName())` is `false`, `result` remains `null`. This means a `NotifyClientTerminationRequest` with a blank group name will produce no authorization context at all. Please confirm this is the intended security posture — i.e., that a null context results in the request being **denied** rather than silently passing through. If the framework treats a null context as "no restriction," this would be a privilege-escalation vector.

#HB7JH, #QR74G, #0R09S: The guard checks `request.getGroup().getName()` for blankness, but does not guard against `request.getGroup()` itself being `null`. If a malformed or adversarial message omits the group entirely, this will throw a `NullPointerException` at the `.getName()` call. Consider a null-safe check such as:
```java
if (request.getGroup() != null && StringUtils.isNotBlank(request.getGroup().getName())) {
```

#HB7JH, #KMM6F, #3DXSQ, #QR74G, #SKKE3: The blank-name guard is applied only to the `NotifyClientTerminationRequest` branch, while the `ChangeInvisibleDurationRequest` and `QueryAssignmentRequest` branches still call `addGroupResourceAndPerm` / `newGroupSubContexts` unconditionally. If the motivation is to avoid registering a resource entry with an empty group name (which would pollute the permission map), the same risk exists in the other two branches. Please clarify whether those request types are guaranteed to always carry a non-blank group, or whether the guard should be applied uniformly.
