#0ZF4M: The test change looks correct and well-structured. The assertions are properly generalized from 10 to 256 documents, and the pragma overrides (`task_concurrency=10`, `data_partitioning=doc`) intentionally target the concurrent doc-partitioning code path that `ReinitializingSourceProvider` guards.
One minor observation: `randomPragmas()` may already set `task_concurrency` and `data_partitioning` to random values, which are then immediately overridden. This is fine for test intent, but a reader might wonder why the random values are generated at all. A brief inline comment (e.g., `// override to force the concurrent doc-partitioning path`) could make the intent clearer.

#DJ9MA, #YZ9VR: The refactoring from a single `perThreadProvider` field to a `ConcurrentHashMap` keyed by thread ID is a clear thread-safety improvement — the old code had a race where two threads could simultaneously pass the null/thread check, both create providers, and one would silently overwrite the other before the final read of `perThreadProvider.source`.
One concern: the map is never pruned. Each distinct thread that calls `getSource` leaves a permanent entry. In practice this is bounded by the Elasticsearch thread pool sizes, so it is unlikely to be a real leak. However, if this object is long-lived (e.g., cached across many queries) and the JVM spawns many short-lived threads over time, the map will grow monotonically. Consider whether a `WeakHashMap`-style approach or a size cap would be warranted, or at minimum document the assumption that the number of concurrent threads is bounded.
