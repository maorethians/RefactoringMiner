#28GMW: `preShutdown()` closes `writeOptions`, `deleteOptions`, and `defaultCFHandle`, but does not close `columnFamilyHandle` (the "popState" column family handle) or the `options` (DBOptions). This is a native resource leak — RocksDB native handles will not be released until the JVM exits. Both `columnFamilyHandle` and `options` should be closed here.

#7VE8W: `ConsumerRecords.getMinOffsetInBuffer()` calls `recordTreeMap.firstEntry()` and `getInFlightRecordCount()` calls `recordTreeMap.size()` without acquiring the `lock`. Since `TreeMap` is not thread-safe, concurrent calls to `write()` or `delete()` (which do hold the lock) can cause `ConcurrentModificationException` or inconsistent reads. These methods should acquire the lock before accessing the map, or the map should be replaced with a `ConcurrentSkipListMap`.

#DK6P0, #0ZM3V, #Z3EYJ: The loop `while (consumerLockService.tryLock(groupId, topicId)) {}` spins the CPU in a tight loop until the lock is acquired. Under contention this will burn CPU. Consider adding a `Thread.yield()` or a short `LockSupport.parkNanos()` inside the loop, or using a proper blocking lock mechanism.

#DK6P0: **`recode` logic contradicts its comment**: The comment states "The buffer should not be re-encoded when popResponseReturnActualRetryTopic is true", but the code does the opposite:
```java
boolean recode = brokerConfig.isPopResponseReturnActualRetryTopic();
if (recode && popConsumerRecord.isRetry()) { ... }
```
When `isPopResponseReturnActualRetryTopic()` is `true`, the code *does* re-encode. The condition should likely be `!brokerConfig.isPopResponseReturnActualRetryTopic()` to match the stated intent.

#0ZM3V: **Missing handling for `nextOffset == -2`**: The `commitAndNext` method can return `-2` (meaning "no need commit"), but the code only handles `> -1` (success) and `== -1` (error). When `-2` is returned, the method falls through both branches and returns without setting any response code or logging. This case should be explicitly handled (e.g., log and return success, or set an appropriate response).

#K149S: In `resetOffsetInner`, the call `brokerController.getPopConsumerService().clearCache(group, topic, queueId)` uses the outer `queueId` variable instead of `entry.getKey()`. Since this is inside a loop over `queueOffsetMap.entrySet()`, each iteration should clear the cache for the specific queue being reset (`entry.getKey()`), not the same `queueId` every time.

#RXXAV: The `dryRun` logic is counterintuitive:
```java
boolean dryRun = commandLine.hasOption('d') &&
    Boolean.FALSE.toString().equalsIgnoreCase(commandLine.getOptionValue('d'));
```
This means `--dryRun false` enables dry-run mode (no changes), while `--dryRun true` actually performs the export. The option is named "dryRun" but passing "false" activates it. This will confuse operators. Consider inverting the logic or renaming the option (e.g., `--execute`).

#VAK0Y, #8KPG1: Both diffs add `private final String reviveTopic;` to `PopMessageProcessor`. If both are at the class level in the same class, this would be a duplicate field declaration causing a compilation error. Please verify that only one declaration remains.

#HS6F5: In the new KV-service path of `processRequest`, when `result.isFound()` is `false` and polling succeeds (`POLLING_SUC`), the lambda returns `null`. The subsequent `thenAccept(result -> NettyRemotingAbstract.writeResponse(channel, request, result))` will then call `writeResponse` with a `null` response. While `writeResponse` is annotated `@Nullable`, this means the client receives no response at all for a successful long-poll registration. Verify this is the intended behavior (i.e., the client is expected to wait for a push notification) and that no response is needed to acknowledge the poll registration.
