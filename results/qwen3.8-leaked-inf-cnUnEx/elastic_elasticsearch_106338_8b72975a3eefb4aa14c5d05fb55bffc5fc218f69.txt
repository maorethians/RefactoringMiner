#HSMKX: The auto-store mutation (`store.setValue(true)`) is applied to the shared `Parameter` instance on the `Builder`. If the same `Builder` were ever reused for a second `build()` call (e.g., in a multi-tenant or retry scenario), the second call would see `store.isSet() == true` and skip the auto-store logic, silently producing a non-stored text field. In practice `Builder` instances are single-use, so this is unlikely to bite, but it's a latent coupling worth being aware of. A defensive alternative would be to compute the effective store value locally rather than mutating the parameter:
```java
boolean effectiveStore = store.value();
if (effectiveStore == false
    && store.isSet() == false
    && context.isSourceSynthetic()
    && TextFieldMapper.getKeywordFieldMapperForSyntheticSource(multiFields) == null) {
    effectiveStore = true;
}
// pass effectiveStore into TextParams.buildFieldType(...)
```
This avoids the side-effect on the shared parameter and makes the intent more explicit. That said, if the project convention is that `Builder` is strictly single-use, the current approach is acceptable.
