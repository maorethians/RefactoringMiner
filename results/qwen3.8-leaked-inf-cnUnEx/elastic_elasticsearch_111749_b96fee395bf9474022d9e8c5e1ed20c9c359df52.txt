#Q7PG8, #SZJB3, #86Q9T, #3V795, #X83CZ, #KVXJW, #7KY9K, #CT8XE, #CYZJC, #0SRRY, #NJN3B: In `MvPercentile.processDoubles`, `processInts`, and `processLongs`, the `if (valuesBlock.mvSortedAscending())` block is missing a `return` statement after appending the result. As written, when the data is already sorted ascending, the code:
1. Appends a result from the sorted path (using incorrect indices — see below), then
2. Falls through to the unsorted path (copy → sort → compute) and appends a **second** result.
This means every position in a sorted-ascending block gets two values appended to the builder instead of one, corrupting the output block. A `return;` is needed at the end of the `if (valuesBlock.mvSortedAscending())` block.

#NJN3B: In the sorted-ascending fast path of `processDoubles`, `processInts`, and `processLongs`, the value indices passed to `getDouble`/`getInt`/`getLong` do not account for `firstValueIndex`. For example:
```java
builder.appendDouble(valuesBlock.getDouble(0));              // should be firstValueIndex
builder.appendDouble(valuesBlock.getDouble(valueCount - 1)); // should be firstValueIndex + valueCount - 1
valuesBlock.getDouble(lowerIndex)                            // should be firstValueIndex + lowerIndex
valuesBlock.getDouble(upperIndex)                            // should be firstValueIndex + upperIndex
```
The `getDouble(int valueIndex)` method takes an absolute value index into the block, not an offset within the current position. Without adding `firstValueIndex`, these calls read from the wrong positions in the block (only correct when `position == 0`).

#NJN3B: In `calculateLongPercentile`, `new BigDecimal(fraction)` uses the `BigDecimal(double)` constructor, which captures the exact (often surprising) binary representation of the double (e.g., `new BigDecimal(0.1)` → `0.1000000000000000055511151231257827021181583404541015625`). Use `BigDecimal.valueOf(fraction)` instead, which goes through the canonical string representation and yields the expected decimal value.

#KNRP7: In `MvPercentileTests.makeSupplier`, the expected-value computation for the `Double` case uses `BigDecimal` arithmetic:
```java
return calculatePercentile(fraction, new BigDecimal(values[lowerIndex]), new BigDecimal(values[upperIndex])).doubleValue();
```
However, the implementation (`calculateDoublePercentile`) uses plain `double` arithmetic with a special case for sign-separated values. For large magnitudes (e.g., `±Double.MAX_VALUE`), the `BigDecimal`-based test oracle and the `double`-based implementation can diverge beyond the `closeTo` tolerance. Consider mirroring the implementation's `calculateDoublePercentile` logic in the test oracle, or widening the tolerance for the "big double difference" case.
