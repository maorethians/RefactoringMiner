#P60ZD, #5M04X, #40WAF: `pooledChunkAllocations` is only incremented in `allocateNormal`, but `pooledChunkDeallocations` is incremented in `freeChunk` for **both** `Normal` and `Small` size classes (the increment sits outside the `switch`). If `allocateSmall` also creates new chunks via `newChunk`, those allocations are never counted while their eventual deallocations are. This asymmetry means:
- `numChunkAllocations()` under-reports the true number of chunks created.
- `numActiveChunks()` (`allocations - deallocations`) can drift negative, silently clamped by `max(val, 0)`, hiding the accounting error.
The fix would be to also increment `pooledChunkAllocations` in the `allocateSmall` path (and any other size-class allocation path that calls `newChunk`), or to scope both counters to the same set of size classes and document that.
