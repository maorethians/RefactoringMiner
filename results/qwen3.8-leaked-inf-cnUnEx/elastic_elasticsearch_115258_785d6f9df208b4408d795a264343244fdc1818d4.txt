#1WBMD: The condition `Runtime.version().feature() < 20` appears to be inverted relative to the stated intent. The Javadoc says "This is not supported on JDK versions less than 20," and the note added in `Reverse.java` (#DG7CD) confirms the feature works correctly only on JDK 20+. However, `Runtime.version().feature() < 20` evaluates to `true` (enabled) on JDK < 20 and `false` (disabled) on JDK >= 20 — the opposite of what is intended.
This should likely be `Runtime.version().feature() >= 20` so the capability is reported as supported only when the runtime actually supports grapheme-cluster reversal.

#5QHE5: The `Cap(FeatureFlag featureFlag)` constructor now captures `featureFlag.isEnabled()` at enum-initialization time (class load), whereas the previous implementation called `featureFlag.isEnabled()` dynamically inside `isEnabled()` on every invocation. If any `FeatureFlag` instance can have its state toggled after startup (e.g., via a cluster setting or admin API), this is a behavioral regression: the capability's enabled state would be frozen at class-load time and would no longer reflect runtime changes.
If feature flags are guaranteed to be immutable after construction, this is fine, but it would be worth a brief comment or an `assert` to document that assumption. Otherwise, consider keeping the dynamic lookup for this constructor variant.
