#FHANM: The error messages in the LOGSDB no-explicit-sort-fields branch are misleading. When `INDEX_SORT_ORDER_SETTING` (or mode/missing) is present without `INDEX_SORT_FIELD_SETTING`, the thrown message says "size mismatch" and includes `fields` which is an empty list at that point (e.g., `"index.sort.fields:[] index.sort.order:[desc], size mismatch"`). The actual problem is that these companion settings are not allowed without an explicit `index.sort.field` — it's not a size mismatch. A clearer message would be something like:
```java
throw new IllegalArgumentException(
    "index.sort.order cannot be set without index.sort.field for logsdb indices"
);
```
The same applies to the `index.sort.mode` and `index.sort.missing` checks immediately below.

#EHQ6V, #98YN4: In `getMappingData`, when `LOGSDB_SORT_ON_HOST_NAME` is explicitly `false` in the request settings but the mapping contains a `host.name` field mapper, the returned `MappingData` has `sortOnHostName = true` (because of the `||` with the `instanceof FieldMapper` check). Then in `getAdditionalIndexSettings`, the provider injects `index.logsdb.use_default_sort_config=true`, silently overriding the user's explicit `false`. Consider whether the user's explicit `false` should be respected (i.e., short-circuit to `sortOnHostName = false` when the setting is explicitly present and `false`), or document that this setting is purely internal and should not be set by users.

#KTNZZ: The `timeStampSpec` instance is shared across `TIME_SERIES_SORT`, `TIMESTAMP_SORT`, and `HOSTNAME_TIMESTAMP_SORT`. This is currently safe because the code paths that use these arrays always return before reaching the mutation loops (`sortSpecs[i].order = ...`). However, this is a latent maintenance hazard: if a future change removes an early return or adds a new code path that mutates sort specs, it would silently corrupt the other shared arrays. Consider creating independent `FieldSortSpec` instances for each array to eliminate the shared-mutable-state risk.

#C93PY: The refactoring moves the `DiscoveryNode.isStateless` check from a guard around `init()` to a parameter. This means `mapperServiceFactory` is now always set (even for stateless), so `getMappingData` will actually create a `MapperService` for stateless deployments when it reaches the mapper-service code path. Previously, for stateless, `mapperServiceFactory.get()` would throw (SetOnce not set) and the catch block would return `MappingData.EMPTY`. Verify that creating a `MapperService` in stateless mode is safe and doesn't have side effects (e.g., file system access, resource leaks) that were previously avoided.

#0A5WA: The test asserts `hasPrimarySortOnField("host.name")` equals `sortOnHostName`, but this only holds when the index version is `>= LOGSB_OPTIONAL_SORTING_ON_HOST_NAME`. The test relies on `IndexSettingsTests.newIndexMeta` setting a sufficiently recent version. If that helper ever defaults to an older version, the BWC path would always return `true` and the test would fail for `sortOnHostName = false`. Consider explicitly setting the index version in the test metadata to make the intent clear and guard against regressions.
