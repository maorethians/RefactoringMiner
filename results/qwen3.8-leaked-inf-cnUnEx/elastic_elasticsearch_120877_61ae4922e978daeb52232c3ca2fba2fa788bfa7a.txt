#JVZR1, #A9XWN: The `threadContextUpdater` calls `threadPool.getThreadContext().putHeader(...)`, which mutates the thread-local `ThreadContext` (as shown in the dependency: `threadLocal.set(threadLocal.get().putRequest(key, value))`). After `execute()` returns, nothing in this code path explicitly removes or restores the header. If the thread is returned to the pool and reused for an unrelated operation before the framework resets the context, the `X-Opaque-Id` from this request could leak into that operation's context, causing deprecation warnings to be misattributed.
This is likely safe in practice because Elasticsearch's transport layer typically scopes and resets the `ThreadContext` per request, but it would be more defensive to either:
- Save and restore the previous header value (or the entire context) after `execute()` completes, or
- Add a brief comment noting that cleanup is the responsibility of the surrounding transport/task framework, so a future reader doesn't assume the header is self-cleaning.
