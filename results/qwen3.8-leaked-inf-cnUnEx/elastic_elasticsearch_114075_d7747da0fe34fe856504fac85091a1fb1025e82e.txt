#VKNJD, #4CX2R: The two methods `updateExecutionInfoAfterCoordinatorOnlyQuery` (in `ComputeService`) and `updateTookTimeForRemoteClusters` (in `EsqlSession`) share nearly identical iteration logic over `clusterAliases()` with the same `LOCAL_CLUSTER_GROUP_KEY` guard and the same `swapCluster` pattern. Consider extracting a small shared utility (e.g., a method on `EsqlExecutionInfo` itself, or a static helper) to reduce duplication and make the "skip local cluster" invariant easier to maintain if the set of conditions evolves.

#4CX2R: The condition `v.getTook() == null && v.getStatus() != EsqlExecutionInfo.Cluster.Status.SKIPPED` will also match clusters whose status is `FAILED` or any future non-SKIPPED terminal state. If an unavailable cluster is set to a non-SKIPPED status by `updateExecutionInfoWithUnavailableClusters` but its `took` is left null, this method would assign it a took time. Consider whether an explicit allow-list (e.g., only `RUNNING`) is safer than the current deny-list (everything except `SKIPPED`), to avoid inadvertently stamping took on clusters in unexpected states.

#1GW2J: The `updateExecutionInfoAfterCoordinatorOnlyQuery` call is placed inside `listener.map(...)`, so it only executes on the success path. If the coordinator-only compute fails, the execution info (overall took, remote cluster statuses) will remain in its pre-execution state. This is likely acceptable since the error is propagated to the caller, but it's worth confirming that no downstream consumer (e.g., Kibana's column-discovery flow) relies on `overallTook` being populated even on failure.
