```java
// Current (buggy):
assertThat(getApiKeyResponse, hasItem(transformedMatch(ApiKey::getRealmType, is(realm1Type))));
assertThat(getApiKeyResponse, hasItem(transformedMatch(ApiKey::getRealmType, is(realm1Type))));  // should be getRealmIdentifier
...
assertThat(getApiKeyResponse, hasItem(transformedMatch(ApiKey::getRealmType, nullValue())));
assertThat(getApiKeyResponse, hasItem(transformedMatch(ApiKey::getRealmType, nullValue())));  // should be getRealmIdentifier
```
The third assertion should be `transformedMatch(ApiKey::getRealmIdentifier, is(new RealmConfig.RealmIdentifier(realm1Type, realm1)))` and the sixth should be `transformedMatch(ApiKey::getRealmIdentifier, nullValue())`. Compare with the correctly-written equivalent in #4GH4W/#D3BSY (the query API keys section), which properly asserts on `getRealmIdentifier`. As written, the `getRealmIdentifier` contract is no longer tested in the `getApiKeys` path.

#T04CQ: `getApiKeyCreatorSubject` is invoked up to three times per API key: once in the initial `subjects` stream, and then twice in the response mapping (once for the null-check, once for the map lookup). Each call performs a `realmRefLookup.apply(...)` call. A cleaner and more efficient approach would be to pre-compute a `Map<ApiKey, Subject>` (or index-based list) upfront and reuse it in both the subject collection and the response mapping, avoiding redundant lookups:
```java
List<Subject> subjects = apiKeyInfos.stream()
    .map(this::getApiKeyCreatorSubject)
    .filter(Objects::nonNull)
    .distinct()
    .toList();
// ... in response:
// use a pre-built map or parallel list instead of re-calling getApiKeyCreatorSubject
```

#HQTBQ, #DRFHG: The size-mismatch validation is performed both before the loop (via `size()` comparison) and redundantly inside the loop (via `hasNext()` checks on the iterators). Since the upfront `size()` check guarantees the iterators will never be exhausted before the primary iterator, the in-loop checks are unreachable dead code. Removing them would simplify the logic and avoid the impression that a different failure mode is possible.
