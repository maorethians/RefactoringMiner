#26GQZ, #ESY71, #BJK93, #VY1B3, #FC7PS: The introduction of the `strict` parameter in `HttpVersion` and its usage in `valueOf` methods is clear, but it introduces a new behavior that should be documented. The existing constructors and methods do not specify whether they perform strict or lenient parsing, which could lead to confusion for users of the API.

#26GQZ: The `VERSION_PATTERN_STRICT` pattern does not allow for optional whitespace around the slash (`/`) between "HTTP" and the version numbers. This might be too restrictive if clients sometimes send versions with spaces (e.g., "HTTP /1.1"). Consider whether this strictness is necessary or if it should be configurable.

#QJSCB, #624V9: The comments added to `createMessage` methods in `HttpRequestDecoder` and `HttpResponseDecoder` are helpful for understanding the change, but they could be more descriptive about why strict version checking is being enforced. This would aid future maintainers or users of the code.

#VY1B3, #FC7PS: The new test cases added to `HttpRequestDecoderTest` and `HttpResponseDecoderTest` cover various invalid HTTP versions, which is good for ensuring that the strict parsing behaves as expected. However, consider adding tests for edge cases such as very long version strings or strings with unusual characters to ensure robustness.
