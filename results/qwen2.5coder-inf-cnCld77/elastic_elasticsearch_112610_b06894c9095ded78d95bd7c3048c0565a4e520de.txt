#5W338, #VD6V6: The logic for parsing the schema row in both `loadPageFromCsv` and `loadCsvData` has been modified to handle type mappings. However, the error handling for missing types is inconsistent. In `loadPageFromCsv`, an exception is thrown if `typeName` is null or empty, but in `loadCsvData`, no such check exists after splitting the schema entry. This could lead to a `NullPointerException` when `Type.asType(typeName)` is called with a null `typeName`.

#BBARN: The method `readMappingFile` is introduced to modify the mapping JSON based on `typeMapping`. This method uses Jackson's `ObjectMapper` to parse and manipulate the JSON. However, there is no error handling for potential exceptions that could be thrown by `mapper.readTree(mappingJsonText)` or `mapper.writerWithDefaultPrettyPrinter().writeValueAsString(mappingNode)`. These operations can throw `IOException`, which should be caught and handled appropriately.

#3550J: The method `load` has been refactored to use a `TestsDataset` object instead of individual parameters. This change simplifies the method signature but requires careful handling of null values, especially for `settingFileName`. The current implementation checks if `dataset.settingFileName` is not null before loading settings, which is correct. However, it would be beneficial to add comments or assertions to clarify that `mappingFileName` and `dataFileName` are expected to be non-null.

#EBXWQ: The new constructor and methods in the `TestsDataset` record provide a flexible way to create datasets with different configurations. However, the `withTypeMapping` method does not validate the provided `typeMapping`. It would be good practice to add validation to ensure that the keys and values in `typeMapping` are valid field names and data types, respectively.
