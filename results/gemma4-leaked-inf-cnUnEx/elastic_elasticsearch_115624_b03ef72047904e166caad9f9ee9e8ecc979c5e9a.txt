#9T1V4, #CS0C1: The implementation of the limit pushdown for `MvExpand` uses a non-standard approach by encoding the "outer" limit as a property within the `MvExpand` logical node rather than maintaining it as a separate `Limit` node in the logical plan. While this works because the `Mapper` (#CS0C1) explicitly reconstructs the physical `LimitExec` based on this property, it creates a discrepancy between the logical plan structure and the resulting physical plan. Specifically, the transformation in `#9T1V4` (`MvExpand -> Limit -> Child`) results in a physical plan of `LimitExec (outer) -> MvExpandExec -> LimitExec (inner) -> ChildExec`. This is functionally correct but relies on a tight coupling between the optimizer rule and the mapper.

#P1YFQ: The use of `assert limit == null;` in `writeTo` is risky. If the application is run with assertions enabled (`-ea`), any attempt to serialize an optimized logical plan (where `limit` has been populated by the optimizer) will trigger an `AssertionError`. While the constructor from stream (#H9HS1) explicitly resets this value to `null`, indicating that the optimization is not preserved across serialization, using a hard assertion here may cause unexpected crashes in environments where assertions are enabled. A safer approach would be to simply omit the field from serialization without asserting its state.
