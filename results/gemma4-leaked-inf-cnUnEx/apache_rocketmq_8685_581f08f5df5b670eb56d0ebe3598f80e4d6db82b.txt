#ZT9CD: The use of `channelWrapperTables.computeIfPresent` to handle reconnection introduces two significant issues:
1. **Memory Leak**: The remapping function returns `channelWrapper0`, which preserves the mapping for the old `channel` key in the map. Simultaneously, a new mapping is added for the new channel via `channelWrapperTables.put(...)`. This results in multiple keys (the old and new channels) pointing to the same `ChannelWrapper`, causing the old `Channel` objects to leak in memory.
2. **Potential Deadlock/Concurrency Issue**: The Java documentation for `ConcurrentHashMap.computeIfPresent` explicitly warns that the remapping function should not attempt to update other mappings of the map. Modifying the map inside the compute function can lead to deadlocks or undefined behavior, especially if the old and new channel keys hash to the same bin.
A safer approach would be to remove the old mapping first using `remove(channel)` and then conditionally put the new mapping.

#E7JNC, #JB0F4: The removal of `lastReconnectTimestamp` and its associated check in `reconnect()` removes the rate-limiting mechanism for reconnections triggered by "GO_AWAY" signals. Without a minimum interval between reconnection attempts, the client may enter a tight loop of connection attempts if the server repeatedly sends "GO_AWAY" responses, potentially increasing load on both the client and server.
