#B4JT9, #94Q6X, #K33S7: The removal of `handleAlreadyShuttingDownWorker()` and the associated `isShutdown()` checks in both `forcefullyStopProcess` and `stopProcessAfterCompletingPendingWork` creates a gap in task cleanup. Previously, if the worker was already shut down, `notifyQueueRunnables()` was called to ensure all pending tasks in the queue were notified of failure or rejection. With these changes:
1. In `forcefullyStopProcess`, calling `shutdownNow()` and awaiting termination does not trigger `notifyQueueRunnables()`. Consequently, any tasks remaining in the queue will not be explicitly failed/rejected.
2. In `stopProcessAfterCompletingPendingWork`, if the worker is already shut down, `signalAndWaitForWorkerTermination` will likely return without timing out, bypassing the only remaining call to `notifyQueueRunnables()`.

#B4JT9: In the `InterruptedException` catch block, the log message uses the generic constant `PROCESS_NAME` ("inference process") instead of the specific deployment ID (`task.getDeploymentId()`). For better traceability in logs, it is recommended to use the deployment ID to identify which specific model process was interrupted.
