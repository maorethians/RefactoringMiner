#F31TQ, #ERA66, #P2K7F, #XYXPC: The call to `handleData.lock(timeout)` is performed inside a `ConcurrentHashMap` compute lambda (`compute` or `computeIfPresent`). In Java's `ConcurrentHashMap`, these methods lock the internal hash bin for the duration of the lambda. Because `lock()` calls `semaphore.tryAcquire(timeoutMs, ...)`, which can block for the full timeout period, this will hold the map's internal lock and potentially block all other threads attempting to access any key that maps to the same hash bin. To avoid this contention, consider acquiring the lock outside the compute lambda or using a non-blocking approach.

#E3SBJ, #M9S22: The logic uses `System.currentTimeMillis()` to calculate elapsed time for lock expiration and timeouts. `currentTimeMillis` is subject to system clock adjustments (e.g., NTP syncs), which can cause the clock to jump forward or backward. This could lead to locks expiring prematurely or failing to expire. For measuring durations, `System.nanoTime()` should be used as it provides a monotonic clock.

#M9S22: The "force lock" (steal) mechanism allows a thread to proceed if the previous lock holder has exceeded the expiration threshold, even though the semaphore permit was not actually acquired. While this is intended as a recovery mechanism for hung locks, it means that if a previous holder is merely slow rather than deadlocked, multiple threads could enter the critical section simultaneously (e.g., if Thread B steals from A, and then Thread C steals from B). This breaks mutual exclusion and may lead to race conditions when updating `HandleData` fields.
