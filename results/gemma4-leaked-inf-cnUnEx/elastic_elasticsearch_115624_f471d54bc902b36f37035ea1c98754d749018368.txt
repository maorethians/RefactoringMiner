#89XMM: In `#89XMM`, when a `Limit` node is encountered above an `MvExpand` node:
- The code updates the `MvExpand` limit to $\min(\text{existing}, \text{current})$.
- It then pushes the original `Limit` node below the `MvExpand`.
If the existing `mvxLimit` was already smaller than the current `limitVal`, the resulting plan becomes: `MvExpand(limit=small) -> Limit(large) -> child`. 
While logically correct (the outer limit will constrain the result), it is slightly inefficient as the pushed-down `Limit` node still uses the larger value, potentially fetching more rows from the child than necessary. It would be more optimal to push down a `Limit` node using $\min(\text{existing}, \text{current})$.

#89XMM: In `#89XMM`, the code performs a direct cast: `var limitVal = (int) limitSource.fold();`. 
This assumes that the limit expression is always foldable to an integer. While this matches existing patterns in `PushDownAndCombineLimits` (as seen in the `descendantLimit` dependency), it remains a fragile point if non-constant expressions are ever permitted in limits, as it would trigger a `ClassCastException`.
