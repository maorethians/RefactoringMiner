#ZGAH3, #7HB6Z, #3AM91, #QD8N5: There is a critical inconsistency between the updated index mapping and how the data is both stored and accessed:
1. **Mapping Change**: In `#ZGAH3`, the mapping for `host` and `cloud` is changed from flat fields (e.g., `host.id`) to object structures with nested properties (`host: { properties: { id: ... } }`).
2. **Data Mismatch**: The test data in `#7HB6Z` and `#QD8N5` continues to use flat keys with dot-notation (e.g., `"host.id": "..."`, `"cloud.provider": "..."`). In Elasticsearch, indexing a document with a flat key like `"host.id"` will not populate the nested property `id` of the `host` object; instead, it will create a separate flat field named `host.id`.
3. **Logic Mismatch**: The Java logic in `#3AM91` attempts to retrieve these values using flat keys (e.g., `source.get("cloud.provider")`). If the mapping is an object, the resulting map from Elasticsearch would be nested (`source.get("cloud")` returning a Map), and `source.get("cloud.provider")` would return `null`.
To resolve this, either the index mapping should remain flat, or both the data ingestion (test data) and the retrieval logic in `InstanceType.java` must be updated to use nested object structures.
