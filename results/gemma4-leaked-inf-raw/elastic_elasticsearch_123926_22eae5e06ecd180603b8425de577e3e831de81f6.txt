#TF1DC: **Issue 1: Improper error handling in asynchronous callbacks**
In several methods, exceptions are thrown directly inside `ActionListener` callbacks instead of calling the `markAsFailed(Exception e)` method. Because this is a `PersistentTask`, throwing an exception within a callback will likely result in the thread terminating or the error being logged without updating the task's state in the cluster metadata. This prevents the migration from being officially marked as failed and may lead to inconsistent task states.
Specifically, this occurs in:
- `migrateDataStream`: when `startMigrationResponse.isAcknowledged()` is false.
- `dataStreamMigrationFailed`: where it throws a newly constructed `ElasticsearchException`.
- `cancelExistingDataStreamMigrationAndRetry`: when the cancellation response is not acknowledged.

#TF1DC: **Issue 2: Inaccurate logging/exception message**
In `dataStreamMigrationFailed`, the exception message is constructed using string concatenation with the `migrationInfo` object:
`"error occurred while reindexing data stream [" + migrationInfo + "]"`
Since `SystemDataStreamMigrationInfo` does not override `toString()`, this will produce a generic object reference (e.g., `org.elasticsearch...SystemDataStreamMigrationInfo@hash`) instead of the actual name of the data stream. It should use `migrationInfo.getDataStreamName()`.
