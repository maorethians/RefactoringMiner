#RQ566: The implementation of `unsignedLongAsLongExact` appears to have inverted logic for overflow detection. If the input `l` (representing an unsigned long) is non-negative, it already fits within a signed long and should be returned. Instead, the current code throws an `ArithmeticException`. Conversely, if `l` is negative, it represents a value $\ge 2^{63}$, which cannot fit into a positive signed long, yet the code attempts to return a converted value.

#90GCR: In the `unsignedDifference` method, signed comparison operators (`>=`, `<`) are used on variables that represent unsigned long values. In Java, this leads to incorrect results because negative signed longs (which represent large unsigned values) are treated as smaller than positive signed longs. For example, if `a` is the maximum unsigned value (represented as `-1L`) and `b` is `0L`, the condition `a >= b` evaluates to `false`, leading to an incorrect absolute difference calculation. These should be replaced with `Long.compareUnsigned(a, b)`.

#90GCR: The method `unsignedDifference` is used within `finish` and `ascending` for long/unsigned long types. Because it produces incorrect results for large unsigned values (as noted above), the resulting Median Absolute Deviation (MAD) calculation will be incorrect for any dataset where the median or data points have the high bit set.
