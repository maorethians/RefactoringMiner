#SKDDZ: **Incorrect Lock Acquisition Loop in `clearCache`**
- **Diff ID:** `#SKDDZ`
- The loop `while (consumerLockService.tryLock(groupId, topicId)) {}` is logically inverted. It will continue to loop as long as the lock is successfully acquired and only exit when it fails to acquire the lock. This prevents the method from ever executing its core logic while holding the lock and likely results in an immediate `IllegalMonitorStateException` or similar failure when calling `unlock()` in the `finally` block because the lock was not held upon exiting the loop. It should be `while (!consumerLockService.tryLock(groupId, topicId)) {}`.

#SKDDZ: **Potential Lock Leak in `popAsync`**
- **Diff ID:** `#SKDDZ`
- The lock is acquired via `consumerLockService.tryLock(groupId, topicId)`. The release logic (`unlock`) is attached to the completion of the asynchronous chain using `.whenComplete(...)`. However, if a `Throwable` is caught in the `catch (Throwable t)` block before the future chain is fully constructed and returned, the lock will never be released. The `unlock` call should be ensured regardless of whether the async chain was successfully initiated.

#XS6TQ, #QTNF0, #0N9W1: **Resource Exhaustion via Busy-Wait Loops**
- **Diff IDs:** `#XS6TQ`, `#QTNF0`, `#0N9W1`
- Several methods (`appendAckNew`, `ackOrderlyNew`, and `processChangeInvisibleTimeForOrderNew`) use empty `while` loops to wait for a lock: `while (!consumerLockService.tryLock(...)) {}`. This is a "busy-wait" that consumes 100% CPU on the executing thread until the lock is available. In a high-concurrency broker environment, this can lead to severe performance degradation. Consider using a timed wait or `Thread.onSpinWait()` (Java 9+) to hint to the JVM that the thread is spinning.

#SKDDZ: **Blocking Call in Service Thread**
- **Diff ID:** `#SKDDZ`
- In `PopConsumerService.revive`, the code calls `CompletableFuture.allOf(futureList.toArray(new CompletableFuture[0])).join()`. This blocks the service's main execution thread until all asynchronous revive operations (which may involve network I/O via the escape bridge) are complete. If a large number of records expire simultaneously or if there is latency in the underlying storage/network, this will stall the entire `PopConsumerService` loop.

#3R2YR: **Platform-Dependent Byte Encoding**
- **Diff ID:** `#3R2YR`
- In `PopConsumerRecord.getKeyBytes()`, the methods `groupId.getBytes()` and `topicId.getBytes()` are called without specifying a charset. This uses the platform's default charset, which can lead to inconsistent key generation and data corruption if the broker is migrated across different operating systems or environments with different default encodings. Use `StandardCharsets.UTF_8` explicitly.

#P9F6T: **Redundant/Duplicate Logic in `PopMessageProcessor`**
- **Diff ID:** `#P9F6T`
- The logic for building subscription data for the origin topic and the retry topic is duplicated almost exactly across two different blocks (one for when `requestHeader.getExp()` is present and one for when it is not). This should be extracted into a helper method to improve maintainability and reduce the risk of divergent behavior between these paths.
