#W996H: The logic in `findRedundantSort` contains a correctness bug regarding how it identifies redundant sorts. 
Currently, when the traversal encounters an `OrderBy` node, it immediately adds it to the `redundant` map before checking if any subsequent operations depend on that sort's order:
```java
if (p instanceof OrderBy ob) {
    result.put(ob, null); // Marked redundant immediately
    toCheck.push(ob.child());
} else if (p instanceof SortAware sa && sa.dependsOnInputOrder() == false) {
    // ... continue traversal
}
```
If a plan is structured as `TopN (Root) -> OrderBy (Inner) -> WindowFunction (DependsOnInputOrder = true)`, the following happens:
1. The root `TopN` triggers the rule, and `findRedundantSort` starts at `OrderBy (Inner)`.
2. `OrderBy (Inner)` is immediately added to the redundancy map.
3. The traversal moves to `WindowFunction`, which returns `true` for `dependsOnInputOrder()`, causing the traversal for that branch to stop.
4. The result is that `OrderBy (Inner)` is pruned, even though the `WindowFunction` requires the order it provides.
To fix this, a sort should only be marked as redundant if no node in the subtree below it (until another sort or a leaf) depends on input order.
